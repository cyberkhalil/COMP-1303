7.1 · Why Virtual Memory

In Week 2 we saw that every process has its own address space — the range of memory addresses it can touch. But we never explained how the operating system actually delivers that promise. How does each process get its own private view of memory, when there is only one physical RAM chip shared by everybody? That is the subject of this week.

The answer is virtual memory — one of the most important abstractions in all of computing. It gives every process the illusion of having a large, private, contiguous block of memory, while the kernel quietly juggles its pages between physical RAM, caches, and the disk.

The problem we are solving

Imagine we had no virtual memory. Each process would be loaded directly into physical RAM at some base address. Three serious problems arise immediately:

Problem 1 — No isolation

A buggy program could read or write another program's memory simply by using the right address. There would be no hardware check to stop it. One buggy process could corrupt or crash every other running process — and the OS as well.

Problem 2 — Fragmentation

Processes come and go. If each one needs a contiguous block of RAM, the free space becomes fragmented over time. A process that needs 100 MB might be unable to fit even if the total free memory is 500 MB, because the free space is scattered in 50 MB chunks.

Problem 3 — No flexibility

Programs would need to know at load time how much space the heap and stack would need. The heap could never grow past a fixed limit. Sharing code between processes would require loading duplicate copies of the same binary into RAM.

The solution

Introduce a layer between the addresses a program uses and the physical addresses of RAM. Program addresses become virtual; the kernel and hardware translate them to physical addresses on the fly. Every access goes through this translation.

The address space abstraction

Every process is given a fictitious-looking range of addresses — usually starting at 0 and extending up to some large limit (e.g., 48 bits on x86-64 Linux, giving 256 TB of address space). This is the process's virtual address space. It is not tied to any particular physical location.

The process sees a simple layout: code at the bottom, then data, then heap growing up, then a big gap, then stack growing down. This is the exact picture we saw back in Week 2. But underneath, the kernel may place those regions anywhere in physical memory — or nowhere at all until they are actually touched.

Two processes, each with its own virtual address space, mapped onto interleaved regions of physical RAM — without either process knowing about the other.

What virtual memory gives us

Virtual memory is not one feature, it is a bundle of four very valuable properties:

Property What it means
Isolation Process A cannot read or write process B's memory — the hardware refuses any access the kernel has not explicitly mapped.
Flexibility Heap and stack can grow independently. Regions can be mapped or removed at runtime. The code segment can be shared between processes.
Overcommit Processes can have address spaces larger than physical RAM. The kernel spills cold pages to disk and brings them back on demand.
Density Physical RAM is used only for what is actually being touched right now. Multiple processes fit in RAM at once even if their combined virtual size exceeds it.
The one-line summary: virtual memory decouples the addresses a program uses from the physical addresses of the hardware, giving each program a private, protected, flexible view of the machine.

7.2 · Contiguous Allocation & Fragmentation

The simplest way to implement address spaces is called contiguous allocation: each process gets one single contiguous block of physical memory. The kernel tracks a base register and a limit register for each process, and the hardware checks every access against them.

Base and limit registers

The base register contains the physical address where the process's memory begins. The limit register contains the size of that region. When the CPU translates a virtual address v, it performs these steps in hardware:

  1. Check that v < limit. If not, raise a trap — segmentation fault.
  2. Add the base: physical address = base + v.
  3. Use the physical address to access RAM.

This gives a basic form of isolation — a process cannot reach outside its block. But it has a serious limitation: the whole block must be contiguous in physical memory.

The fragmentation problem

Consider a system with 1 GB of RAM and three processes, each taking roughly 250 MB. After they load, the free space is scattered in the gaps between them. Now a fourth process needs 300 MB. It cannot fit anywhere contiguously — even though the total free memory might be enough.

This is called external fragmentation: free memory exists, but not in a form that can satisfy an allocation request. It is one of the two great curses of memory management.

External fragmentation

Free memory exists as many small holes between allocations. A new allocation cannot fit even though total free memory exceeds what is needed. This is the classic problem of contiguous allocation.

Internal fragmentation

Allocated memory is larger than requested — the extra space is wasted inside the allocation. This happens when allocations are rounded up to a fixed unit (e.g., 4 KB blocks). We will see this with paging.

External fragmentation: three free holes exist, but none is large enough to satisfy the 200 MB request — even though the total is more than sufficient.

Can we fix it?

The classic response is compaction: move all the processes together so the free memory becomes one large contiguous block. This works, but it is very expensive — every process has to be paused, its entire memory copied to a new location, and all the pointers and addresses in the process fixed up. On modern systems with gigabytes of memory, compaction is completely impractical.

The real solution is to abandon contiguity altogether. That is exactly what the next two techniques do — and they are the ones real operating systems use.

7.3 · Segmentation

Contiguous allocation treats the whole address space as one big block. But we already know that an address space is not one block — it is several logically distinct regions: code, data, heap, and stack. Segmentation is the idea of treating each region separately, giving each its own base and limit register.

The mechanism

With segmentation, the kernel maintains a table — the segment table — with one entry per segment. Each entry contains a base and a limit for that segment.

When the CPU sees a virtual address, it is interpreted as two parts: a segment number in the high bits, and an offset within that segment in the low bits. The hardware:

  1. Reads the segment number from the virtual address.
  2. Looks up that segment in the segment table to find its base and limit.
  3. Checks that offset < limit. If not — a trap.
  4. Computes the physical address as base + offset.
A virtual address is split into a segment number and an offset. The segment table translates each segment independently, so the regions do not need to be contiguous in RAM.

What segmentation buys us

  • Regions can grow independently. The heap can expand without pushing the rest of the address space around.
  • Sharing becomes easy. The code segment can be shared by mapping multiple processes' code segment entries to the same physical base.
  • Protection is per-segment. The hardware can mark segment 0 as read-only, segment 1 as read-write, and so on.

But it does not solve everything

Segments still have to be contiguous within themselves. If the heap segment grows from 1 MB to 2 MB, we may need to move the entire heap to a new location where 2 MB is available. And we still have external fragmentation — the segments themselves are variable-sized blocks scattered through physical memory.

The fix for this is a more radical idea. Instead of dividing memory into the logical regions of a program, divide it into fixed-size chunks and let each chunk live wherever it wants. That idea is called paging, and it is the way every modern operating system actually works.

7.4 · Paging — The Big Idea

Paging takes the address space and chops it into small fixed-size pieces called pages — typically 4 KB each on x86-64 systems. Physical RAM is chopped into the same-size pieces, called frames. And then the kernel is free to put any page into any frame — they do not need to be adjacent at all.

The core idea in one sentence: paging completely eliminates external fragmentation, because any free frame will do — there is no "large enough contiguous block" to search for.

How a virtual address splits

A virtual address in a paged system is interpreted as two numbers:

  • Virtual page number (VPN): the upper bits — which page of the address space we are addressing.
  • Offset: the lower bits — where we are inside that page. Since a page is 4 KB, the offset uses 12 bits (212 = 4096).

With a 4 KB page, the low 12 bits of any virtual address are the offset and go through translation unchanged. The high bits are the VPN — they are the ones the kernel translates to a physical frame number (PFN). 

Virtual address (32-bit example, 4 KB pages):
┌───────────────────────┬──────────────────┐
│    VPN (20 bits)      │  Offset (12 bits)│
└───────────────────────┴──────────────────┘
         ↓
      Translated via page table
         ↓
┌───────────────────────┬──────────────────┐
│    PFN (20 bits)      │  Offset (12 bits)│
└───────────────────────┴──────────────────┘
            Physical address
The page table maps virtual pages to physical frames. There is no requirement that the frames be contiguous — any free frame will do. VP 1 is unmapped (would cause a page fault if touched).

The page table

The page table is the data structure that holds the mapping. It is an array indexed by virtual page number, where each entry contains the physical frame number (PFN) plus a few flag bits — a valid bit, a dirty bit, a permission bit, etc.

Every memory access the CPU makes goes through this table. That is the price of paging: we have added an extra memory access (to read the page table) before every load or store. We will see shortly how the TLB eliminates most of that cost.

Paging in numbers — why page size matters

The page size is a design choice, and it affects everything:

Page size Advantages Disadvantages
Small (e.g. 4 KB) Less internal fragmentation — wasted space inside a page is small. Larger page tables and more TLB misses.
Large (e.g. 2 MB) Smaller page tables and fewer TLB misses. More internal fragmentation — a program using 1 byte of a 2 MB page wastes 2 MB.

x86-64 supports multiple page sizes simultaneously — 4 KB for small allocations, 2 MB and 1 GB for large ones. The operating system picks what makes sense. Linux, by default, uses 4 KB pages for regular memory and transparent huge pages (2 MB) for large allocations, to reduce TLB pressure.

Why paging wins: paging eliminates external fragmentation entirely — any free frame will do — and makes memory sharing simple, because a page table entry is basically a pointer that multiple page tables can point at the same frame.

7.5 · Page Tables & the TLB

Here is the problem. On a system with 4 KB pages, almost every address the CPU sees will fall on a different page. Every single memory access — including the access to fetch the next instruction — requires a page-table lookup. Without help, every memory operation becomes two memory operations, halving performance.

Real systems solve this with a small, fast, hardware-managed cache: the Translation Lookaside Buffer, or TLB.

What the TLB is

The TLB is a cache of recent virtual-to-physical translations. For our purposes it looks like a small lookup table with just a few dozen to a few thousand entries:

VPN PFN Flags
0x000040x00000valid, R, X (code)
0x000050x00007valid, R, W (data)
0x000120x00002valid, R, W (heap)
0x000280x00011valid, R, W (stack)
… dozens or hundreds more entries

The TLB is not a normal memory structure. It is not indexed by address — it is indexed by content. You hand it a VPN, and it tells you the PFN if it has one, or not found if it does not. This is a content-addressable memory implemented directly in silicon.

The TLB hit path

When the CPU handles a memory access with the TLB in play, this is what happens:

  1. Split the virtual address into VPN and offset.
  2. Look up the VPN in the TLB.
  3. Hit: get the PFN from the TLB, combine with offset, proceed. Done. This takes a single CPU cycle or two.
  4. Miss: walk the page table in memory (slow), get the PFN, insert it into the TLB for next time, then proceed.
Why this is such a big win: thanks to cache locality — programs access a small working set of pages repeatedly — the TLB hit rate is typically over 99%. So the expensive page-table walk happens rarely, and the common case is essentially free.
The TLB turns almost all virtual-to-physical translations into a single-cycle lookup. On a context switch the TLB must be flushed, or the CPU uses Address Space Identifiers (ASIDs) to keep them separate.

The TLB and context switches

Here is a subtlety. When the kernel switches from process A to process B, the TLB still contains translations from A's address space. B's address space means completely different virtual-to-physical mappings. If we did nothing, B would be using A's translations — which would be catastrophic.

There are two ways the hardware handles this:

  • Flush the TLB on every context switch. Simple, but expensive — every process starts cold, with an empty TLB, and pays the cost of page-table walks for its first several thousand memory accesses.
  • Use Address Space Identifiers (ASIDs). Each TLB entry is tagged with an ID identifying which address space it belongs to. Context switches do not need to flush — the CPU just checks the ASID and ignores entries belonging to other processes.

Modern x86-64 CPUs use a variant of ASIDs called PCIDs (Process Context Identifiers). ARM and RISC-V have equivalents. This is one of the reasons modern systems can context-switch so efficiently compared to older machines.

7.6 · Multi-Level Paging

The page table is a data structure that lives in memory. On a 64-bit system like x86-64, the virtual address space is enormous. If we used a single-level page table with 4 KB pages, the table would need 252 entries — one for every possible 4 KB page in a 64-bit address space. That is trillions of entries, none of which could fit in real memory.

The fix is called multi-level paging. Instead of one giant flat table, we use a tree of small tables. Only the branches that are actually used exist in memory — the rest are marked as empty, and cost nothing.

The four-level tree on x86-64

x86-64 uses a four-level page table tree. A 48-bit virtual address is split into five chunks: 

48-bit virtual address, 4 KB pages:

┌────────┬────────┬────────┬────────┬───────────┐
│ PGD    │ PUD    │ PMD    │ PTE    │  Offset   │
│ 9 bits │ 9 bits │ 9 bits │ 9 bits │  12 bits  │
└────────┴────────┴────────┴────────┴───────────┘
   │        │        │        │         │
   │        │        │        │         └─→ position in page
   │        │        │        └─→ level-1 PTE (leaf)
   │        │        └─→ level-2 page middle directory
   │        └─→ level-3 page upper directory
   └─→ level-4 page global directory (root)

Walking the tree to translate a single virtual address requires four dependent memory accesses — plus one more for the actual data. Without caching, that would be five memory accesses for every load or store. This is exactly why the TLB is so essential.

Multi-level paging stores only the branches that are actually used. Most of the address space has no table reserved — the tree is sparse.

What multi-level paging buys us

  • Sparse mapping is cheap. A process that only uses 10 MB of its 48-bit address space only has tables for those 10 MB. The rest of the tree is empty.
  • Large regions can use huge pages. A big contiguous region can be covered by a single entry in a higher level of the tree — for example, a 2 MB page covers 512 leaf entries.
  • Tables can be swapped to disk. If a leaf table is not needed for a while, the kernel can move it to swap.
The cost: a full page-table walk now requires four memory accesses instead of one. Real systems mitigate this with the TLB and with caching of interior tables, but the underlying complexity is real. This is what real operating system engineers spend their careers optimizing.

7.7 · Demand Paging & Page Faults

Up to this point we have assumed that the whole virtual address space of a process is mapped into physical RAM. But that is not how real systems work. Real processes can have address spaces much larger than physical RAM — some run on machines with 4 GB of RAM while having 100 GB address spaces.

The trick is demand paging: pages are only loaded into RAM when they are actually touched. Until then, they live on disk — usually in a swap file or a memory-mapped file. When a page is accessed but not currently in RAM, the hardware raises a page fault and the kernel fetches it.

The page fault mechanism

Here is what happens when a program touches a page that is not in RAM:

  1. The CPU translates the virtual address, finds the page table entry marked as not present, and raises a page fault exception.
  2. The CPU traps into the kernel.
  3. The kernel:
    • Checks that the access is legitimate (the page is mapped, just not resident). If not, the process gets a segmentation fault.
    • Finds a free physical frame (or evicts a page to create one — see section 7.8).
    • Reads the page from disk into that frame (this involves scheduling a disk I/O and blocking the process).
    • Updates the page table to mark the entry as present and point to the new PFN.
    • Returns from the trap.
  4. The CPU re-executes the offending instruction — this time the translation succeeds.
Why demand paging wins: most programs only use a small fraction of their address space at any moment. Loading the entire address space on startup would be a huge waste. Demand paging means we only load the pages that are actually used — and we can evict the ones that are not.

How long does a page fault take?

A page fault is expensive because it involves disk I/O. The numbers are stark:

Operation Approximate time Notes
CPU access in RAM ~100 ns A cache miss going to DRAM
TLB hit ~1 ns Almost free
TLB miss with page-table walk in RAM ~200–500 ns Additional memory accesses
Page fault, page on SSD ~50,000–100,000 ns Solid-state disk read
Page fault, page on spinning disk ~5,000,000–10,000,000 ns Seek + rotational latency

A page fault from spinning disk is roughly 50,000 times slower than a normal memory access. If even one in a thousand accesses hits this slow path, the overall slowdown is catastrophic. That is why the page replacement algorithm has to be very good at keeping the working set in RAM.

7.8 · Page Replacement Algorithms

When a page fault occurs but there is no free physical frame available, the kernel has to evict — pull a page out of RAM, write it back to disk if it was dirty, and use the freed frame for the incoming page. Which page should be evicted? That is the page replacement problem, and it has been studied for over fifty years.

How we measure replacement algorithms

We test algorithms on a reference string — a sequence of page accesses — and count how many page faults occur as we process it. The lower the fault count, the better the algorithm, given a fixed number of physical frames.

The three classic algorithms, in order of increasing quality, are FIFO, LRU, and Optimal. Let's walk through each on the same example: reference string 7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1 with three physical frames.

FIFO — First In, First Out

The simplest algorithm. Keep the pages in a queue ordered by arrival time. When you need to evict, throw out the oldest one — the one that has been in memory the longest.

Simple to implement with a queue. But it has a nasty property: it can evict a page that is used constantly, simply because it happens to have arrived early. And it suffers from Belady's anomaly — adding more physical frames can sometimes increase the number of page faults. That is deeply counter-intuitive.

Belady's anomaly in action

Consider the reference string 1 2 3 4 1 2 5 1 2 3 4 5. With three frames, FIFO causes nine faults. With four frames, FIFO causes ten faults. More memory means more faults — an absurd result, and the reason FIFO is not used in practice.

LRU — Least Recently Used

Much better. On eviction, throw out the page that has not been used for the longest time. The idea: if a page has been untouched for a while, it probably will not be needed soon.

LRU is not optimal — it can be fooled by cyclic access patterns over slightly more pages than fit in memory — but it works very well in practice and does not suffer from Belady's anomaly.

The catch: implementing true LRU requires updating a data structure on every single memory access. On a real system, that is prohibitive — millions of updates per second. Real systems approximate LRU using hardware support (the accessed bit in the page table) — see "Clock" below.

Optimal (OPT) — Replace what will be used furthest in the future

If we could see into the future — if we knew which page would be accessed furthest from now — we could evict that one and achieve the minimum possible number of faults. This is called Optimal or Belady's Algorithm, and it is the theoretical optimum.

Of course, we cannot know the future. Optimal is useless in practice — but it is extremely valuable as a benchmark. It tells us how much room for improvement a real algorithm has. If LRU gets within 10% of Optimal on a workload, we know it is doing well.

Clock — the practical approximation of LRU

Real systems use the accessed bit in the page table entry — a single bit that the hardware sets whenever the page is touched, and that the kernel can clear. This gives a cheap, approximate signal of recent use.

The Clock algorithm layers on top of that. Imagine pages arranged in a circle — like a clock face — with a hand that sweeps around. When we need a victim:

  1. Look at the page under the hand.
  2. If its accessed bit is 1, clear it to 0 and move the hand forward. The page has been used recently — give it another chance.
  3. If its accessed bit is 0, evict that page.

This approximation of LRU costs almost nothing per access — the hardware sets a single bit — and achieves most of LRU's benefit.

Algorithm Idea Practical? Belady's anomaly?
FIFO Evict the oldest page. Yes — trivial to implement. Yes — a fatal flaw.
LRU Evict the least recently used. Rarely in practice — too expensive. No — stack algorithm.
Optimal (OPT) Evict what will be used furthest later. Never — requires knowing the future. No.
Clock Approximate LRU with an accessed bit. Yes — used by real kernels. No.
The bottom line: real operating systems use approximations of LRU — Clock, or enhanced variants like CLOCK-Pro and the multi-generational LRU used by recent Linux kernels. The accessed bit and the dirty bit in the page table are the tools that make these approximations possible at full CPU speed.

7.9 · Thrashing & the Working-Set Model

Once we have virtual memory, an interesting failure mode appears. If the system tries to run too many processes with too little physical RAM, every process spends most of its time waiting for page faults to be resolved by disk. The CPU is idle, but the system is completely unusable. This is thrashing.

The thrashing death spiral

The pathological sequence goes like this:

  1. Too many processes are running for the available RAM.
  2. Each one, individually, does not have enough frames to hold its working set.
  3. Page faults increase sharply.
  4. Each page fault must wait for disk I/O.
  5. While waiting, the CPU is idle. The scheduler notices the idle CPU and thinks: "the load is low, I should run more processes."
  6. More processes are launched, making the memory pressure worse.
  7. Repeat.

In the terminal stage, the disk is being hammered by page faults, the CPU is idle, and total system throughput collapses to near zero. On old systems with spinning disks, this looked like the machine had frozen.

CPU utilization rises as more processes are added — up to a point. Past a threshold, adding more processes causes thrashing, and CPU utilization collapses because everyone is waiting for page faults.

The working-set model

The fix is to explicitly track each process's working set — the set of pages it has been using recently — and to give each process enough frames to hold its working set. If a process cannot be given enough frames, it should be swapped out entirely rather than allowed to thrash.

The classic definition uses a time window. If we call pages that have been accessed in the last Δ seconds the process's working set, then measuring the working set becomes a matter of checking which pages have their accessed bit set. The kernel periodically:

  • Reads each process's accessed bits.
  • Updates an estimate of each process's working-set size.
  • If the total exceeds the available frames, evicts entire processes.

Modern Linux uses a variant of this idea to control page reclaim. The kernel's reclaim pressure mechanism decides, based on measured fault rates and working set sizes, whether to reduce the memory footprint of a process or swap it entirely out.

The intuition to remember: virtual memory works because most programs only touch a small subset of their pages in any short window. When that subset gets too large relative to physical RAM, virtual memory stops being a benefit and becomes a liability.

7.10 · Touch Lab — Reading Linux Memory Statistics

Now let's look at how modern Linux exposes virtual memory to user space. The three tools we will use are free, vmstat, and /proc/meminfo. Together they give you a complete picture of physical memory, swap usage, page faults, and reclaim activity.

Step 1 — The free command

$ free -h
               total        used        free      shared  buff/cache   available
Mem:           7.7Gi       1.2Gi       5.6Gi        24Mi       1.1Gi       6.1Gi
Swap:          2.0Gi          0B       2.0Gi

Let me walk through each column:

  • total — total physical RAM.
  • used — memory currently in use by processes. Note: this does not include cache.
  • free — memory that is completely unused. On healthy Linux systems this is often small, because Linux aggressively uses spare memory for caching.
  • shared — memory used by tmpfs and shared memory segments.
  • buff/cache — page cache and buffer cache. This is the kernel's disk cache. It is reclaimable — the kernel can drop it at any time if a process needs the memory.
  • available — the number that actually matters. It is what free + reclaimable cache, so it tells you how much memory is realistically available to processes without triggering swap.
Common beginner mistake: looking at the "free" column and panicking because Linux seems to have no free memory. On a healthy Linux system, "free" is often near zero because the kernel uses all spare RAM for caching. The correct column to look at is available.

Step 2 — The vmstat command

$ vmstat 1 5

 0  0      0 57210  34216 1068416    0    0    32    18  421  712  3  1 96  0  0

 0  0      0 57180  34216 1068420    0    0     0     0  411  691  2  0 98  0  0

The most important columns for this week's material:

  • r — runnable processes (ready to run, waiting for CPU).
  • b — blocked processes, including those in uninterruptible sleep — usually waiting for I/O.
  • swpd — KB of swap currently used.
  • si — swap-in rate. Pages being brought back from swap. If this is nonzero, the system is under memory pressure.
  • so — swap-out rate. Pages being written to swap. Nonzero means real memory pressure.
  • bi — blocks in (read from disk).
  • bo — blocks out (written to disk).
  • cs — context switches per second.
  • us, sy, id, wa — the same CPU usage breakdown we saw in Week 5.
The diagnostic signal for memory pressure: nonzero si and so. If you see sustained swap-in and swap-out activity, the system is thrashing. If so is high and si is low, the workload is being paged out to swap and probably not coming back — a workload that no longer fits in RAM.

Step 3 — /proc/meminfo

For the full picture, look at /proc/meminfo. It has dozens of fields, but here are the most important ones: 

$ grep -E "MemTotal|MemFree|MemAvailable|Buffers|Cached|SwapTotal|SwapFree|Dirty|Writeback|Active|Inactive" /proc/meminfo
MemTotal:        8008064 kB
MemFree:         5834560 kB
MemAvailable:    6271520 kB
Buffers:          342160 kB
Cached:         10940540 kB
SwapTotal:       2097152 kB
SwapFree:        2097152 kB
Dirty:               468 kB
Writeback:             0 kB
Active:          1238472 kB
Inactive:        4501888 kB

A few fields worth understanding:

  • MemAvailable — the same as the "available" column in free -h.
  • Cached — the page cache. Free memory, as far as any user process is concerned.
  • Dirty — pages that have been modified in memory but not yet written back to disk. High values indicate the kernel is delaying write-back, or that the disk is slow.
  • Writeback — pages that are currently in the process of being written to disk. Sustained nonzero values suggest I/O pressure.
  • Active / Inactive — how the kernel classifies pages for its LRU-like reclaim.

Step 4 — Triggering memory pressure

The easiest way to see memory pressure in action is to consume memory deliberately. On a VM with little RAM, we can build a small memory hog. But careful: on a shared machine, this can cause actual problems. Safest is to do this in a script that allocates and immediately stops, or to use a mode that consumes memory but does not modify it: 

$ grep -E "MemAvailable|SwapFree" /proc/meminfo
MemAvailable:    6271520 kB
SwapFree:        2097152 kB

$ dd if=/dev/zero of=/dev/null bs=1M count=3000 &   # pure I/O, no memory
$ tail -f /dev/zero | head -c 100000000 > /dev/null &  # 100 MB of pipes

Or, more realistic — allocate memory in a controlled way with stress-ng if you have it installed: 

$ sudo apt install stress-ng
$ stress-ng --vm 1 --vm-bytes 2G --timeout 30s

# While that runs, in another terminal:
$ watch -n 1 'grep -E "MemAvailable|SwapFree|Dirty" /proc/meminfo'
$ vmstat 1

# Watch MemAvailable fall, SwapFree fall (if the workload exceeds RAM),
# and si/so climb in vmstat.

If the workload exceeds physical RAM, the kernel starts swapping. If swap is exhausted, the kernel's OOM (Out-of-Memory) killer steps in and terminates one of your processes. That last event usually appears in dmesg.

Never run this on a shared or production system. Memory pressure tests can push an entire machine into swapping and make it unresponsive for minutes. On a virtual machine that you own, it is safe. On a production server, it is a serious incident.

Step 5 — Cleanup and observation

$ sleep 30   # let the stress test finish
$ grep -E "MemAvailable|SwapFree" /proc/meminfo
MemAvailable:    6271520 kB
SwapFree:        2097152 kB

On a healthy system, after the pressure ends, memory availability returns to normal. If the system swapped pages out, they will be read back in as they are needed. Eventually, the system returns to its baseline.

What to look for next time you diagnose a slow Linux system: run free -h (is "available" low?), run vmstat 1 (are si/so nonzero?), and check /proc/meminfo for Dirty and Writeback. Those are the pure-memory signals. If they all look normal, the problem is elsewhere — CPU, I/O, or network.

7.11 · Touch Lab — Simulating Page Replacement

Reading about FIFO, LRU, and Optimal is one thing; watching them produce fault counts on the same reference string is another. In this lab we will build a small Python simulator and compare all three algorithms on the classic reference string from the textbook.

Step 1 — Create the script

$ nano pagerepl.py

Paste the following code:

#!/usr/bin/env python3
"""
Compare FIFO, LRU, and Optimal page-replacement algorithms
on the same reference string.
"""


def simulate_fifo(ref_string, frames):
    memory = []
    faults = 0
    trace = []

    for page in ref_string:
        if page not in memory:
            faults += 1
            if len(memory) < frames:
                memory.append(page)
            else:
                memory.pop(0)               # evict the oldest
                memory.append(page)
            trace.append((page, list(memory), "FAULT"))
        else:
            trace.append((page, list(memory), "hit"))
    return faults, trace


def simulate_lru(ref_string, frames):
    memory = []
    last_used = {}                          # page -> last access time
    faults = 0
    trace = []

    for t, page in enumerate(ref_string):
        if page not in memory:
            faults += 1
            if len(memory) < frames:
                memory.append(page)
            else:
                # evict the least recently used
                victim = min(memory, key=lambda p: last_used[p])
                memory.remove(victim)
                memory.append(page)
            trace.append((page, list(memory), "FAULT"))
        else:
            trace.append((page, list(memory), "hit"))
        last_used[page] = t
    return faults, trace


def simulate_optimal(ref_string, frames):
    memory = []
    faults = 0
    trace = []

    for i, page in enumerate(ref_string):
        if page not in memory:
            faults += 1
            if len(memory) < frames:
                memory.append(page)
            else:
                # evict the one used furthest in the future
                farthest = -1
                victim = None
                for m in memory:
                    # find next use of m after i
                    try:
                        next_use = ref_string.index(m, i + 1)
                    except ValueError:
                        next_use = float('inf')
                    if next_use > farthest:
                        farthest = next_use
                        victim = m
                memory.remove(victim)
                memory.append(page)
            trace.append((page, list(memory), "FAULT"))
        else:
            trace.append((page, list(memory), "hit"))
    return faults, trace


def print_trace(name, trace):
    print(f"\n{name} step-by-step:")
    print(f"{'Step':>4} {'Access':>6} {'Memory':>20} {'Result':>8}")
    for i, (page, mem, result) in enumerate(trace, 1):
        print(f"{i:>4} {page:>6} {str(mem):>20} {result:>8}")


def main():
    ref = [7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2, 1, 2, 0, 1, 7, 0, 1]
    frames = 3

    print(f"Reference string: {' '.join(map(str, ref))}")
    print(f"Physical frames : {frames}")

    fifo_faults, fifo_trace = simulate_fifo(ref, frames)
    lru_faults, lru_trace = simulate_lru(ref, frames)
    optimal_faults, opt_trace = simulate_optimal(ref, frames)

    print_trace("FIFO", fifo_trace)
    print_trace("LRU", lru_trace)
    print_trace("Optimal", opt_trace)

    print("\n" + "=" * 40)
    print("Summary — total page faults")
    print("=" * 40)
    print(f"FIFO     : {fifo_faults}")
    print(f"LRU      : {lru_faults}")
    print(f"Optimal  : {optimal_faults}")


if __name__ == "__main__":
    main()

Step 3 — Test Belady's anomaly

Now modify the script: change the reference string to 1 2 3 4 1 2 5 1 2 3 4 5, and run FIFO with three frames and then with four frames. 

# In the script, change ref_string:
ref = [1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5]
frames = 3   # first run

# Then change to:
frames = 4   # second run

With three frames, FIFO produces 9 faults. With four frames, it produces 10 faults. That is Belady's anomaly, reproduced in your own simulator — more physical memory producing more faults.

Run the same experiment with LRU. You will find LRU produces 10 faults with three frames and 8 with four — monotone improvement, as expected. LRU does not suffer from Belady's anomaly.

Why LRU is monotone and FIFO is not: LRU belongs to the class of stack algorithms. If you increase the number of frames, the set of pages in memory is always a superset of what it was before. FIFO does not have this property — adding a page to memory can change the order in a way that hurts.

What this exercise teaches: the difference between the theoretical optimum (Optimal) and the practically-implementable algorithms (LRU approximation, Clock). This gap between theory and practice is not just academic — it is where every real operating system's memory subsystem lives.

Week 7 Summary

  • Virtual memory gives every process a private, protected, and flexible address space by decoupling program addresses from physical addresses.
  • Contiguous allocation is simple but suffers from external fragmentation, and requires expensive compaction.
  • Segmentation divides the address space into logical regions, each with its own base and limit — allowing regions to grow independently.
  • Paging chops the address space into fixed-size pages and physical memory into frames. Any page fits any frame — external fragmentation is eliminated.
  • The page table stores the mapping from virtual pages to physical frames. Because of its size, real systems use multi-level paging — a tree of small tables that is only as dense as the address space actually used.
  • The TLB caches recent translations and turns almost all lookups into single-cycle operations. On context switches, the TLB is flushed or tagged with ASIDs.
  • Demand paging loads pages only when they are touched. A page fault brings a page in from disk — thousands of times slower than a RAM access.
  • Page replacement strategies: FIFO (simple but suffers Belady's anomaly), LRU (good but expensive to implement exactly), Optimal (used as a benchmark only), and Clock (approximates LRU with a single accessed bit).
  • Thrashing happens when processes do not have enough frames to hold their working set. The working-set model tells the kernel when to swap a process out entirely.
  • Tools: free -h, vmstat, and /proc/meminfo expose the kernel's memory state. Watch MemAvailable, swap-in (si), and swap-out (so) for signs of memory pressure.
