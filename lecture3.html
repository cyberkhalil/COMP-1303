3.1 · Process vs Thread

In Week 2 we saw that a process is an isolated execution environment: it has its own virtual address space, its own file descriptors, and the kernel protects it from every other process. That isolation is powerful — but it is also expensive when you actually need two pieces of code to cooperate. Creating a process is relatively slow, sharing data requires IPC, and switching between processes is costly.

A thread solves this. It is often called a lightweight process, and the name is very telling: a thread is a unit of execution that lives inside a process. Multiple threads can exist in the same process, sharing almost everything — except the things that must be private for each one.

One-line definition: a thread is the smallest unit of CPU execution that the kernel can schedule, and it always belongs to exactly one process.

What threads share, and what they own

This is the key mental model. When you create a thread, the kernel does not create a new address space, a new file descriptor table, or a new set of signals. It creates a new execution context inside the process that already exists.

 Shared between all threads  Private to each thread
Virtual address space — code, data, heap Program counter (PC)
Open file descriptors and sockets CPU registers (general-purpose, stack pointer, flags)
Current working directory Stack (local variables, return addresses)
Global and static variables Thread ID (TID), and pthread_t handle
Signal handlers, signal disposition Signal mask (which signals are blocked)
User and group identity (UID, GID) errno value and scheduling priority/affinity
The rule of thumb: if it makes sense for two running functions to share it, it is shared between threads. If it must be preserved separately for each running function, it is private.
A single-threaded process has one stack. A multi-threaded process shares code, data, and heap — but each thread has its own private stack.

What this means in practice

Because the code, data, and heap are shared, threads can exchange information with a simple variable assignment. That is the whole reason threads exist — they make communication both trivial and fast. But it is also the whole reason threads are dangerous: nothing prevents one thread from corrupting data that another thread is using. We will see exactly how in section 3.4.

Because each thread has its own stack and registers, the CPU can only run one thread of a given process at any given moment on a single core. To run multiple threads in parallel, you need multiple cores. Modern CPUs with 4, 8, or 16 cores are exactly why threads matter so much today.

3.2 · Thread Models

Where do threads live? Are they known to the kernel? Who decides which one runs? These questions lead to three classic threading models, each describing how user-level threads map to kernel-level threads.

Model Mapping Strengths Weaknesses / Examples
1:1 Each user thread is backed by exactly one kernel thread. True parallelism on multicore, and blocking calls block only one thread. Kernel resources per thread. Linux NPTL, Windows, macOS.
N:1 Many user threads are multiplexed on top of a single kernel thread. Very cheap to create and switch (no kernel involvement). No parallelism, one blocking call freezes all. Green threads, early Java.
M:N Many user threads mapped onto a smaller pool of kernel threads. Combines cheap user-level threads with multicore scaling. Complex to implement. Go goroutines, older Solaris, Erlang BEAM.
The three classic threading models. Linux uses the 1:1 model — every pthread is backed by a real kernel-scheduled task.

What Linux actually does

Linux uses the 1:1 model. This surprises many students because Linux threads feel cheap to create. The trick is that the Linux kernel does not distinguish between processes and threads at the lowest level — both are represented by the same data structure, called task_struct. The difference is what the clone() system call shares between the new task and its parent.

When you call fork(), the kernel clones with no sharing: new address space, new file descriptor table, new everything. When a thread library calls clone() with CLONE_VM, CLONE_FILES, and other flags, the new task shares the address space and file descriptors with its parent. That is what makes it a thread.

Why this matters: In Linux, a thread is literally a task that shares resources with another task via clone(). This design is elegant because it uses one uniform abstraction for both processes and threads, and it is why tools like ps -eLf show threads as lightweight processes with their own LWP (Light Weight Process) numbers.

3.3 · Benefits & Overheads

Threads are not a free lunch. They solve certain problems beautifully and create new problems of their own. Understanding both sides is the mark of a serious systems programmer.

Benefits

  • Responsiveness: a long computation in one thread does not freeze the entire application — the UI thread keeps updating.
  • Resource sharing: threads share memory by default, so no IPC ceremony is needed to pass data.
  • Economy: creating a thread is roughly 10–100× cheaper than creating a process. Context switching between threads is also cheaper — no address-space change, so the TLB is not flushed.
  • Scalability: on a multi-core CPU, threads run truly in parallel — this is what makes modern software fast on modern hardware.

Overheads & risks

  • Race conditions: if two threads access shared data without synchronization, results are unpredictable.
  • Deadlocks: two threads, each holding a lock the other wants, will wait forever.
  • Debugging complexity: bugs may appear only on one machine, one core count, or one timing. Non-deterministic bugs are the worst kind.
  • Loss of isolation: one thread calling exit() or crashing with SIGSEGV kills the entire process — and all its siblings.
Design principle: prefer processes for isolation and robustness, and threads for performance and shared-state concurrency. Modern designs often combine both — for instance, Chrome uses one process per tab (isolation), and each process uses multiple threads for rendering and I/O (performance).

Cost comparison (rough order of magnitude)

Operation Approximate cost Notes
Create a process (fork) ~10,000–100,000 ns Depends heavily on memory size (COW helps a lot)
Create a thread (pthread_create) ~1,000–10,000 ns Kernel allocates stack, task_struct, and TID
Context switch between processes ~1,000–10,000 ns Includes TLB flush and memory-map switch
Context switch between threads (same process) ~500–2,000 ns No TLB flush — same address space
Send a message over a pipe ~1,000 ns + data copy Involves two syscalls (write + read)
Write to a shared variable ~1 ns Direct memory access — no kernel involvement

The last three rows are why threads are so attractive: a shared variable write is a thousand times faster than sending a message through a pipe. When you need high-performance communication between concurrent computations, threads are the natural choice — as long as you use them safely.

3.4 · Race Conditions — A First Look

Every benefit of threads comes with a matching risk. The most fundamental of those risks is the race condition: a situation where the correctness of a program depends on the timing of thread execution.

The classic example: two threads incrementing a counter

Imagine two threads each increment a shared counter 100,000 times. In code, that looks like this: 

static volatile int counter = 0;

void *worker(void *arg) {
    for (int i = 0; i < 100000; i++) {
        counter++;   /* looks atomic — is it? */
    }
    return NULL;
}

You would expect the answer to be 200,000. But when you actually run it, you often get something smaller — maybe 187,431, maybe 164,929, maybe a different number every time. The result is non-deterministic.

Why? The counter++ instruction is not atomic

At the assembly level, counter++ is three separate machine instructions:

  1. Load the current value of counter from memory into a register.
  2. Increment the value in the register.
  3. Store the register's value back to memory.

If two threads interleave these three steps without coordination, data can be lost:

Two threads load 0 into their private registers. Each increments its own register to 1. Each stores back 1. The counter was incremented twice but ends up at 1 — one increment was lost.

This is called the lost update problem. It is the simplest possible race condition, and it underlies a huge class of real-world bugs.

The lesson: counter++ looks innocent but is not atomic. Many operations that look atomic at the source level — like x = x + 1 or if (ptr != NULL) free(ptr); — involve a load, a modify, and a store. Without synchronization, any of them can lose data.

Critical sections and mutual exclusion

The piece of code that accesses shared data — the counter++ above — is called a critical section. The rule that only one thread may be inside the critical section at a time is called mutual exclusion. The mechanism that enforces it is a lock or mutex.

We will study locks, mutexes, semaphores, and condition variables in detail in Week 4. For now, I want you to internalize the concept — this will be one of the most important mental models of the entire course.

Preview of Week 4: the fix for the counter problem is to wrap the increment inside a lock. But if you use the wrong lock, forget to release it, or take two locks in the wrong order, you get either a partial fix or a deadlock. That is the entire subject of next week.

3.5 · The POSIX Threads (pthread) API

On Linux and other Unix-like systems, threads are exposed through the standard POSIX API — pthreads. It is part of the C library and is what nearly all Linux multi-threaded software is built on. Let's look at the core functions you will use.

pthread_create — create a new thread

#include <pthread.h>

int pthread_create(
    pthread_t *thread,             /* OUT: handle to the new thread */
    const pthread_attr_t *attr,    /* attributes — pass NULL for defaults */
    void *(*start_routine)(void *),/* the function to run in the thread */
    void *arg                      /* argument passed to start_routine */
);

The new thread runs start_routine(arg) in parallel with the calling thread. It returns 0 on success, or a non-zero error code on failure (unlike most syscalls, pthread_* functions return the error code directly instead of setting errno).

pthread_join — wait for a thread to finish

int pthread_join(pthread_t thread, void **retval);

Blocks the calling thread until the given thread terminates, then reaps its resources — just like wait() does for processes. The exit value of the thread (whatever it returned from start_routine) is stored in *retval if not NULL.

You must join or detach every thread. If a thread terminates and is never joined nor detached, its resources are not freed — this is the thread equivalent of a zombie process. You can also call pthread_detach(thread) to specify that the thread's resources should be freed automatically on exit.

Other essential functions

pthread_t pthread_self(void);
/* Returns the handle of the calling thread */

int pthread_exit(void *retval);
/* Terminates the calling thread, not the whole process */

int pthread_detach(pthread_t thread);
/* Mark a thread as detached — its resources are auto-freed on exit */

pthread_t pthread_equal(pthread_t t1, pthread_t t2);
/* Compare two thread handles for equality */

Compiling with pthreads

When you compile a program that uses pthreads, you must tell the linker to include the pthread library: 

$ gcc -Wall -pthread -o myprog myprog.c

The -pthread flag does two things: it defines _REENTRANT (which makes certain library functions thread-safe) and it links against libpthread. If you forget this flag, your program may compile but fail at runtime with strange errors.

3.6 · Touch Lab — Your First pthread Program

Let's write, compile, and run a real multi-threaded program. We will create four threads, and each will print its own thread ID and the ID of the process.

Step 1 — Create the source file

$ nano threads.c

Paste the following code:

#include <stdio.h>
#include <pthread.h>
#include <unistd.h>
#include <sys/types.h>

/* Each thread runs this function */
void *worker(void *arg) {
    long tid = (long)arg;

    /* getpid() returns the same PID for all threads */
    /* pthread_self() returns a different value for each */
    printf("Thread %ld: PID = %d, TID = %lu\n",
           tid, getpid(), (unsigned long)pthread_self());

    return NULL;
}

int main(void) {
    pthread_t threads[4];

    printf("Main thread: PID = %d, TID = %lu\n",
           getpid(), (unsigned long)pthread_self());

    for (long i = 0; i < 4; i++) {
        if (pthread_create(&threads[i], NULL, worker, (void *)i) != 0) {
            perror("pthread_create");
            return 1;
        }
    }

    for (int i = 0; i < 4; i++) {
        pthread_join(threads[i], NULL);
    }

    printf("All threads finished. Main exits.\n");
    return 0;
}

Step 2 — Compile (note the -pthread flag)

$ gcc -Wall -pthread -o threads threads.c

Step 3 — Run it

$ ./threads
Main thread: PID = 5120, TID = 140234567890176
Thread 0: PID = 5120, TID = 140234559497984
Thread 1: PID = 5120, TID = 140234551105280
Thread 2: PID = 5120, TID = 140234542712576
Thread 3: PID = 5120, TID = 140234534319872
All threads finished. Main exits.

Look carefully at the output. All five "threads" — main plus the four workers — have the same PID. That confirms they all live inside a single process. But every one of them has a different TID. That is the fundamental difference between a process and a thread made visible.

Note on TID size: on 64-bit Linux, pthread_t is typically an unsigned long — a large number in the range 140,000,000,000,000 and up. This is because glibc often uses the thread's stack address as its handle. Casting to unsigned long and printing with %lu is portable enough for our purposes.

Experiment: run it several times

Notice that the output order of the four "Thread N:" lines is not deterministic. Sometimes thread 2 runs before thread 0. Sometimes they are all printed at the same instant by different cores. On a multi-core machine, real threads really do run simultaneously — and the exact order is up to the scheduler.

Try this: run ./threads | sort five times. The sorted output is stable because the numbers are the same, but the unsorted output varies each run. This is the essence of concurrent execution.

3.7 · Touch Lab — Observing Threads from the Outside

In the previous lab, the program told us about its own threads. Now let's observe them from the outside, the way a system administrator would — using ps and the /proc file system.

Modify the program to run longer

To actually observe the threads while they are running, let's make them sleep for a few seconds. Open threads.c and add a sleep(30) at the end of the worker function: 

void *worker(void *arg) {
    long tid = (long)arg;
    printf("Thread %ld: PID = %d, TID = %lu\n",
           tid, getpid(), (unsigned long)pthread_self());
    sleep(30);   /* keep the thread alive for observation */
    return NULL;
}

Recompile and run it in the foreground:

$ gcc -Wall -pthread -o threads threads.c
$ ./threads &
[1] 5200

Using ps -eLf to see threads as light-weight processes

$ ps -eLf | head -1
UID   PID  PPID   LWP  C NLWP STIME TTY   TIME CMD

$ ps -L -p 5200
UID   PID  PPID   LWP  C NLWP STIME TTY   TIME CMD
student 5200  5120  5200  0    5 14:22 pts/0 0:00 ./threads
student 5200  5120  5201  0    5 14:22 pts/0 0:00 ./threads
student 5200  5120  5202  0    5 14:22 pts/0 0:00 ./threads
student 5200  5120  5203  0    5 14:22 pts/0 0:00 ./threads
student 5200  5120  5204  0    5 14:22 pts/0 0:00 ./threads

Let me point out the important columns:

  • PID — the process ID. All five lines share the same PID, confirming they belong to one process.
  • LWP — Light Weight Process ID. This is essentially the thread ID as seen by the kernel. Notice it is different for each line.
  • NLWP — Number of Light Weight Processes. This is the thread count — 5 in our case (four workers plus the main thread).
  • CMD — the command line, the same for all threads of the process.
Remember: in Linux, "LWP" and "TID" are essentially the same concept. The kernel calls them tasks; user space calls them threads. Same thing, different vocabulary.

Exploring /proc/<pid>/task

The kernel exposes every thread of a process as a subdirectory inside /proc/<pid>/task/. Let's look: 

$ ls /proc/5200/task
5200  5201  5202  5203  5204

$ ls /proc/5200/task/5201
attr        comm       fd          mem         ns          sched
auxv        cgroup     fdinfo      mountinfo   numa_maps   schedstat
...
stat        status     syscall     wchan

Each directory is a full window into that thread's state — its own scheduler statistics, its own CPU affinity, its own system call activity. Let's look at the status of one thread: 

$ cat /proc/5200/task/5201/status
Name:   threads
State:  S (sleeping)
Tgid:   5200
Pid:    5201
PPid:   5120
...
Threads:        5

A few fields deserve attention:

  • Tgid — Thread Group ID. This is the PID of the process that owns all these threads. Every thread in the same process shares the same Tgid.
  • Pid — the individual thread's ID (the same number you saw in the LWP column).
  • Threads — the current number of threads in this process.

Investigate the stacks

Each thread has its own stack. You can see this by examining the memory maps of individual threads — they differ only in the stack region: 

$ cat /proc/5200/task/5201/maps | tail -5
...
7f8a2c1f2000-7f8a2c1f3000 ---p 00000000 00:00 0
7f8a2c9f3000-7f8a2d1f2000 rw-p 00000000 00:00 0
7f8a2d1f2000-7f8a2d1f3000 ---p 00000000 00:00 0
7f8a2d9f3000-7f8a2e1f2000 rw-p 00000000 00:00 0

Those large rw-p regions near the high end of the address space are the thread stacks. Each thread gets its own 8 MB stack by default — that is one of the reasons threads are a bit heavier than they look at first glance.

Clean up

$ kill 5200
[1]+  Terminated              ./threads

Notice that killing the process terminates all its threads. There is no way to kill just one thread from the outside — threads have no external identity separate from the process in the shell.

An important consequence: killing a process also kills all its threads, cleanly or not. If one thread in a multi-threaded program crashes with SIGSEGV, the entire process dies — and every other thread with it. This is why isolation between threads is so much weaker than isolation between processes.

Week 3 Summary

  • Thread: a unit of CPU execution inside a process. Shares code, data, heap, file descriptors. Has its own registers, stack, and TID.
  • Thread models: 1:1 (Linux, Windows — true parallelism), N:1 (green threads — cheapest, no parallelism), M:N (Go, Erlang — best of both, complex).
  • Why threads: responsiveness, resource sharing, cheaper creation and context switching than processes, and real parallelism on multi-core CPUs.
  • Overheads: race conditions, deadlocks, loss of isolation, hard-to-debug non-deterministic behavior.
  • Race condition: a bug that appears when two threads access shared data without coordination — the counter++ example is its simplest form.
  • pthreads API: pthread_create, pthread_join, pthread_exit, compiled with -pthread.
  • Linux view: threads are LWPs — lightweight processes — visible in ps -eLf and /proc/<pid>/task/.
