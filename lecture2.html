2.1 · What is a Process?

In Week 1 we learned that an operating system manages resources and abstracts hardware. Nowhere is this more obvious than in the concept of a process — which is, put simply, a program in execution.

When you compile a C file, you get an executable file sitting on disk. That's just bytes — no execution, no CPU activity, nothing happening. When you run it, the OS loads it into memory, gives it a CPU context, and lets it execute. That running instance is a process. If you run the same executable twice, you get two independent processes.

Program vs Process: A program is a passive entity — a file on disk. A process is an active entity — a program in memory with a program counter, registers, stack, and a set of allocated resources.

What lives inside a process

Every process has its own virtual address space, which is typically divided into four regions:

Code (Text) Segment

The compiled machine instructions of the program. Usually read-only, and often shared between processes that run the same binary (for instance, five instances of bash can share the same code pages).

Data Segment

Contains global and static variables. This region is writable and grows in a fixed direction.

Heap

Dynamically allocated memory — what you get from malloc() in C, or from new in higher-level languages. The heap grows upward (usually towards higher addresses).

Stack

Function call frames: local variables, parameters, return addresses. The stack grows downward (towards lower addresses) in most architectures.

Typical layout of a process's virtual address space — from top (high addresses: stack) to bottom (low addresses: code).

Why do processes matter?

Processes are the OS's fundamental unit of isolation and protection. Two processes cannot accidentally read or write each other's memory — the virtual memory subsystem enforces this boundary in hardware via the MMU (Memory Management Unit). If process A tries to write to process B's address space, the CPU raises a page fault and the kernel terminates A. This is why one buggy program does not destroy your entire system.

2.2 · Process States and the PCB

At any given moment, a process is in one of a small number of states. The exact labels vary slightly between textbooks, but the classic five-state model used by Silberschatz is the most widely adopted:

The five-state process model: New → Ready → Running → Waiting → Terminated, with transitions driven by the kernel and by I/O events.

The five states, defined

State Meaning
New The process is being created. The OS is allocating resources (address space, PCB), but the process is not yet ready to run.
Ready The process has everything it needs to run and is waiting in the ready queue for the CPU scheduler to pick it.
Running The process is currently executing on the CPU. On a single-core system, only one process is running at any instant.
Waiting The process is blocked, waiting for an event (I/O completion, a signal, a child process). Even if the CPU were free, this process could not run.
Terminated The process has finished execution. It is now ready to be reaped by its parent.

The Process Control Block (PCB)

How does the kernel keep track of all this? Every process has a data structure called the Process Control Block (PCB) — called task_struct in Linux. The PCB is the kernel's "identity card" for a process and contains everything the OS needs to manage it:

  • Process ID (PID): A unique integer identifying the process.
  • Parent PID (PPID): Identifies the parent process that created this one.
  • Process state: One of New, Ready, Running, Waiting, or Terminated.
  • Program Counter (PC): The address of the next instruction to execute.
  • CPU registers: The full register set — needed to restore the process later.
  • Memory management information: Pointers to page tables, base and limit registers, memory maps.
  • I/O status: Open file descriptors, pending I/O requests, devices in use.
  • Accounting information: CPU time consumed, wall-clock time, priority, scheduling parameters.
Simply put: if the OS ever needs to pause a process and come back to it later, the PCB contains everything required to resume that process as if it had never been interrupted.

2.3 · Context Switching

Modern computers look like they run many programs simultaneously, but on a single CPU core, only one instruction stream executes at any given nanosecond. What actually happens is that the CPU rapidly switches between processes: this is context switching.

A context switch is the act of saving the state of the currently running process and loading the state of the next one. The kernel must:

  1. Save the CPU registers of the running process into its PCB.
  2. Update the process's state (from Running to Ready or Waiting).
  3. Select the next process to run (using the scheduler).
  4. Load the saved CPU registers of the next process from its PCB.
  5. Switch the memory map — update the MMU to point to the next process's page tables.
  6. Resume execution of the next process.
Context switches are not free. A typical context switch on Linux takes on the order of 1–10 microseconds — mostly because of the memory-map switch, which invalidates the TLB (a cache that maps virtual to physical addresses). If a system switches too frequently, the overhead dominates and performance collapses. This is called context-switch thrashing.

Context switch vs mode switch

A subtle but important distinction: entering the kernel via a system call is not the same as a context switch. When a process makes a syscall, the CPU switches from user mode to kernel mode, but the process remains the same — same PID, same address space. No context switch occurs.

A context switch happens only when the kernel decides to run a different process. Syscalls cause context switches only if they block (e.g., read on a slow disk) or if the scheduler decides it's time to preempt.

2.4 · fork(), exec(), and wait()

On Unix-like systems, all process creation flows through a single syscall: fork(). Other operations are built on top of it. Let's look at the key ones.

fork() — the only way to create a process

fork() creates a copy of the calling process. The kernel duplicates the entire address space, creates a new PCB, and returns twice: once in the parent, once in the child.

In the parent, fork() returns the PID of the newly created child process. In the child, it returns 0. This is how each side knows which one it is. 

#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

int main(void) {
    pid_t pid = fork();

    if (pid < 0) {
        perror("fork failed");
        return 1;
    } else if (pid == 0) {
        printf("Child process:  PID = %d, PPID = %d\n", getpid(), getppid());
    } else {
        printf("Parent process: PID = %d, child PID = %d\n", getpid(), pid);
    }
    return 0;
}
Modern optimization: A full memory copy on fork() would be very expensive. Linux uses copy-on-write (COW): the child shares the parent's pages until one of them writes to a page. Only then is that page physically copied. This makes fork() fast and memory-cheap when the child immediately calls exec.

exec family — replacing the current program

exec() replaces the calling process's code, data, heap, and stack with a new program. It does not create a new process — it becomes a different program, same PID. There is no "return" from a successful exec.

The name execve() refers to the underlying syscall; execl, execv, execvp, etc., are C library wrappers that differ in how arguments are passed.

wait() and waitpid() — waiting for children

A parent process typically wants to know when its child has finished. wait() blocks until any child terminates; waitpid() waits for a specific child.

When a child terminates, the kernel does not immediately free its PCB — because the parent needs to be able to read the exit status. In this intermediate state, the child is called a zombie. Once the parent calls wait(), the kernel reaps the zombie and frees the resources.

The zombie problem: If a parent terminates without reaping its children, they get re-parented to init (PID 1), which reaps them automatically. But if a parent is alive and never calls wait(), zombies accumulate and can exhaust the process table. This is why wait() is not optional in well-behaved code.

The classic Unix pattern: fork + exec

When you type ls into a bash shell, the shell does not execute ls in itself. Instead, it:

  1. Forks a child process.
  2. The child calls execvp("ls", args) — replacing itself with ls.
  3. The parent (the shell) waits for the child to finish using waitpid().
  4. Once the child finishes, control returns to the shell, which prints the next prompt.

Every command you have ever run in a Linux shell went through this pattern. Understanding it is a major milestone in learning systems programming.

The classic Unix pattern: parent forks a child, child calls exec to become a new program, parent waits for the child to finish.

2.5 · Inter-Process Communication (IPC) Basics

Processes are isolated from each other by design — that is how the OS keeps them from corrupting one another. But they still need to communicate. The OS provides several mechanisms, each with its own trade-offs.

Mechanism How it works Strengths & weaknesses
Pipes Unidirectional byte stream between two related processes (usually parent → child). Very simple, tiny buffer. Unidirectional only; requires shared ancestry.
Named pipes (FIFOs) Same as pipes, but accessible via the file system — any two processes can use them. More flexible than anonymous pipes. Still unidirectional.
Shared memory Both processes map the same physical memory pages into their address space. Fastest method — no kernel involvement after setup. But synchronization is the programmer's responsibility.
Message queues Kernel-managed queues; processes send and receive structured messages. Cleaner semantics than pipes. Slower than shared memory.
Sockets Endpoint-based communication — works for both local and network connections. Most general and portable. More overhead for local communication.
Signals Asynchronous notifications — a process is interrupted to handle a signal. Very lightweight, but carries little data. Ideal for events like Ctrl+C (SIGINT).
Rule of thumb: for two related processes that just need to pass bytes — pipes. For high throughput and short messages — shared memory. For cross-machine communication — sockets. For events — signals.

2.6 · Touch Lab — fork() and Process Trees

Let's write, compile, and run our first real systems program. The goal is to see in practice what the theory has been describing.

Step 1 — Create the source file

$ nano forktree.c

Paste the following code:

#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();

    if (pid < 0) {
        perror("fork");
        return 1;
    } else if (pid == 0) {
        /* Child */
        printf("[CHILD ]  PID = %d, my parent PPID = %d\n", getpid(), getppid());
    } else {
        /* Parent */
        printf("[PARENT]  PID = %d, I just created child %d\n", getpid(), pid);
        wait(NULL);
        printf("[PARENT]  child %d has just terminated\n", pid);
    }
    return 0;
}

Step 2 — Compile

$ gcc -Wall -o forktree forktree.c
$ ls -l forktree
-rwxr-xr-x 1 student student 16512 ... forktree

Step 3 — Run it

$ ./forktree
[PARENT]  PID = 4711, I just created child 4712
[CHILD ]  PID = 4712, my parent PPID = 4711
[PARENT]  child 4712 has just terminated

Note that the order of the first two lines is not deterministic — the scheduler decides who runs first after the fork. Try running the program several times to see for yourself.

Step 4 — Observe the process tree

In another terminal, run this while the first program is running (to slow down the child, you can modify the code to sleep for a few seconds): 

$ pstree -p <your_user>
bash(4500)─┬─forktree(4711)───forktree(4712)
            └─pstree(4720)

You should see the parent process and the child fork, both with distinct PIDs, and the parent-child relationship preserved.

Step 5 — Inspect /proc

While the child is still alive, you can inspect its live kernel-facing state: 

$ cat /proc/4712/status
Name:	forktree
State:	S (sleeping)
Pid:	4712
PPid:	4711
Uid:	1000	1000	1000	1000
VmSize:	   2580 kB
...

$ ls -l /proc/4712/fd
total 0
lrwx------ 1 student student 64 ... 0 -> /dev/pts/0
lrwx------ 1 student student 64 ... 1 -> /dev/pts/0
lrwx------ 1 student student 64 ... 2 -> /dev/pts/0

The /proc/<pid> directory is a virtual file system exposed by the kernel. Every file inside it is generated on the fly and reflects the current state of the process — its memory maps, open file descriptors, CPU affinity, scheduling policy, and much more.

Fun fact: /proc is not a real file system — nothing is stored on disk. It is a window into the kernel's in-memory data structures. Every read from a file in /proc is really a function call inside the kernel.

2.7 · Touch Lab — Monitoring Processes with ps and top

In the previous lab, we looked at processes from inside our own program. Now let's look at them from the "outside" — using the tools every Linux administrator uses daily.

ps — take a snapshot of running processes

ps shows a picture of the current process table. The bare command shows only the processes attached to your terminal. To see everything, use flags. 

$ ps                              # your shell session only
$ ps aux                           # all processes, BSD-style
$ ps -ef                           # all processes, UNIX-style
$ ps -eo pid,ppid,stat,cmd         # custom columns

Common columns in ps aux output:

  • USER — who owns the process.
  • PID — the process ID.
  • %CPU — CPU usage since the process started.
  • %MEM — resident memory usage as a percentage.
  • STAT — process state code (R = running, S = sleeping, D = uninterruptible sleep, Z = zombie, T = stopped).
  • TIME — total CPU time consumed.
  • COMMAND — the command line that started the process.

top — a live view of the system

top is like ps but refreshes every few seconds and sorts by CPU usage. It also shows system-wide metrics like load average and memory usage at the top. For a more modern and colorful version, install htop: 

$ sudo apt install htop
$ htop

Background jobs, fg, and bg

Your shell can manage multiple processes through job control. Display the current jobs, background a running one, or bring it back to the foreground with these commands: 

$ sleep 300 &         # start sleep in the background
[1] 4810
$ jobs                # list jobs of the current shell
[1]+ Running    sleep 300 &

$ sleep 500           # now press Ctrl+Z to suspend it
^Z
[2]+ Stopped    sleep 500

$ bg %2               # resume job 2 in the background
$ fg %1               # bring job 1 to the foreground
$ kill 4810           # send SIGTERM to a process by PID
Signals matter: kill does not mean "destroy" — it means "send a signal." The default signal is SIGTERM (15), which politely asks the process to terminate. SIGKILL (9) is uncatchable and forces immediate termination — use it only as a last resort, since the process gets no chance to clean up.

Practice exercise

  1. Open a terminal and run sleep 1000 & three times.
  2. Run jobs and note the job numbers.
  3. Run ps -eo pid,ppid,stat,cmd | grep sleep and identify all three sleeps.
  4. Use fg %1 to bring the first one back, then Ctrl+C to kill it.
  5. Use kill to terminate the two remaining background jobs.

When you can do this without hesitation, you have mastered the basic vocabulary of Linux process control — and you will use it every single day for the rest of this course.

Week 2 Summary

  • Process: an active program in memory, with its own address space and PCB.
  • Process states: New, Ready, Running, Waiting, Terminated — with transitions driven by syscalls, I/O events, and the scheduler.
  • PCB: the kernel's per-process record containing PID, PPID, registers, memory maps, open files, and scheduling information.
  • Context switch: saving and restoring a process's full state. Expensive because of the memory-map switch and TLB invalidation.
  • fork / exec / wait: the classic Unix trio for creating, replacing, and reaping processes.
  • IPC: pipes, FIFOs, shared memory, message queues, sockets, and signals — each serving different needs.
  • Tools: ps, top, htop, jobs, kill, and /proc/<pid> put process management into your hands.
