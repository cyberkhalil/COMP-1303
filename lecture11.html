11.1 · Why DNS Matters

Last week we configured a DHCP server that delivers IP addresses, gateway, and DNS servers to clients. Now we are going to build the DNS server itself — the service those addresses point to. This is one of the most important pieces of infrastructure on any network, and for many engineers it is also the most mystifying.

Think about what happens when you type github.com into a browser. You have typed a name, not a number. But the network underneath speaks in IP addresses. Somewhere between your keyboard and the GitHub server, that name has to be translated into an address. That translation is DNS — the Domain Name System.

One-sentence definition: DNS is a globally distributed, hierarchical database that maps human-readable names to IP addresses — and a lot more besides. It is, quite literally, the phone book of the internet.

Why not just use IP addresses everywhere?

Because names are infinitely more stable, memorable, and manageable than numbers.

  • Names are stable. GitHub's servers may change their IPs whenever they want — they have moved to different cloud providers, added anycast, and re-architected their infrastructure. But github.com has always pointed to the right place.
  • Names are memorable. You remember google.com. You do not remember whatever the current IP is.
  • Names are flexible. A single name can point to multiple IPs for load balancing, to a canonical name that redirects, or to mail servers, and so on.
  • Names are hierarchical. The DNS namespace is a tree, which means it can be delegated — this is what makes the internet scale.

The problem DNS solves at scale

There are roughly 350 million registered domain names as of today, and that number keeps growing. There is no central server that knows all of them. No single machine could store it, answer the query volume (over a trillion per day), or be close enough to everyone on Earth to answer quickly.

DNS solves this with three ideas, and every part of this week's lecture builds on them:

Idea What it means
Hierarchy The namespace is a tree. Each level only needs to know about the level below it. Root servers delegate .com to TLD servers, which delegate github.com to GitHub's authoritative servers, and so on.
Distribution Each piece of the tree is served by many independent servers, spread across the world. There is no single point of failure.
Caching Every answer comes with a lifetime. Resolvers near you cache the answers, so the next million queries for the same name never leave your ISP.
The result: name resolution that is fast (typically tens of milliseconds for a cached answer), resilient (many servers, many paths), and global (works the same on every continent).

What DNS carries besides IP addresses

DNS is often called "the phone book" but that undersells it. A modern DNS zone can store dozens of different kinds of records:

  • IPv4 and IPv6 addresses for hosts (A and AAAA records).
  • Aliases and canonical names (CNAME records).
  • Mail routing information (MX records).
  • Zone delegation (NS records).
  • Service discovery (SRV records).
  • Anti-spam policy (TXT/SPF/DKIM/DMARC).
  • Reverse lookups from IP back to hostname (PTR records).
  • Free-form text for any purpose you can think of (TXT records).

In this week's labs, we will set up a BIND9 server that handles A, AAAA, CNAME, MX, NS, SOA, and PTR records — which covers the vast majority of what you will ever touch as a practical administrator.

11.2 · The DNS Hierarchy

The DNS namespace is an inverted tree. The root is a dot — literally . — and everything below it is a series of labels separated by dots, read from right to left.

In the name www.example.com., the trailing dot is the root, com is the top-level domain, example is the second-level domain, and www is the host name. When you type a name without a trailing dot, your resolver appends a default search suffix or the root, depending on configuration.

DNS names are read right to left. The root delegates to top-level domains, each TLD delegates to registered domains, and each domain delegates to whatever subdomains it wants to create.

The three tiers

Tier What it does Examples
Root servers Know where the TLD servers are. There are 13 logical roots, each served by hundreds of physical machines globally via anycast. They do not know about individual domains — only about .com, .org, .ps, and the ~1500 other TLDs. a.root-servers.net through m.root-servers.net
TLD servers Know which DNS servers are authoritative for each domain under them. For example, the .com servers know who handles github.com and google.com. These are run by the registry, e.g. Verisign runs .com, the .ps registry runs .ps.
Authoritative servers Hold the actual records for a zone. When someone asks "what is the IP of www.example.com?", the authoritative server gives the true answer. These are run by the domain owner — you, if you own a domain. In our lab, our own BIND9 server.

Delegation — the secret of scale

The crucial design principle is delegation. The root servers do not know how to reach www.example.com. They only know who runs .com. The .com servers do not know how to reach www.example.com either — they only know who runs example.com. And the example.com servers know everything about their own zone.

This is what makes the whole system work. Each level does not need to know about everything below it — only about the next level down. If example.com adds a new subdomain, the .com servers do not even notice. If a domain owner runs their own DNS servers on the other side of the world, the registry does not care — it only stores the pointer.

Delegation is captured in the NS records. An NS record says "for this zone, ask that nameserver". At the top of every zone, you will find NS records that delegate sub-zones to their own servers. This is also how you take a subdomain like dev.example.com and hand it to a completely separate team or server.

11.3 · Resolution — Recursive & Iterative

Now that we know the structure of the hierarchy, let's walk through what actually happens when you type www.example.com into a browser. There are two actors involved — a recursive resolver and one or more authoritative servers — and two different kinds of queries flow between them.

The two kinds of queries

Recursive query

"Give me the final answer — or tell me it does not exist." The client trusts the resolver to do all the work, including following delegations across the internet. This is what your laptop sends to your ISP's resolver.

Iterative query

"Give me the best answer you have — even if it is only a referral." The resolver uses this when talking to root and TLD servers, which do not do full resolution for anyone. They return pointers to whoever knows more.

referral, not an answer. Only the last hop gives the authoritative answer. Total time for a cold lookup: 50–200 ms · For a cached answer: under 1 ms.
The client sends one recursive query. The resolver, behind the scenes, sends several iterative queries — each one to a server closer to the answer.

The full sequence, step by step

  1. The browser needs to reach www.example.com. It asks the local stub resolver — usually via systemd-resolved or the C library's gethostbyname() — for the address.
  2. The stub resolver is not authoritative for anything, so it forwards a recursive query to a configured resolver — say, 1.1.1.1 (Cloudflare) or 8.8.8.8 (Google), or your ISP's resolver.
  3. The recursive resolver does not have the answer cached. It begins an iterative hunt:
    • It asks a root server: "who handles com?" The root returns a referral — the list of .com TLD nameservers.
    • It asks one of the .com TLD servers: "who handles example.com?" The TLD returns a referral — the NS records for the zone.
    • It asks one of the authoritative servers for example.com: "what is the address of www.example.com?" The authoritative server returns the A record — the actual IPv4 address.
  4. The resolver caches the answer, respecting its TTL, then returns it to the stub resolver, which returns it to the browser.
  5. The browser opens a TCP connection to the address and fetches the page.
Why this scales: the root servers are asked billions of times per day, but the answers never change and come with long TTLs. Every resolver in the world caches them. What the root servers actually answer is a tiny, static dataset — the TLD referral list. This is why 13 root clusters can keep the entire internet running.

11.4 · Resource Record Types

A DNS zone is a text file made of resource records — RRs for short. Each record has the same logical structure — name, type, class, TTL, and data — but the meaning of the data depends on the type.

The generic record format

name    [TTL]   [class]   type   data

; Example — all on one logical line
www.example.com.   3600   IN   A   203.0.113.42
^name              ^TTL   ^class ^type ^data

The class field is almost always IN — for "Internet" — and is nearly always omitted in modern zone files because it is implied. The TTL, if omitted, inherits from the previous record or from the SOA's default.

The record types you must know

Type Purpose Example
SOA Start of Authority. Every zone has exactly one. Holds the primary nameserver, the administrative email (with . instead of @), and various timing parameters. example.com. IN SOA ns1.example.com. admin.example.com. ( 2024010101 3600 1800 604800 86400 )
NS Nameserver. Declares which servers are authoritative for this zone. Zone files have one NS record per authoritative server. example.com. IN NS ns1.example.com.
A Address. Maps a name to an IPv4 address. www IN A 203.0.113.42
AAAA IPv6 address ("quad-A"). Maps a name to an IPv6 address. www IN AAAA 2001:db8::42
CNAME Canonical Name. An alias — this name is really that other name. Cannot coexist with other record types for the same name. web IN CNAME www
MX Mail Exchanger. Where to deliver email for this domain. Has a priority number; lower number = higher priority. example.com. IN MX 10 mail1.example.com.
PTR Pointer. Used in reverse zones: maps an IP address back to a name. 42 IN PTR www.example.com.
TXT Text. Free-form strings. Used for SPF, DKIM, DMARC, and site-verification challenges. example.com. IN TXT "v=spf1 -all"
SRV Service. Points to a host and port for a specific service, with priority and weight. _sip._udp IN SRV 10 5 5060 sipserver.example.com.
AAAA alias note Remember: you cannot have a CNAME and any other record with the same name. If you need both address records and mail records on the same name, use A/AAAA, not CNAME. —

CNAME — the alias with a rule

CNAMEs are the most misused record type in DNS. Let me explain the rule carefully because it will cause you trouble in the lab if you violate it.

A CNAME says: "this name is an alias for another name — go look up that other name and use the result". It is a complete redirection. This is why a CNAME cannot coexist with any other record for the same owner name, and it cannot exist at the apex of a zone (where the SOA and NS records already live).

The CNAME trap: you cannot have example.com. IN CNAME foo.example.com. at the apex of a zone, because the apex already has an SOA record and NS records. And you cannot have www IN CNAME target and www IN A 203.0.113.42 — the two conflict. If BIND rejects your zone file with "CNAME and other data at the same name", this is why.

SOA — the zone's identity card

Every zone begins with an SOA record. It defines the zone's identity and operating parameters. Let me walk through the fields: 

@   IN  SOA ns1.example.com. admin.example.com. (
        2024111501   ; Serial    — increment on every change
        3600         ; Refresh   — how often secondaries check for updates
        1800         ; Retry     — how long to wait after a failed check
        604800       ; Expire    — how long secondaries may serve without contact
        86400        ; Minimum   — negative-cache TTL
)
  • Serial: a version number for the zone. Whenever you edit the zone, you must increment this. If you forget, secondaries will not pick up the change. A common convention is YYYYMMDDnn — the date plus a two-digit counter.
  • Refresh: how often secondary servers should poll the primary for changes.
  • Retry: if a poll fails, how long to wait before trying again.
  • Expire: how long a secondary may continue serving the zone if it cannot reach the primary at all. After this, it must stop answering.
  • Minimum: originally the default TTL for the zone. In modern use, it is the negative-caching TTL — how long a resolver may cache a "name not found" answer.
Remember the serial increment rule. It is the single most common mistake beginners make when editing a zone file. If you change a record, change the serial. If you forget, and you are running primary/secondary replication, the change may never propagate.

11.5 · Zones & Zone Files

A zone is a contiguous portion of the DNS namespace that is managed by a single administrative entity. It is what the SOA record actually declares authority over.

Note the distinction: a domain is a subtree of the namespace. A zone is a domain minus whatever has been delegated to child zones. When we say a server is "authoritative for example.com", we mean it is authoritative for the zone whose apex is example.com — not for every name that ends in example.com, if some subdomain has been delegated away.

Zone file examples

Here is what a simple forward zone file for lab.local looks like. This is exactly the pattern we will build in the labs this week: 

$TTL 3600
$ORIGIN lab.local.

@    IN   SOA   ns1.lab.local.  admin.lab.local. (
                  2024111501    ; serial
                  3600          ; refresh
                  1800          ; retry
                  604800        ; expire
                  86400 )       ; minimum

; Nameservers
@       IN   NS      ns1.lab.local.
@       IN   NS      ns2.lab.local.

; Mail exchanger
@       IN   MX   10   mail.lab.local.

; Host records
ns1     IN   A       192.168.56.1
ns2     IN   A       192.168.56.2
mail    IN   A       192.168.56.10
www     IN   A       192.168.56.20
web     IN   CNAME   www

; Wildcard (any name not otherwise defined)
*       IN   A       192.168.56.99

Let me point out a few conventions.

  • $TTL sets a default time-to-live that applies to all following records that do not have their own TTL.
  • $ORIGIN sets the domain that is appended to any name that does not end with a dot. This is why we can write www instead of www.lab.local.
  • @ is shorthand for the current origin. At the top of the file, @ means lab.local..
  • Trailing dots matter. ns1.lab.local. (with trailing dot) is a fully qualified domain name. ns1.lab.local (without) would be treated as ns1.lab.local., which is usually not what you want. Always use trailing dots for FQDNs.
  • Relative names like www are appended with the current origin, so they become www.lab.local.
Trailing dots are the number-one source of zone file bugs. If your zone file loads but nothing resolves, check the trailing dots first. BIND is strict about this — it does not guess.

Organizing a zone file

Real zones are organized into sections for readability. The standard order:

  1. $TTL and $ORIGIN directives.
  2. The SOA record.
  3. NS records for the zone's own nameservers.
  4. MX records for mail routing.
  5. A, AAAA, CNAME records for hosts.
  6. Any delegation records (NS records for sub-zones).

Comments start with a semicolon and continue to the end of the line.

11.6 · Reverse Zones & PTR Records

So far we have been mapping names to addresses. But there is a mirror-image concern: given an IP address, what name is associated with it? This is called a reverse lookup, and it matters for a surprising number of things.

Why reverse lookups exist

  • Log readability. When your web server logs a client's IP, that IP is essentially useless in a log. A reverse lookup gives you the hostname — much easier to interpret.
  • Spam filtering. Many mail servers refuse mail from IPs whose PTR records do not match the sending domain. This is called a forward-confirmed reverse DNS check.
  • Diagnostics. When you traceroute across the internet, every hop shows the reverse name of the router — if the operator has set it up.
  • Access control. Some legacy systems use reverse lookups for coarse authentication.

The in-addr.arpa domain

Because DNS names are hierarchical with the most significant part last, and IP addresses are hierarchical with the most significant part first, reverse lookups require reversing the IP octets. IPv4 reverse lookups all live under a special domain called in-addr.arpa.

To look up the name associated with 192.168.56.20, we reverse the octets and append in-addr.arpa: 

20.56.168.192.in-addr.arpa.

This is the name that actually gets queried. It is a PTR-type query, and the answer is the corresponding hostname.

A reverse zone file

Here is a reverse zone file for 192.168.56.0/24. It lives in the domain 56.168.192.in-addr.arpa — the first three octets in reverse, plus in-addr.arpa. 

$TTL 3600
$ORIGIN 56.168.192.in-addr.arpa.

@    IN   SOA   ns1.lab.local.  admin.lab.local. (
                  2024111501    ; serial
                  3600          ; refresh
                  1800          ; retry
                  604800        ; expire
                  86400 )       ; minimum

@       IN   NS      ns1.lab.local.

; PTR records — one per host that needs reverse lookup
1       IN   PTR     ns1.lab.local.
10      IN   PTR     mail.lab.local.
20      IN   PTR     www.lab.local.

Notice how the PTR record owner is just the last octet — 1, 10, 20. The $ORIGIN line supplies the rest, so 20 becomes 20.56.168.192.in-addr.arpa..

Forward-confirmed reverse DNS (FCrDNS)

A well-configured host has both directions matching:

  1. Forward: mail.lab.local → 192.168.56.10
  2. Reverse: 192.168.56.10 → mail.lab.local

When both match, we say the record is forward-confirmed. This is what spam filters check. A misconfigured mail server whose forward and reverse directions disagree will have trouble delivering to many recipients.

The reverse zone lesson: it is not enough to define an A record. If you want a host to be findable by IP — for logs, for reverse diagnostics, or because some other service requires it — you must also create the corresponding PTR record, in a separate reverse zone. Many a first-time DNS deployment breaks silently on this point.

11.7 · Caching, TTL & Forwarding

We saw in section 11.3 that the whole reason DNS scales is caching. Let's look at caching more carefully, because it also has a dark side and a related technique called forwarding.

TTL — the cache lifetime

Every DNS record carries a TTL — a time-to-live — in seconds. When a resolver caches a record, it remembers it for at most that long. After the TTL expires, the record must be re-fetched.

TTL is a trade-off between freshness and load.

TTL setting What it means When it is right
Very low (30–60 seconds) The record is refreshed quickly, so changes propagate fast. But the number of queries to the authoritative server skyrockets. Right before a planned migration, when you want to be able to change IPs quickly. Common in anycast/failover setups.
Medium (5 minutes – 1 hour) Good balance of freshness and load. What most production services use. Standard production websites and services.
High (several hours – days) Very light load on authoritative servers, but changes can be slow to propagate. Resolvers may still hold stale data for many hours. Stable records that rarely change — nameserver records, MX records, TXT records.
Common migration tip: before moving a service to a new IP, lower the TTL of its record to 60 seconds a day or two in advance. This lets all resolvers expire their old cached copies. Then, make the change, and after a day you can raise the TTL back to something normal.

The negative cache

DNS also caches the absence of a record. If you ask for a name that does not exist, the resolver remembers the "NXDOMAIN" response for a duration defined by the SOA Minimum field. This prevents repeated lookups of a name that everyone agrees does not exist.

This is worth knowing because it can bite you: when you first create a new subdomain, some resolvers may still hold the negative cache entry. Their users will fail to resolve the new name until the TTL expires. Setting a shorter SOA Minimum reduces this window.

Forwarding — when you do not want to do it all yourself

A recursive resolver does a lot of work — multiple queries across the globe for every uncached name. Sometimes you do not want to do that work. This is where forwarding comes in.

A forwarding resolver is configured to hand off recursive queries to an upstream resolver. It does not do the iterative hunt itself — it just forwards the query and returns whatever comes back.

  • Small networks usually use forwarding: internal residential routers forward all DNS to the ISP's resolver. Simple and efficient.
  • Corporate networks often use a mix: forward to internal servers for internal zones, forward to public resolvers for external names.
  • Privacy-conscious setups forward to explicit resolvers like 1.1.1.1 or 9.9.9.9, with encrypted transport (DNS over HTTPS or DNS over TLS) to prevent eavesdropping.

In BIND9, forwarding is configured in the options block: 

options {
    directory "/var/cache/bind";
    recursion yes;
    forwarders {
        1.1.1.1;
        8.8.8.8;
    };
    forward only;   /* only forward, never recurse on our own */
    ...
};

The forward only; directive tells BIND to never do its own recursion — always defer upstream. The alternative, forward first;, means "try forwarding, but fall back to recursion if that fails".

11.8 · Querying DNS: dig, nslookup, host

Now that we understand the theory, let's look at the tools you use every day to query DNS. There are three main ones — dig, nslookup, and host — and they serve overlapping but different purposes.

dig — the professional's tool

dig — Domain Information Groper — is the tool serious administrators use. It sends a single DNS query, prints the full response, and exits. No interactive mode, no guessing. Every piece of information in the response is visible. 

$ dig example.com A

; <<>> DiG 9.18.24 <<>> example.com A
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12345
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; QUESTION SECTION:
;example.com.       IN   A

;; ANSWER SECTION:
example.com.    300 IN   A    93.184.216.34

;; Query time: 24 msec
;; SERVER: 1.1.1.1#53(1.1.1.1) (UDP)
;; WHEN: Fri Nov 15 10:22:14 UTC 2024
;; MSG SIZE  rcvd: 56

Let me decode the important parts:

  • status: NOERROR — the query succeeded. Common alternatives: NXDOMAIN (name does not exist), SERVFAIL (server error).
  • flags: qr rd ra — qr means "query response" (this is a reply). rd means "recursion desired" (the client wants full resolution). ra means "recursion available" (the server supports it). If you see aa, the server was authoritative.
  • ANSWER SECTION — the actual answer. In this case, one A record with a TTL of 300 seconds.
  • Query time, SERVER — how long the response took, and which server answered.

Useful dig variations

dig example.com              # A record by default
dig example.com MX           # mail exchangers
dig example.com NS           # authoritative nameservers
dig example.com TXT          # any TXT records (SPF, etc.)
dig -x 93.184.216.34         # reverse lookup — PTR query
dig @8.8.8.8 example.com     # query a specific server
dig +short example.com       # just the answer, no headers
dig +trace example.com       # walk the hierarchy from the root
dig +noall +answer example.com   # suppress everything except the answer
dig ANY example.com          # request all record types (often ignored)
The single most useful debug command: dig +trace example.com. This command starts at the root servers, follows every referral, and prints each step. It shows you exactly which servers answered at each level, and where the resolution succeeds or fails. When DNS is broken, this command tells you where.

nslookup — the interactive classic

nslookup is older than dig and its output is less structured. It is often used interactively, which makes exploratory debugging pleasant. 

$ nslookup example.com
Server:		1.1.1.1
Address:	1.1.1.1#53

Non-authoritative answer:
Name:	example.com
Address: 93.184.216.34

# Interactive mode:
$ nslookup
> server 8.8.8.8
> set type=MX
> example.com
> exit

The phrase "Non-authoritative answer" simply means the answer came from a cache, not from an authoritative server. This is normally fine. If you need an authoritative answer, query the authoritative server directly with nslookup example.com ns1.example.com.

host — brief and to the point

host is the simplest of the three. It gives you what you asked for in one line, without any of the extra output. 

$ host example.com
example.com has address 93.184.216.34
example.com has IPv6 address 2606:2800:220:1:248:1893:25c8:1946
example.com mail is handled by 0 .

$ host 93.184.216.34
34.216.184.93.in-addr.arpa domain name pointer example.com.

For simple queries — "what is the IP of this name?" or "what is the name of this IP?" — host is the fastest to type and the fastest to read. When you need to inspect the full response, use dig.

Which to use?

Tool Best for Output style
dig Debugging, scripted queries, full detail, trace queries Verbose, structured, everything visible
nslookup Interactive exploration, one-off queries Readable but less structured
host Quick single queries, scripts that want terse output One or two lines, minimal formatting

11.9 · Deep Lab — Installing and Configuring BIND9

Now let's build. In this lab, we will install BIND9 — the reference implementation of DNS and the most widely deployed authoritative DNS server in the world — and configure it as the authoritative nameserver for our own private zone.

Step 1 — Install BIND9

sudo apt update
sudo apt install bind9 bind9utils bind9-doc dnsutils -y

bind9 is the server itself. bind9utils contains the zone file checking tools we will use. dnsutils gives us dig and nslookup.

Step 2 — Understand the default layout

BIND9's configuration lives in /etc/bind/. After installation you will see: 

$ ls /etc/bind/
bind.keys   db.0     db.255    db.empty   db.local
db.root     named.conf  named.conf.default-zones  named.conf.local
named.conf.options  rndc.key  zones.rfc1918

$ ls /var/cache/bind/     # working directory for BIND
$ ls /var/lib/bind/       # dynamically-updated zones

The key files:

  • named.conf — the main config. It includes the others.
  • named.conf.options — global options like forwarders, ACLs, listening interfaces.
  • named.conf.local — where you declare your own zones. This is the one we edit most.
  • named.conf.default-zones — the standard zones (root hints, localhost, etc.). Leave it alone.

Step 3 — Configure listening and recursion

sudo nano /etc/bind/named.conf.options

Replace the options block content with: 

options {
    directory "/var/cache/bind";

    // Listen on all interfaces on port 53
    listen-on { any; };
    listen-on-v6 { any; };

    // Allow recursion only from the lab network
    recursion yes;
    allow-recursion { 192.168.56.0/24; 127.0.0.1; };

    // Forward everything else to public resolvers
    forwarders {
        1.1.1.1;
        8.8.8.8;
    };

    // Standard best-practice request
    dnssec-validation auto;

    // Use IPv4 and IPv6
    listen-on-v6 { any; };
};
Never run an open recursive resolver on the public internet. If you set recursion yes without an allow-recursion ACL, anyone on the network can use your server to attack third parties. This is called a "DNS amplification attack", and your server will be blacklisted within hours. Always restrict recursion to your own network — as we did above with the 192.168.56.0/24 ACL.

Step 4 — Check and restart

sudo named-checkconf
# No output means the config is syntactically valid.

sudo systemctl restart named
sudo systemctl status named

# Verify it is listening:
sudo ss -tlnp | grep :53

You should see both UDP and TCP listeners on port 53. DNS uses UDP for most queries and TCP for large responses and zone transfers.

Step 5 — Verify basic resolution

# Ask BIND9 (running on localhost) about a public domain
dig @127.0.0.1 example.com A

# You should see NOERROR and an A record.
# If you get SERVFAIL, check journalctl -u named -n 50.
What you have built: a working recursive DNS resolver that your lab machines can point at. This is already useful — but the real lab is next: making it authoritative for our own private zone.

11.10 · Deep Lab — Authoritative Zone for lab.local

Now the main event. We will create a forward zone and a reverse zone for lab.local, populate them with A, CNAME, MX, and PTR records, and then verify resolution from a client machine.

Step 1 — Create the forward zone file

sudo nano /etc/bind/db.lab.local

Paste this content:

;
; Forward zone file for lab.local
;
$TTL 3600
$ORIGIN lab.local.

;
; SOA — start of authority
;
@   IN  SOA ns1.lab.local. admin.lab.local. (
        2024111501   ; serial   — increment on every change
        3600         ; refresh  — secondary checks every hour
        1800         ; retry    — retry every 30 minutes
        604800       ; expire   — stop serving after a week
        86400 )      ; negative cache TTL

;
; Nameservers
;
@       IN  NS      ns1.lab.local.
@       IN  NS      ns2.lab.local.

;
; Mail exchanger — priority 10 for mail.lab.local
;
@       IN  MX  10  mail.lab.local.

;
; Address records
;
ns1     IN  A       192.168.56.1
ns2     IN  A       192.168.56.2
mail    IN  A       192.168.56.10
www     IN  A       192.168.56.20
db      IN  A       192.168.56.30

; CNAME — an alias
web     IN  CNAME   www

; Wildcard — anything not otherwise defined
*       IN  A       192.168.56.99

Step 2 — Create the reverse zone file

sudo nano /etc/bind/db.192.168.56
;
; Reverse zone file for 192.168.56.0/24
;
$TTL 3600
$ORIGIN 56.168.192.in-addr.arpa.

@   IN  SOA ns1.lab.local. admin.lab.local. (
        2024111501   ; serial
        3600         ; refresh
        1800         ; retry
        604800       ; expire
        86400 )      ; minimum

;
; Nameservers
;
@       IN  NS      ns1.lab.local.

;
; PTR records — reverse lookups
;
1       IN  PTR     ns1.lab.local.
10      IN  PTR     mail.lab.local.
20      IN  PTR     www.lab.local.
30      IN  PTR     db.lab.local.

Step 3 — Validate the zone files before loading

This step is essential. Never point BIND at a zone file you have not validated — a syntax error can prevent the service from starting entirely. 

sudo named-checkzone lab.local /etc/bind/db.lab.local
# Expected: "zone lab.local/IN: loaded serial 2024111501"
# and "OK"

sudo named-checkzone 56.168.192.in-addr.arpa /etc/bind/db.192.168.56
# Expected: "zone 56.168.192.in-addr.arpa/IN: loaded serial 2024111501"
# and "OK"

If you see anything other than OK, read the error message carefully. The most common causes are missing trailing dots and mismatched parentheses in the SOA block.

Step 4 — Declare the zones in named.conf.local

sudo nano /etc/bind/named.conf.local

Add these two zone declarations:

zone "lab.local" {
    type master;
    file "/etc/bind/db.lab.local";
    allow-update { none; };
};

zone "56.168.192.in-addr.arpa" {
    type master;
    file "/etc/bind/db.192.168.56";
    allow-update { none; };
};

type master means this server is the primary authoritative server for the zone. allow-update { none; } disables dynamic DNS updates — we want only explicit file edits to affect the zone.

Step 5 — Reload BIND and verify

sudo named-checkconf       # validate the whole config tree
sudo systemctl reload named

# Check the journal for zone loading
sudo journalctl -u named -n 20

# You should see lines like:
#   zone lab.local/IN: loaded serial 2024111501
#   zone 56.168.192.in-addr.arpa/IN: loaded serial 2024111501

Step 6 — Test from the server itself

# Forward lookup — A record
dig @127.0.0.1 www.lab.local A
# Expected: 192.168.56.20

# CNAME
dig @127.0.0.1 web.lab.local A
# Expected: web is a CNAME for www.lab.local, then the A record 192.168.56.20

# MX
dig @127.0.0.1 lab.local MX
# Expected: 10 mail.lab.local.

# Reverse
dig @127.0.0.1 -x 192.168.56.20
# Expected: www.lab.local.

# Wildcard
dig @127.0.0.1 anything.lab.local A
# Expected: 192.168.56.99
If all five queries return the expected answer, your zone is working correctly. You have built an authoritative DNS server.

Step 7 — Point a client at your server

On a second VM connected to the same host-only network, change the DNS server configuration to point at 192.168.56.1 (or whatever address your BIND9 server holds on that network).

If the client is using Netplan: 

sudo nano /etc/netplan/01-netcfg.yaml

Add 192.168.56.1 as the first nameserver for the interface. Then:

sudo netplan apply
cat /etc/resolv.conf
# The first "nameserver" line should now be 192.168.56.1

# Test resolution
dig www.lab.local
host mail.lab.local
nslookup db.lab.local

From the client, all names in lab.local should resolve to their configured addresses — routed through your BIND9 server.

Step 8 — Break it, then fix it

Now let's build some diagnostic reflexes. Introduce a deliberate mistake in the zone file: 

sudo nano /etc/bind/db.lab.local
# Change the serial to a random value, or remove a trailing dot
# (for example: change "ns1.lab.local." to "ns1.lab.local")

sudo named-checkzone lab.local /etc/bind/db.lab.local
# This will produce an error — read it.

# Try to reload:
sudo systemctl reload named
# The reload may succeed at the systemd level, but BIND will
# reject the zone. Check the journal.
sudo journalctl -u named -n 30 --no-pager

The journal is where BIND tells you exactly what it did not like. Look for lines mentioning db.lab.local and the specific error message — usually something like "bad owner name" or "not at top of zone". Fix the mistake, re-run named-checkzone until it says OK, and reload.

The workflow you have just learned: edit zone file → run named-checkzone → reload → check journal. Never skip the check. On a production primary nameserver for a public zone, skipping this check can take an entire domain offline.

Step 9 — Add a new host, end to end

As a final exercise, add a new host — say, app.lab.local at 192.168.56.40 — and verify that both forward and reverse lookups work.

  1. Add an A record to db.lab.local.
  2. Add a matching PTR record to db.192.168.56.
  3. Increment the serial in both SOA records.
  4. Run named-checkzone on both files.
  5. Reload BIND and verify with dig from server and client.
The serial rule in action: if you change the record but forget to change the serial, and this server were a primary with secondaries, the secondaries would not pick up the change. On a single-server lab, the change still applies immediately — but build the discipline of incrementing the serial anyway. It is a habit that will save you on real infrastructure.

Week 11 Summary

  • What DNS does: maps human-readable names to IP addresses and everything else networks need. It is the phone book of the internet, but far richer than that.
  • The hierarchy: an inverted tree. Root servers delegate TLDs, TLDs delegate domains, domains delegate subdomains. Delegation is what makes DNS scale.
  • Resolution: clients send recursive queries to a resolver. The resolver sends iterative queries to root, TLD, and authoritative servers, following referrals until it gets a final answer.
  • Resource records: A, AAAA, CNAME, MX, NS, PTR, SOA, TXT, SRV. Each one carries a different kind of data. CNAMEs cannot coexist with other records at the same name.
  • Zones and zone files: a zone is a portion of the namespace managed by one authority. Zone files are text files with SOA, NS, and record entries. Trailing dots matter.
  • Reverse zones: they live under in-addr.arpa, with IP octets reversed. PTR records map IP addresses back to hostnames. Forward-confirmed reverse DNS matters for mail servers and logging.
  • Caching and TTL: every record carries a time-to-live. Caching is what makes DNS cheap; TTL controls the freshness/load trade-off. Negative caching also occurs.
  • Forwarding: a simpler resolver model where queries are handed off upstream to a designated resolver instead of being resolved iteratively by the local server.
  • Tools: dig for full-detail queries and traces, nslookup for interactive exploration, host for brief answers.
  • BIND9: the reference authoritative server. Configuration under /etc/bind/. Always validate with named-checkzone before reloading. Restrict recursion with an ACL — never run an open resolver.
