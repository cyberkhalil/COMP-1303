13.1 · Why a Database Service

For the last four weeks, we have been building up the pieces of a small Linux stack. In Week 10 we learned to install packages and configure networks, and we built a DHCP server. In Week 11 we built a DNS server that resolves names for our own internal domain. In Week 12 we deployed Nginx as a web server and set it up as a reverse proxy in front of a Python application.

But every one of those services has the same limitation. The state they hold lives in RAM, and it disappears when the process restarts. Our DHCP leases vanish. Our DNS zone is a set of files that must be edited by hand. Our web application stores its data in Python dictionaries that evaporate the moment the process exits.

To build a real service, we need persistent structured storage. That is what a database service provides — and this week, we are going to install, configure, and administer one of the most widely used open-source database systems in the world: MariaDB.

One-line definition: MariaDB is a community-developed fork of MySQL. It is a relational database management system — it stores structured data in tables, provides ACID transactional guarantees, and speaks the SQL language over a network socket.

Why MariaDB and not MySQL?

In 2009, Oracle acquired Sun Microsystems, which had previously acquired MySQL AB, the company behind MySQL. Concerned about Oracle's stewardship of the project, the original MySQL developers forked the codebase and created MariaDB. It is named after Maria Widenius, the younger daughter of MySQL's founder — the elder daughter, My, gave MySQL its name.

From a technical perspective, MariaDB and MySQL are remarkably similar. MariaDB maintains drop-in compatibility with MySQL at the protocol level, the SQL-language level, and the client-tool level. Any application that speaks MySQL can talk to MariaDB, and vice versa. For most workloads, you can switch between them without changing a line of code.

Aspect MariaDB vs MySQL
Licensing MariaDB is 100% open source under the GPL. MySQL is dual-licensed, with proprietary enterprise features managed by Oracle.
Development MariaDB is community-governed through the MariaDB Foundation. MySQL is developed and released by Oracle.
Storage engines Both support InnoDB (transactions) and MyISAM (legacy). MariaDB adds Aria, ColumnStore, and other engines.
Compatibility MariaDB is a drop-in replacement for MySQL 5.7 in most cases. Some features diverge after MySQL 8.0.
Default on Ubuntu Ubuntu ships MariaDB in its default repositories. MySQL is also available but not the default.

For this course, we use MariaDB because it is the default on Ubuntu, and because installing it requires no third-party repositories. But everything we learn — SQL, users, privileges, backups — applies directly to MySQL and to any other relational database you might use later.

The role of a database in a Linux stack

In a typical Linux service stack, the database is the layer that persists state. Consider a simple web application:

A database service sits at the bottom of the stack. When it goes down, everything above it stops working.

The database holds the state that everything else depends on. Customer records, orders, sessions, configuration, analytics — all of it lives here. And this makes the database's job difficult: it must be fast, reliable, consistent, and durable. A web server crashing is an annoyance. A database losing data is a catastrophe.

What "relational" means

The word relational comes from the mathematical concept of relations — tables, essentially. The relational model was proposed by Edgar F. Codd in 1970 and was one of the foundational advances in database theory.

The core idea: instead of storing records in hierarchies or pointers — the way network and hierarchical databases did in the 1960s — you store them in flat tables of rows and columns, and you relate tables to one another through primary and foreign keys. Queries are expressed declaratively, using SQL.

Why relational databases won: because the model is simple, the query language is standardized, and the computer science behind query optimization has been refined for fifty years. Good relational databases answer arbitrary queries efficiently, without the application needing to know how the data is physically stored.

What modern relational databases guarantee

Relational databases are usually described as providing ACID guarantees. Let me unpack that because it explains what a database gives you that a file system does not.

Property Meaning
Atomicity A transaction — a group of operations — either fully succeeds or fully fails. There is no partial state.
Consistency A transaction takes the database from one valid state to another. Constraints, invariants, and foreign-key relations are always honored.
Isolation Concurrent transactions do not interfere with each other. To a reader, transactions appear to run in some serializable order.
Durability Once a transaction has been committed, it survives crashes, power failures, and restarts. Often achieved with write-ahead logging.
What ACID buys you: you can write an application that says "transfer ten dollars from Alice's account to Bob's" as two operations, and be sure that if the process crashes between them, the database will either have done both or neither. Implementing that guarantee yourself, on top of the file system, is an enormous amount of work. Relational databases do it for you.

13.2 · The Relational Model & SQL

Before we install anything, let's make sure the vocabulary is clear. Every relational database speaks in terms of a small set of concepts, and understanding them makes everything else easier to reason about.

The units of structure

Term Meaning Example
Database A named collection of tables that belong together, usually accessed by one application. shop_app
Table A set of rows with the same structure. Analogous to a spreadsheet or a class of objects. customers
Column A field of a table — a name and a type. Every row has a value (or NULL) for each column. email VARCHAR(255)
Row A single record. Equivalent to an instance of a class, or a line in a spreadsheet. (1, 'Alice', 'alice@example.com')
Primary key A column (or set of columns) that uniquely identifies a row. Cannot be NULL, must be unique. id INT PRIMARY KEY
Foreign key A column that references the primary key of another table. Enforces referential integrity. customer_id INT REFERENCES customers(id)
Index A data structure that speeds up lookups on a column or set of columns. Takes up extra space. CREATE INDEX ON customers(email);
View A stored query that appears like a table. Useful for abstracting complex queries. CREATE VIEW active_customers AS SELECT ...

A concrete example

Let's build a small schema for an online store. Two tables, related by a foreign key. 

-- Customers: one row per person

CREATE TABLE customers (
    id      INT AUTO_INCREMENT PRIMARY KEY,
    name    VARCHAR(100) NOT NULL,
    email   VARCHAR(255) NOT NULL UNIQUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Orders: many orders per customer

CREATE TABLE orders (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    customer_id  INT NOT NULL,
    total        DECIMAL(10,2) NOT NULL,
    placed_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (customer_id) REFERENCES customers(id)
);

Two things are worth pointing out.

  • AUTO_INCREMENT tells the database to assign the next integer automatically every time a new row is inserted. We do not have to keep track of IDs — the database does.
  • The foreign key is enforceable metadata. If we try to insert an order with a customer_id that does not exist, the database will refuse. This is the "consistency" in ACID, enforced for us.

SQL in three families

Structured Query Language — SQL — is the language we use to talk to relational databases. It is divided into several families of statements, and it is worth knowing which is which.

Family Stands for Statements
DDL Data Definition Language CREATE, ALTER, DROP, TRUNCATE — these define and modify the structure of tables.
DML Data Manipulation Language SELECT, INSERT, UPDATE, DELETE — these work with the rows.
DCL Data Control Language GRANT, REVOKE — these manage who can do what. We will use these extensively in the users-and-privileges section.
TCL Transaction Control Language BEGIN, COMMIT, ROLLBACK — these define transactional boundaries.
SQL is declarative, not imperative. When you write SELECT name FROM customers WHERE email = 'alice@example.com', you are telling the database what you want, not how to compute it. The database's query planner decides which indexes to use, in what order to join tables, and which algorithm to apply. This is a big part of why relational databases are so powerful: fifty years of research have made the query planner very good at this, and you do not have to reason about it yourself.

Data types you will use most

MariaDB supports a rich set of data types. The following are the ones you will see in practice.

Type Used for Notes
INT Integer numbers up to about two billion (signed). Use BIGINT for larger, or INT UNSIGNED for positives only.
DECIMAL(p, s) Exact decimal numbers, with p total digits and s after the decimal point. Use for money. Never use FLOAT for currency.
VARCHAR(n) Variable-length strings up to n characters. Preferred for names, usernames, and short text.
TEXT Large text — up to 64 KB. Use for content, comments, descriptions.
TIMESTAMP Date and time. Has special default behavior — can auto-update. Range limited to years 1970–2038. Use DATETIME for wider range.
BOOLEAN Boolean values. MariaDB stores it as TINYINT(1) — true is 1, false is 0.
ENUM('a','b','c') One value from a fixed list. Useful for status fields and categories.
JSON Semi-structured JSON data with query support. MariaDB supports JSON as an alias for LONGTEXT with validation.
Never use FLOAT for money. Floating-point numbers cannot exactly represent most decimal fractions. 0.1 + 0.2 in floating point is not 0.3. For currencies, totals, and anything that must be exact, use DECIMAL. This is a classic beginner mistake that has cost companies real money.

13.3 · Installing MariaDB

Installing MariaDB on Ubuntu is one apt command. This is one of the reasons we used Ubuntu for this course — MariaDB ships in the default repositories, so no third-party sources and no key juggling are needed.

The install

sudo apt update
sudo apt install mariadb-server mariadb-client

Two packages. The mariadb-server package contains the actual daemon — the process that listens on a socket, keeps the data in memory, and writes to disk. mariadb-client contains the command-line client we use to talk to it.

On Ubuntu, the package will automatically:

  • Create the mysql system user and group.
  • Create the data directory at /var/lib/mysql/.
  • Install a systemd unit file, enabling MariaDB to start at boot.
  • Start the service automatically.

Service management with systemd

MariaDB runs as a systemd service. Let's recall the pattern from Week 9: 

# Check the current status
systemctl status mariadb

# Start, stop, restart
sudo systemctl start mariadb
sudo systemctl stop mariadb
sudo systemctl restart mariadb

# Enable or disable start-at-boot
sudo systemctl enable mariadb
sudo systemctl disable mariadb

# Follow the logs
journalctl -u mariadb -f

After installing, check the status. You should see "active (running)" and a process ID for the MariaDB daemon — which is named mariadbd.

A naming note. If you look at logs or process lists, you may see MariaDB referred to as mysqld, mariadbd, or simply mysql. The daemon is usually called mariadbd on modern Ubuntu, but many files and directories retain their mysql prefix for compatibility. This is worth remembering when you go looking for where configuration lives.

How MariaDB is structured

The mariadbd daemon writes to /var/lib/mysql/ and listens for clients on both a Unix socket and TCP port 3306.

Connecting for the first time

On Ubuntu, the root user of the system can connect to MariaDB as the root database user without a password — through the Unix socket only. This is by design: the initial configuration assumes you are the system administrator and can prove it by using sudo. 

sudo mariadb

You should get a MariaDB prompt: 

Welcome to the MariaDB monitor.  Commands end with ; or \g.
Your MariaDB connection id is 42
Server version: 10.11.6-MariaDB-0ubuntu0.24.04.1 Ubuntu 24.04

Type 'help;' or '\h' for help. Type '\c' to clear the current input statement.

MariaDB [(none)]>

The prompt shows [(none)] because we are not connected to any specific database yet. Type quit or press Ctrl+D to exit.

This initial state is not safe for production. Anyone with sudo on this machine can log in as root. There is no password on the root database user. Anonymous users may exist. The default installation serves only the local machine, so this is not immediately dangerous — but we are about to fix it anyway.

13.4 · Securing the Installation

MySQL and MariaDB ship with a script that walks you through a handful of security hardening steps. On MariaDB the script is called mariadb-secure-installation — on MySQL it is mysql_secure_installation. Run it once after the very first install, before you put any real data in the database. 

sudo mariadb-secure-installation

The script asks a series of yes-or-no questions. Let's walk through them.

Step 1 — Set a root password

The first question asks whether you want to set a root password. In older versions, the root user of MariaDB had no password by default and could only be accessed via the Unix socket. On modern MariaDB, whether this is asked depends on the version and the distribution.

If you are asked, answer yes. Choose a strong password — this is a root account, equivalent to system root for the database. Save it in a password manager. Do not use the same password as your system account.

Why a root password at all? Because in production, an attacker who gets a valid MariaDB client on the machine should not automatically have root in the database. A password is a separate proof of identity. On our lab VM, the socket authentication is enough — but it is good practice to set the password anyway, and it is required on most cloud databases.

Step 2 — Remove anonymous users

MariaDB ships with anonymous user accounts — a concept that made sense decades ago but is dangerous today. Answer yes to remove them.

Step 3 — Disallow root login remotely

The root database user should only ever be allowed to connect from localhost. Allowing remote root login means that anyone who knows the password can attack the database from anywhere on the network. Answer yes to disallow remote root.

Do not allow remote root. When you need remote access to a database, create a separate account for that, with the narrowest possible privileges, restricted to the specific host that needs it. Root is for local administration only.

Step 4 — Remove the test database

MariaDB ships with a database named test that anyone can use. It is a long-standing footgun. Answer yes to drop it.

Step 5 — Reload privilege tables

Finally, the script asks whether you want to reload the privilege tables. Answer yes. This applies all the changes immediately without a restart.

What the secure script actually did

Under the hood, the script is running ordinary SQL commands against the mysql system database. If you want to see exactly what it did, you can inspect the user table: 

sudo mariadb -e "SELECT User, Host, plugin FROM mysql.user;"

Typical output after running the secure script: 

+-------------+-----------+-----------------------+
| User        | Host      | plugin                |
+-------------+-----------+-----------------------+
| mariadb.sys | localhost | mysql_native_password |
| root        | localhost | mysql_native_password |
+-------------+-----------+-----------------------+

Just two users remain. The root account can only log in from localhost. No anonymous users exist. This is a good baseline.

Additional hardening beyond the script

The script covers the standard cases. For a production server, consider these additional measures.

  • Bind only to localhost by default. MariaDB should listen on 127.0.0.1 or on a private interface — not on the public internet. If a web application on the same machine needs the database, use the Unix socket, not TCP.
  • Firewall the port. If you must allow remote connections, use ufw or iptables to restrict port 3306 to specific source IPs.
  • Enable binary logging and slow query logging. These let you audit what is happening on the server and diagnose slow queries.
  • Schedule backups. We will cover this in section 13.8.
  • Keep the server patched. Security updates for MariaDB arrive through apt like any other package.
Where things stand: after running the secure script, we have a clean, minimal MariaDB install. Only root can log in, and only from localhost. No anonymous users, no test database. This is the correct starting point for every deployment.

13.5 · Databases, Tables & SQL Basics

Now we use the database. In this section we will create a database, define a couple of tables, insert some rows, query them back, and finally clean them up. Everything is done through the MariaDB command-line client or from SQL scripts.

DDL — creating structure

-- Create a new database
CREATE DATABASE shop_app;
USE shop_app;

-- Create the customers table
CREATE TABLE customers (
    id      INT AUTO_INCREMENT PRIMARY KEY,
    name    VARCHAR(100) NOT NULL,
    email   VARCHAR(255) NOT NULL UNIQUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Create the orders table with a foreign key
CREATE TABLE orders (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    customer_id  INT NOT NULL,
    total        DECIMAL(10,2) NOT NULL,
    placed_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (customer_id) REFERENCES customers(id)
        ON DELETE CASCADE
);

A few things to note:

  • CREATE DATABASE creates the container. USE selects it as the current database for subsequent commands.
  • NOT NULL means the column cannot contain null values. This is a constraint — a kind of contract the database enforces.
  • UNIQUE means no two rows may have the same value. So no two customers can register with the same email.
  • DEFAULT CURRENT_TIMESTAMP means that if you do not provide a value, the column gets the current time. This is how created_at fills itself.
  • ON DELETE CASCADE says: if a customer is deleted, delete their orders too. Without this, the delete would fail because orders still reference the customer.

Showing what exists

SHOW DATABASES;
SHOW TABLES;
DESCRIBE customers;

SHOW DATABASES lists the databases on the server. SHOW TABLES lists the tables inside the current database. DESCRIBE gives you the schema — columns, types, keys, defaults. All three are essential when you first connect to a database you have never seen before.

DML — manipulating data

-- Insert a customer
INSERT INTO customers (name, email)
VALUES ('Alice', 'alice@example.com');

-- Insert a second
INSERT INTO customers (name, email)
VALUES ('Bob', 'bob@example.com');

-- Insert an order for customer 1
INSERT INTO orders (customer_id, total)
VALUES (1, 49.99);

-- Read them back
SELECT * FROM customers;
SELECT id, name FROM customers WHERE email LIKE '%example.com';

-- Update
UPDATE customers SET name = 'Alice Smith' WHERE id = 1;

-- Delete
DELETE FROM customers WHERE email = 'bob@example.com';

A few points about SQL statements.

  • INSERT adds rows. You list the columns you are providing values for, and then the values themselves. Columns you omit get their defaults — or NULL if no default exists.
  • SELECT reads rows. SELECT * means "all columns." WHERE filters. LIKE does pattern matching with % as a wildcard.
  • UPDATE modifies existing rows. The WHERE clause determines which rows. Every row matching the WHERE gets the change.
  • DELETE removes rows. Again, the WHERE clause determines which. DELETE with no WHERE clears the entire table.
The most dangerous SQL commands. UPDATE and DELETE without a WHERE clause affect every row in the table. There is no undo. Every serious DBA has at one point in their career typed DELETE FROM users; without a WHERE, on the wrong database, and watched the table empty in a fraction of a second. Many production systems guard against this with a client setting that refuses unqualified UPDATE and DELETE. Enable it.

Joins — reading related data

The real power of relational databases is joins — combining data from multiple tables. The most common is an INNER JOIN, which returns rows that match in both tables. 

-- Every order, with the name of the customer who placed it
SELECT   orders.id,
         orders.total,
         customers.name,
         customers.email
FROM     orders
JOIN     customers ON orders.customer_id = customers.id
ORDER BY orders.placed_at DESC;

JOIN ... ON matches rows from the two tables where the specified condition is true. Here, we match each order with the customer whose ID matches the order's customer_id. This is the fundamental operation that makes normalized data queryable.

Transactions

A transaction is a group of statements that must all succeed or all fail together. The classic example is a bank transfer: 

BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT;

If the process crashes between the two updates, or if we call ROLLBACK instead of COMMIT, the database will not have applied either update. From outside, the transfer either completed or did not happen. There is no in-between.

Why this matters. Without transactions, every application would have to implement its own crash recovery. With transactions, the database provides it. This is one of the biggest reasons relational databases are the default choice for any application that handles money, personal data, or anything else where partial updates are unacceptable.

DDL for changes — ALTER and DROP

-- Add a column to an existing table
ALTER TABLE customers ADD COLUMN phone VARCHAR(20);

-- Add an index for a column you query often
CREATE INDEX idx_customers_name ON customers(name);

-- Remove a column
ALTER TABLE customers DROP COLUMN phone;

-- Delete a table (permanent!)
DROP TABLE orders;

-- Delete a whole database (also permanent!)
DROP DATABASE shop_app;

ALTER modifies the structure of an existing table. DROP removes it. There is no undo. On a production server, every DROP should be preceded by a backup.

13.6 · Users, Hosts & Privileges

MariaDB's permission system is one of the most peculiar things about the product. It is also one of the most important to understand, because misuse is a common source of security problems.

The critical concept: user@host

In MariaDB, a user account is not just a username. It is a pair: a username and a host. Two accounts named app at different hosts are entirely separate accounts with separate passwords and separate privileges. 

app@localhost         -- app, connecting via the local socket or 127.0.0.1
app@192.168.56.%      -- app, connecting from any address in the 192.168.56.0/24 subnet
app@%.example.com     -- app, connecting from any host in the example.com domain
app@%                 -- app, connecting from anywhere

The host field can be a literal IP address, a hostname, a wildcard pattern using % — which matches any sequence of characters — or _, which matches exactly one character.

Most hosts also use % as a well-known default — app@% means "app from anywhere." This is exactly what you want for a user that must be accessed remotely, and exactly what you do not want for a user that only needs local access.

Never grant app@% broad privileges on a server with a public IP. That means the account is accessible from every machine on the internet. If a password leaks, the attacker can log in from anywhere. Restrict by host whenever you can.

Creating a user

CREATE USER 'app'@'localhost' IDENTIFIED BY 'a-strong-password';
CREATE USER 'app'@'192.168.56.%' IDENTIFIED BY 'a-strong-password';

The IDENTIFIED BY clause sets the password. Choose strong passwords. There is no rate-limiting by default on MariaDB password attempts, so a weak password can be brute-forced relatively quickly.

Granting privileges

A newly created user has almost no privileges. It can connect, but it cannot do anything. Privileges are granted explicitly. 

-- Give the app user full access to the shop_app database
GRANT ALL PRIVILEGES ON shop_app.* TO 'app'@'localhost';

-- Give the reporting user read-only access
GRANT SELECT ON shop_app.* TO 'report'@'localhost';

-- Give the app user only what it needs on the orders table
GRANT SELECT, INSERT, UPDATE ON shop_app.orders TO 'app'@'192.168.56.%';

-- Apply the changes
FLUSH PRIVILEGES;

The ON clause specifies the scope of the grant. It can be:

  • *.* — every database, every table. Extremely broad. Use sparingly.
  • shop_app.* — every table in one database. Common for application users.
  • shop_app.orders — a single table. Use this when the application only needs one table.

The principle of least privilege

The single most important rule of database security: grant only what is actually needed. Nothing more.

A web application that reads products and writes orders does not need DROP TABLE permission. A reporting tool that only reads data does not need INSERT or DELETE. A read replica's user does not need write access at all.

Every privilege that is granted is a capability that can be abused if the application is compromised. An attacker who gains control of a web app is limited to what its database user can do. Least privilege turns a catastrophic breach into a contained one.

Scenario Recommended grant
Web application frontend SELECT, INSERT, UPDATE, DELETE on the specific database, from the application server's IP only.
Read-only reporting SELECT only, from the reporting server's IP.
Migration/deployment tool ALTER, CREATE, DROP, INDEX plus DML, ideally used only during deployments.
Backup tool SELECT, LOCK TABLES, SHOW VIEW, TRIGGER, EVENT — enough to take a complete dump.
Local administrator root@localhost, socket-authenticated, no remote access.

Listing users and their privileges

-- List all users
SELECT User, Host FROM mysql.user ORDER BY User;

-- Show what privileges a user has
SHOW GRANTS FOR 'app'@'localhost';

-- Show column-by-column privileges
SELECT * FROM mysql.user WHERE User = 'app'\G

SHOW GRANTS is the beginning of every audit conversation. Whenever you are not sure what an account can do, run it, read the output carefully, and ask: does this account actually need all of these? If the answer is no, revoke what is not needed.

Revoking and dropping

-- Take away a specific privilege
REVOKE DELETE ON shop_app.* FROM 'app'@'localhost';

-- Remove the user entirely
DROP USER 'app'@'localhost';

REVOKE removes specific privileges. DROP USER removes the account. Both are trivially reversible by an administrator, so there is no reason to be reluctant to clean up accounts you no longer need.

13.7 · Connecting from a Web App

Recall from Week 12 that we built a Flask application running on 127.0.0.1:5000 behind Nginx as a reverse proxy. That application had no persistence — its data lived in Python dictionaries and vanished on restart. Now we connect it to a real database.

The connection parameters

To connect to a MariaDB server from an application, you need five things:

  • Host — localhost if the app is on the same machine, or the database server's IP if not.
  • Port — 3306 by default.
  • Database name — shop_app in our example.
  • Username and password — the MariaDB user@host account the app uses.

Here is a minimal Flask application that reads from the database: 

from flask import Flask, jsonify
import mysql.connector

app = Flask(__name__)

def get_db():
    return mysql.connector.connect(
        host='localhost',
        user='app',
        password='a-strong-password',
        database='shop_app'
    )

@app.route('/customers')
def list_customers():
    conn = get_db()
    cur = conn.cursor(dictionary=True)
    cur.execute('SELECT id, name, email FROM customers ORDER BY id')
    rows = cur.fetchall()
    cur.close()
    conn.close()
    return jsonify(rows)

@app.route('/customers/<int:cid>')
def show_customer(cid):
    conn = get_db()
    cur = conn.cursor(dictionary=True)
    cur.execute('SELECT * FROM customers WHERE id = %s', (cid,))
    row = cur.fetchone()
    cur.close()
    conn.close()
    if row is None:
        return jsonify({'error': 'not found'}), 404
    return jsonify(row)

if __name__ == '__main__':
    app.run(host='127.0.0.1', port=5000)
Never embed credentials in source code. The example above has the password hardcoded for brevity, but in any real application, connection credentials belong in environment variables, a configuration file with restrictive permissions, or a secrets manager. If the code is committed to a git repository — even a private one — the password is now stored in the git history forever.

Always use parameterized queries

Notice the second route uses %s as a placeholder and passes the value separately: 

cur.execute('SELECT * FROM customers WHERE id = %s', (cid,))

This is critical. Never build SQL by string concatenation: 

# DANGEROUS — never do this
cur.execute(f'SELECT * FROM customers WHERE id = {cid}')

Concatenating user input into SQL is how SQL injection vulnerabilities happen. An attacker who can control cid in the dangerous version can substitute their own SQL — drop a table, read all data, or in some configurations execute code on the database server.

SQL injection is one of the most common web vulnerabilities in the world. It has been number one on OWASP's top ten for decades. Parameterized queries — passing values separately from the SQL string — are the correct defense. Every database driver supports them. Use them without exception.

Connection pooling

Opening a new database connection for every request is expensive. Each connection involves a TCP handshake, authentication, and allocating a thread on the server. Under load, this becomes the bottleneck.

The fix is a connection pool. The application maintains a small pool of open connections and reuses them. Every major framework has this built in or available as a library. 

from mysql.connector import pooling

pool = pooling.MySQLConnectionPool(
    pool_name='mypool',
    pool_size=5,
    host='localhost',
    user='app',
    password='a-strong-password',
    database='shop_app'
)

def get_db():
    return pool.get_connection()

Five connections is plenty for a small app. In a production deployment, you would tune the pool size based on the number of worker processes and the expected request concurrency.

What the database sees

When the application connects, MariaDB logs the connection. Any administrator can see what is currently connected: 

SHOW PROCESSLIST;

This shows every active connection: its ID, the user, the host it came from, which database it is using, its current command, how long it has been running, and what state it is in. The output is indispensable when you are diagnosing why the database is overloaded.

If you see a query that has been running for minutes, something is wrong. If you see the same user opening dozens of connections, the pool size is wrong or connections are leaking. If you see a lot of Sleep commands, the application is not actually using those connections — they should be closed.

13.8 · Backup & Restore

Backups are the single most important thing a database administrator does. Every other task can be deferred. Backups cannot. The three scenarios that destroy a database without a backup are: hardware failure, human error, and ransomware. RAID does not help with any of them — RAID keeps a running system running, it does not protect against a mistaken DROP or a corrupted file.

The classic tool: mysqldump

mysqldump — also installed as mariadb-dump on modern MariaDB — connects to the server, reads the data, and writes a logical backup: a text file containing SQL statements that will recreate the data when played back. 

# Dump one database to a file
mysqldump -u root -p shop_app > shop_app.sql

# Dump all databases
mysqldump -u root -p --all-databases > all_databases.sql

# Dump the schema only (no data)
mysqldump -u root -p --no-data shop_app > shop_app_schema.sql

# Dump just a few tables
mysqldump -u root -p shop_app customers orders > shop_subset.sql

The output is a plain text SQL file. You can open it, read it, edit it, split it, diff it, commit it to a repository. This is a huge advantage when you need to inspect a backup or reconstruct a specific row.

Restoring from a dump

# Restore into a (freshly created) database
mysql -u root -p shop_app < shop_app.sql

# Or: create the database first if it does not exist
mysql -u root -p -e "CREATE DATABASE shop_app;"
mysql -u root -p shop_app < shop_app.sql

The restore replays every SQL statement in the file, in order. When it finishes, the database is in the same state as when the dump was taken.

A dump is a snapshot, not a live replica. Between the moment you start the dump and the moment it finishes, the live database keeps receiving writes. The dump is consistent — it captures a specific point in time — but it does not contain changes made after that point. If you need continuous replication, you need a different mechanism — MariaDB's binary log replication, or a hot-standby product.

Automating backups

A backup you take by hand once is not a backup strategy. What you want is a script that runs on a schedule, produces reliable dumps, rotates old ones, and warns you if it fails. On Linux, the standard scheduler is cron.

A minimal backup script: 

#!/bin/bash
# /usr/local/bin/backup-mariadb.sh

set -euo pipefail

BACKUP_DIR=/var/backups/mariadb
DATE=$(date +%Y-%m-%d_%H-%M-%S)
FILE="$BACKUP_DIR/shop_app_$DATE.sql.gz"

mkdir -p "$BACKUP_DIR"

# Dump and compress in one pass
mysqldump -u backup -p"$BACKUP_PASSWORD" --single-transaction shop_app | gzip > "$FILE"

# Keep only the last 14 daily backups
find "$BACKUP_DIR" -name 'shop_app_*.sql.gz' -mtime +14 -delete

echo "Backup complete: $FILE"

And the corresponding cron entry: 

# Run at 02:30 every day
30 2 * * * /usr/local/bin/backup-mariadb.sh >> /var/log/mariadb-backup.log 2>&1

Let me point out the two important flags in the dump.

  • --single-transaction makes the dump consistent without locking the tables. This is only correct for InnoDB tables, which is what you should be using. For MyISAM tables, you need --lock-tables, which blocks writes.
  • Compression with gzip reduces the dump size by a factor of ten or more. SQL text compresses very well.
A backup you have never restored is not a backup. It is a hopeful collection of bytes. Once a month, restore your most recent backup into a test database and confirm that the data is there and the application works against it. This catches silent failures: the backup script that stopped running three months ago, the password that expired, the disk that filled up.

Beyond dumps: physical backups and replication

mysqldump is fine for databases up to a few gigabytes. Beyond that, it becomes slow — both to produce and to restore — and it competes with the live workload.

For larger deployments, consider:

Method What it does
mariabackup Physical backup tool derived from Percona XtraBackup. Copies the data files directly, without stopping the server.
Filesystem snapshots LVM, ZFS, or Btrfs snapshots of /var/lib/mysql/. Instantaneous and cheap, if the filesystem supports it.
Binary log replication Streams every write to a replica server. The replica is a live, up-to-date copy of the primary. Requires more infrastructure but gives continuous availability.
Cloud-managed backups Most cloud providers offer automated backups and point-in-time restoration for managed databases. Recommended if you are on a cloud platform.
The rule to remember: a proper backup strategy has three parts — produce regularly, test regularly, and store the backup somewhere other than the server. A backup that lives on the same machine as the database is not a backup — it is an additional copy, and it will disappear with the original.

13.9 · Deep Lab — Deploy MariaDB & Create a Database

Now we build. In this lab we will install MariaDB, secure it, create a database with tables and data, and set up an application user with the least privilege it needs.

Step 1 — Install

sudo apt update
sudo apt install mariadb-server mariadb-client -y

systemctl status mariadb

The service should be running. If it is not, check journalctl -u mariadb -n 50 for the reason.

Step 2 — Secure the installation

sudo mariadb-secure-installation

Answer the prompts as follows:

  • Set root password? Yes — choose a strong one.
  • Remove anonymous users? Yes.
  • Disallow root login remotely? Yes.
  • Remove test database? Yes.
  • Reload privilege tables? Yes.

Step 3 — Verify the resulting users

sudo mariadb -e "SELECT User, Host FROM mysql.user;"

You should see only root@localhost and the internal mariadb.sys account. No anonymous users.

Step 4 — Create a database and tables

sudo mariadb

At the MariaDB prompt:

CREATE DATABASE shop_app CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

USE shop_app;

CREATE TABLE customers (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    name       VARCHAR(100) NOT NULL,
    email      VARCHAR(255) NOT NULL UNIQUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;

CREATE TABLE orders (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    customer_id  INT NOT NULL,
    total        DECIMAL(10,2) NOT NULL,
    placed_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
        ON DELETE CASCADE
) ENGINE=InnoDB;

Notice the ENGINE=InnoDB at the end of each table. This is the default engine on MariaDB, but stating it explicitly is good practice — we want InnoDB, not the legacy MyISAM engine, because InnoDB supports transactions and foreign keys.

Also notice utf8mb4 as the character set. This is the modern UTF-8 collation that handles the full Unicode range, including emoji and many non-Latin scripts. The old utf8 collation in MySQL/MariaDB is actually a limited three-byte variant and causes surprising bugs.

Step 5 — Insert some data

INSERT INTO customers (name, email) VALUES
    ('Alice',   'alice@example.com'),
    ('Bob',     'bob@example.com'),
    ('Carol',   'carol@example.com');

INSERT INTO orders (customer_id, total) VALUES
    (1, 49.99),
    (1, 99.50),
    (2, 12.00),
    (3, 210.75);

SELECT * FROM customers;
SELECT * FROM orders;

Step 6 — Create the application user

-- Application runs on this same machine
CREATE USER 'shop'@'localhost' IDENTIFIED BY 'a-strong-password';

-- Grant only what the app needs
GRANT SELECT, INSERT, UPDATE, DELETE
    ON shop_app.*
    TO 'shop'@'localhost';

FLUSH PRIVILEGES;

-- Verify
SHOW GRANTS FOR 'shop'@'localhost';

The SHOW GRANTS output should show exactly four privileges — SELECT, INSERT, UPDATE, DELETE — on shop_app.*, and nothing else.

Step 7 — Test the application user

quit

mysql -u shop -p shop_app

Enter the password you set. Then try some queries:

SELECT * FROM customers;                   -- should work
INSERT INTO customers (name, email) VALUES ('Dave', 'dave@example.com');  -- should work
DROP TABLE customers;                      -- should FAIL: no DROP privilege
CREATE DATABASE another_app;               -- should FAIL: no CREATE DATABASE privilege
What you just proved: the shop user can do exactly what the web application needs and nothing more. If the application is compromised, the attacker cannot drop tables, create users, or access other databases. This is the principle of least privilege in action.

Step 8 — Check the process list

sudo mariadb -e "SHOW PROCESSLIST;"

You will see your own queries and perhaps a Sleep connection from your earlier login. This is what an administrator looks at when the database is under load.

13.10 · Deep Lab — Full-Stack Integration

In this lab, we connect everything we have built across Phase 2. We will take the Flask app from Week 12, add a real database backend, and serve it through Nginx on a lab domain. When we are done, the whole stack — DNS, HTTP, MariaDB — will be running on one VM.

Step 1 — Install the Python MySQL connector

sudo apt install python3-mysql.connector -y

Ubuntu ships a package for mysql.connector. Alternatively, you can install it with pip in a virtual environment.

Step 2 — Write the Flask app

sudo tee /opt/myapp/app.py > /dev/null <<'EOF'
from flask import Flask, jsonify, request
import mysql.connector
from mysql.connector import pooling

app = Flask(__name__)

pool = pooling.MySQLConnectionPool(
    pool_name='mypool',
    pool_size=5,
    host='localhost',
    user='shop',
    password='a-strong-password',
    database='shop_app'
)

def db():
    return pool.get_connection()

@app.route('/')
def index():
    return '<h1>Shop API</h1><p>Try /customers</p>'

@app.route('/customers')
def list_customers():
    conn = db()
    cur = conn.cursor(dictionary=True)
    cur.execute('SELECT id, name, email, created_at FROM customers ORDER BY id')
    rows = cur.fetchall()
    cur.close()
    conn.close()
    return jsonify(rows)

@app.route('/customers/<int:cid>')
def show_customer(cid):
    conn = db()
    cur = conn.cursor(dictionary=True)
    cur.execute('SELECT id, name, email FROM customers WHERE id = %s', (cid,))
    row = cur.fetchone()
    cur.close()
    conn.close()
    if row is None:
        return jsonify({'error': 'customer not found'}), 404
    return jsonify(row)

@app.route('/customers', methods=['POST'])
def create_customer():
    data = request.get_json() or {}
    name = data.get('name')
    email = data.get('email')
    if not name or not email:
        return jsonify({'error': 'name and email are required'}), 400

    conn = db()
    cur = conn.cursor()
    try:
        cur.execute(
            'INSERT INTO customers (name, email) VALUES (%s, %s)',
            (name, email)
        )
        conn.commit()
        new_id = cur.lastrowid
    except mysql.connector.errors.IntegrityError:
        conn.rollback()
        cur.close()
        conn.close()
        return jsonify({'error': 'email already exists'}), 409
    finally:
        cur.close()
        conn.close()

    return jsonify({'id': new_id, 'name': name, 'email': email}), 201

@app.route('/health')
def health():
    # Verify the DB is reachable
    try:
        conn = db()
        cur = conn.cursor()
        cur.execute('SELECT 1')
        cur.fetchone()
        cur.close()
        conn.close()
        return 'OK', 200
    except Exception as e:
        return f'DB unreachable: {e}', 503

if __name__ == '__main__':
    app.run(host='127.0.0.1', port=5000)
EOF

Step 3 — Run the app

python3 /opt/myapp/app.py &

Step 4 — Test locally

curl http://127.0.0.1:5000/customers
curl http://127.0.0.1:5000/customers/1
curl -X POST http://127.0.0.1:5000/customers \
     -H "Content-Type: application/json" \
     -d '{"name":"Eve","email":"eve@example.com"}'

The first call returns the JSON array of customers from the database. The second returns one specific customer. The third inserts a new one and returns it with a 201 status code.

Step 5 — Put Nginx in front

Recall from Week 12 the reverse proxy config. We will create /etc/nginx/sites-available/shop.local: 

server {
    listen 80;
    server_name shop.local;

    location / {
        proxy_pass http://127.0.0.1:5000;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
sudo ln -s /etc/nginx/sites-available/shop.local \
           /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

Step 6 — Point DNS at it

From Week 11, our BIND9 server manages the lab.local zone. Edit the forward zone file and add: 

shop    IN  A   192.168.56.1

Increment the serial, run named-checkzone, reload BIND9. Now the name shop.lab.local resolves to our VM.

On the client, verify: 

dig shop.lab.local
curl http://shop.lab.local/customers

Step 7 — Test the full flow

From the client machine, create a customer through the stack: 

curl -X POST http://shop.lab.local/customers \
     -H "Content-Type: application/json" \
     -d '{"name":"Frank","email":"frank@example.com"}'

Then list them: 

curl http://shop.lab.local/customers

The new customer is there. And if you log into MariaDB, you can confirm the row is actually persisted: 

sudo mariadb shop_app -e "SELECT * FROM customers WHERE email='frank@example.com';"
What you just built: a complete three-tier web application. A client resolves a name via our own DNS server, HTTP requests are proxied by Nginx to a Flask backend, and the backend reads and writes persistent data in our own MariaDB instance. This is the exact architecture of thousands of real-world deployments.

Step 8 — Test crash behavior

Restart the database and see what happens: 

sudo systemctl restart mariadb
sleep 2
curl http://shop.lab.local/customers

The Flask app's connection pool may briefly fail, but after a moment it should reconnect and serve requests again. This is the value of connection pooling — the app recovers on its own without a restart.

Now stop the database and see the failure: 

sudo systemctl stop mariadb
curl -i http://shop.lab.local/customers

You will get a 500-level error, because the application cannot reach the database. The /health endpoint correctly reports the failure: 

curl http://shop.lab.local/health

This is exactly how a real system behaves. The health endpoint tells the load balancer that this instance is unhealthy, and traffic gets routed elsewhere — or, if there is no "elsewhere," the service is down.

Bring the database back up:

sudo systemctl start mariadb

Step 9 — Back up the database

mysqldump -u root -p shop_app > /tmp/shop_app_$(date +%F).sql
ls -lh /tmp/shop_app_*.sql

Open the file with less to see what a dump looks like. You will see the entire database recreated as SQL statements — CREATE TABLE, INSERT, ALTER — ready to be replayed on another server.

Restore it into a test database: 

mysql -u root -p -e "CREATE DATABASE shop_app_restore;"
mysql -u root -p shop_app_restore < /tmp/shop_app_*.sql
mysql -u root -p shop_app_restore -e "SELECT COUNT(*) FROM customers;"

The count should match the original. You have round-tripped a database through a backup and restore.

Step 10 — Clean up

mysql -u root -p -e "DROP DATABASE shop_app_restore;"
pkill -f /opt/myapp/app.py
sudo rm /etc/nginx/sites-enabled/shop.local
sudo systemctl reload nginx

Week 13 Summary

  • MariaDB is a community fork of MySQL. It is a relational database management system — the persistence layer of every realistic web stack.
  • The relational model organizes data into tables of rows and columns, related by primary and foreign keys. Queries are expressed declaratively in SQL.
  • ACID guarantees — atomicity, consistency, isolation, durability — are what databases provide that file systems do not.
  • Installation on Ubuntu is apt install mariadb-server. The service is managed by systemd like any other.
  • Securing the installation with mariadb-secure-installation removes anonymous users, disallows remote root, and removes the test database.
  • SQL is divided into DDL, DML, DCL, and TCL. The core commands you need are CREATE, INSERT, SELECT, UPDATE, DELETE, and GRANT.
  • MariaDB users are user@host pairs — the host is part of the identity. Grant privileges only for what an application actually needs, from the narrowest possible host.
  • Connecting from a web app uses a client library and parameterized queries. Never build SQL by string concatenation — that is SQL injection.
  • Backups use mysqldump for logical backups — a SQL text file that can be replayed. Automate them, test them, and store them off-server.
  • The full stack — DNS + Nginx + Flask + MariaDB — is a complete three-tier application, running entirely on VMs you built yourself.
