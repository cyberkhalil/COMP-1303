9.1 · The Linux Shell & Filesystem Hierarchy

Welcome to Phase 2. From this week onward, we stop talking about operating systems in the abstract and start working with a real Linux system every single day. The first tool you must master is the shell.

A shell is a command interpreter. It reads the commands you type, expands them, and asks the kernel to execute the resulting programs. The default shell on nearly every Linux distribution is bash — the Bourne-Again SHell. But other shells exist: zsh, fish, dash, and ksh.

Shell Typical use Notes
bashDefault on most Linux systemsPowerful, widely documented, POSIX-compatible with extensions
zshInteractive power usersBetter autocompletion, themes, plugins
fishFriendly interactive shellNot POSIX-compatible, but very user-friendly
dash/bin/sh on Debian/UbuntuMinimal, fast, used for scripts

The Filesystem Hierarchy Standard — FHS

Linux organizes everything into one single tree, starting at /. Unlike Windows, there are no drive letters. Every disk, partition, USB stick, and network share is mounted somewhere inside this one tree.

The Linux filesystem hierarchy. Every device, partition, and network share is mounted somewhere inside this single tree.

Essential navigation commands

pwd                 # print working directory
ls -la              # list all files, long format
cd /etc             # change to /etc
cd ..               # go up one directory
cd ~                # go to your home directory
cd -                # go back to previous directory
tree                # show directory tree (may need to install)
which bash          # show path of a command
type ls             # show how a command is interpreted
Absolute vs relative paths: an absolute path starts at / — for example /etc/hosts. A relative path starts from your current directory — for example hosts if you are already inside /etc. The shortcuts . and .. mean “this directory” and “parent directory”.

9.2 · Pipes, Redirection & Text Processing

The real power of the shell is not in running single commands — it is in combining commands into pipelines. Unix gives every program three standard streams:

Stream Descriptor Default
stdin0Keyboard input
stdout1Terminal screen
stderr2Terminal screen

Redirection operators

command > file        # write stdout to file (overwrite)
command >> file       # append stdout to file
command < file        # read stdin from file
command 2> file       # write stderr to file
command &> file       # write both stdout and stderr to file
command | other       # pipe stdout of command into other
command | tee file    # write to both stdout and file

Text processing tools

Tool Purpose Example
grepSearch for patternsgrep root /etc/passwd
sedStream editor — substitute textsed 's/old/new/g' file
awkField-based processingawk '{print $1}' file
cutExtract columnscut -d: -f1 /etc/passwd
sortSort linessort -n file
uniqRemove adjacent duplicatesuniq -c file
wcCount lines, words, byteswc -l file
head / tailFirst or last lineshead -20 file
The pipeline is the fundamental composition mechanism of Unix. Small tools, connected by pipes, solve complex problems.
Be careful with rm and redirection: command > file will overwrite file immediately, even if command later fails. If you want to avoid accidental data loss, use set -o noclobber or test commands interactively first.

9.3 · Users & Groups

Linux is a multi-user system by design. Every process runs as some user. Every file is owned by some user and some group. Understanding users and groups is essential for administration and security.

Where user information lives

File Contents
/etc/passwdUser accounts: username, UID, GID, home, shell
/etc/shadowEncrypted passwords and password aging
/etc/groupGroups and their members

Common user-management commands

sudo useradd -m -s /bin/bash alice
sudo passwd alice
sudo usermod -aG developers alice
sudo userdel -r alice

sudo groupadd developers
sudo groupdel developers

id alice
groups alice
whoami
who
w
UID 0 is root. The root user has UID 0 and bypasses most permission checks. System users usually have UIDs below 1000. Regular users start at 1000 on most distributions.

9.4 · File Permissions

Every file and directory has a set of permission bits — nine bits in total, split into three groups of three: owner, group, and others. 

$ ls -l notes.txt
-rw-r--r-- 1 alice developers 1024 Nov 12 10:22 notes.txt

 ^^^         owner  group     others
 |||
 ||+-- read for owner
 |+--- write for owner
 +---- no execute for owner

Numeric and symbolic modes

Value Permission Symbol
4readr
2writew
1executex
0none-
 
chmod 755 script.sh      # rwxr-xr-x
chmod 644 file.txt       # rw-r--r--
chmod u+x script.sh      # add execute for owner
chmod g-w file.txt       # remove write for group
chmod o=r file.txt       # set others to read only

chown alice file.txt
chown alice:developers file.txt
chgrp developers file.txt

umask                    # show current umask
umask 022                # default: new files 644, new dirs 755
The nine permission bits are always shown in the order owner, group, others.

9.5 · Special Permission Bits

Bit Effect on files Effect on directories
setuid Program runs with owner's UID, not caller's No effect on Linux
setgid Program runs with owner's GID New files inherit the directory's group
sticky Historically kept program in swap Only owner can delete or rename files 
chmod u+s /usr/bin/program       # set setuid bit
chmod g+s /srv/shared            # set setgid on directory
chmod +t /tmp                    # set sticky bit

ls -ld /tmp
# drwxrwxrwt 1 root root ... /tmp
#          ^ sticky bit shown as t
Security warning: setuid binaries are powerful and dangerous. A setuid root program can do anything root can do. Never set the setuid bit on a script or a program you did not write and audit yourself.

9.6 · su, sudo & Identity

su switches user. sudo runs a single command as another user — by default, root. Modern Linux systems strongly prefer sudo because it is auditable and granular. 

whoami                  # current user
id                      # UID, GID, groups
groups                  # groups of current user

su - alice              # switch to alice, load login environment
sudo command            # run command as root
sudo -i                 # start an interactive root shell
sudo -u alice command   # run command as alice

visudo                  # safely edit /etc/sudoers
Never edit /etc/sudoers directly. A syntax error can lock you out of sudo entirely. Always use visudo, which validates the file before saving.

9.7 · systemd Services

On modern Linux systems, systemd is the init system and service manager. It starts services at boot, manages their lifecycle, collects logs, and handles dependencies.

Command Purpose
systemctl status nginxShow current status of a service
sudo systemctl start nginxStart a service now
sudo systemctl stop nginxStop a service now
sudo systemctl restart nginxRestart a service
sudo systemctl enable nginxStart service at boot
sudo systemctl disable nginxDo not start at boot
systemctl list-units --type=serviceList all services
systemctl daemon-reloadReload unit files after editing

A minimal unit file

[Unit]
Description=My example service
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/my-service.sh
Restart=on-failure
User=nobody

[Install]
WantedBy=multi-user.target

Unit files live in /etc/systemd/system/ for custom services, or /lib/systemd/system/ for packages. After creating or editing a unit file, run sudo systemctl daemon-reload.

9.8 · journalctl — Reading the Logs

systemd collects logs from the kernel, services, and applications into a central journal. The journalctl command lets you query it. 

journalctl                     # all logs
journalctl -u nginx            # logs for one service
journalctl -f                  # follow new logs
journalctl -b                  # logs since last boot
journalctl --since "1 hour ago"
journalctl -p err              # only errors and worse
journalctl -u nginx -n 50      # last 50 lines for nginx
journalctl --disk-usage        # how much space the journal uses
sudo journalctl --vacuum-time=7d   # keep only 7 days
Debugging pattern: when a service fails, run systemctl status service first. It usually shows the last few log lines and the exit code. Then run journalctl -u service -n 100 for full context.

9.9 · Deep Lab — Multi-User Environment

In this lab, you will build a realistic multi-user environment with groups, users, passwords, and a shared directory with special permissions.

Step 1 — Create groups

sudo groupadd developers
sudo groupadd auditors
getent group developers
getent group auditors

Step 2 — Create users

sudo useradd -m -s /bin/bash alice
sudo useradd -m -s /bin/bash bob
sudo useradd -m -s /bin/bash carol

sudo passwd alice
sudo passwd bob
sudo passwd carol

sudo usermod -aG developers alice
sudo usermod -aG developers bob
sudo usermod -aG auditors carol

id alice
id bob
id carol

Step 3 — Create a shared directory

sudo mkdir -p /srv/shared
sudo chown root:developers /srv/shared
sudo chmod 2775 /srv/shared
ls -ld /srv/shared

The leading 2 in 2775 sets the setgid bit. Any file created inside /srv/shared will inherit the developers group, not the creator's primary group.

Step 4 — Test with different users

su - alice
touch /srv/shared/alice-file.txt
ls -l /srv/shared/alice-file.txt
exit

su - bob
echo "hello from bob" > /srv/shared/bob-file.txt
ls -l /srv/shared/bob-file.txt
exit

su - carol
touch /srv/shared/carol-file.txt
# This should fail with permission denied, because carol is not in developers.
exit

Step 5 — Verify sticky bit on /tmp

ls -ld /tmp
# drwxrwxrwt ... /tmp
# The t at the end means sticky bit is set.

9.10 · Deep Lab — Create a systemd Service

In this lab, you will create a simple systemd service that runs a script and writes to the journal.

Step 1 — Create the script

sudo nano /usr/local/bin/hello-service.sh
#!/bin/bash
while true; do
    echo "Hello from my service at $(date)"
    sleep 10
done
sudo chmod +x /usr/local/bin/hello-service.sh

Step 2 — Create the unit file

sudo nano /etc/systemd/system/hello.service
[Unit]
Description=Hello demo service
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/hello-service.sh
Restart=on-failure
User=nobody

[Install]
WantedBy=multi-user.target

Step 3 — Enable and start

sudo systemctl daemon-reload
sudo systemctl enable hello.service
sudo systemctl start hello.service
systemctl status hello.service

Step 4 — Read the journal

journalctl -u hello.service -f
# Press Ctrl+C to stop following.

journalctl -u hello.service -n 20
journalctl -u hello.service --since "5 minutes ago"

Step 5 — Clean up

sudo systemctl stop hello.service
sudo systemctl disable hello.service
sudo rm /etc/systemd/system/hello.service
sudo rm /usr/local/bin/hello-service.sh
sudo systemctl daemon-reload

Week 9 Summary

  • The shell interprets your commands. bash is the standard on most Linux systems.
  • The FHS organizes everything into one tree under /. Key directories: /etc, /home, /var, /usr, /tmp, /proc, /sys.
  • Pipes and redirection connect commands: |, >, >>, 2>, &>, tee.
  • Text tools — grep, sed, awk, cut, sort, uniq, wc — are the workhorses of Linux administration.
  • Users and groups are defined in /etc/passwd, /etc/shadow, and /etc/group. Commands: useradd, usermod, passwd, groupadd.
  • Permissions use rwx bits for owner, group, and others. chmod, chown, chgrp, and umask control them.
  • Special bits: setuid, setgid, sticky. Use setgid on shared directories so new files inherit the group.
  • sudo is preferred over su. Edit /etc/sudoers only with visudo.
  • systemd manages services with systemctl. Unit files live in /etc/systemd/system/.
  • journalctl reads systemd logs. Use -u, -f, -b, --since, and -p err.
