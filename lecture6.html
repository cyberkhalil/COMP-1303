6.1 · What is a Deadlock?

In Week 4 we built up a stack of synchronization primitives — mutexes, semaphores, and condition variables — and we used them to solve the correctness problems that concurrency creates. We also closed that week with a warning: deadlocks are the classic failure mode of locking. Now it is time to take that warning seriously.

A deadlock is a situation in which a set of threads are all waiting for events that can only be caused by another thread in the same set. Because every thread in the set is waiting, none of them can proceed. Nobody can make the first move. The set is stuck forever.

The defining feature of a deadlock: it is not slow progress, it is not starvation, and it is not a livelock. It is a permanent standstill. Nothing that the kernel or the applications do will break it without external intervention. The only way forward is if someone kills a thread — from the outside — or the whole machine reboots.

The simplest example: two threads, two locks

Imagine two threads, A and B, and two mutexes, L1 and L2. Both threads need both locks to do their work. Their code looks like this: 

/* Thread A */                    /* Thread B */
pthread_mutex_lock(&L1);          pthread_mutex_lock(&L2);
   /* work with resource 1 */        /* work with resource 2 */
pthread_mutex_lock(&L2);          pthread_mutex_lock(&L1);
   /* work with resource 2 */        /* work with resource 1 */
pthread_mutex_unlock(&L2);        pthread_mutex_unlock(&L1);
pthread_mutex_unlock(&L1);        pthread_mutex_unlock(&L2);

Notice the danger: Thread A acquires L1 then L2. Thread B acquires L2 then L1. This is the classic opposite order — the single most common way to create a deadlock in real code. Now watch what happens if the scheduler interleaves them just one way:

Two threads each hold one lock and wait for the other — the circular wait is complete, and neither can proceed.

The sequence is:

  1. Thread A executes lock(L1) and succeeds. It now holds L1.
  2. Thread B executes lock(L2) and succeeds. It now holds L2.
  3. Thread A tries lock(L2). It is held by B, so A blocks.
  4. Thread B tries lock(L1). It is held by A, so B blocks.
  5. Both threads are blocked. Neither will ever release its first lock, because they are waiting for the second lock, which cannot be released by the other because it is waiting for the first lock.
The core insight: a deadlock requires a cycle in the "who waits for what" graph. Two threads holding lock A and waiting for B, and holding B and waiting for A, form exactly such a cycle — a 2-cycle. Bigger cycles (three threads, four locks) are just harder to see, not harder to fall into.

Deadlock vs livelock vs starvation

Before we go further, let us distinguish deadlock from two other failure modes that are often confused with it:

Failure What's happening Can it resolve itself?
Deadlock Threads are blocked forever, each waiting for another. Nobody is executing. No. External intervention required.
Livelock Threads are actively running — performing actions — but those actions repeatedly undo each other's work. Similar to two people stepping side-to-side trying to pass on a sidewalk. In principle yes, if timing changes. In practice, no.
Starvation One thread is ready to run but never gets the resource it needs, because others keep winning it. Yes, eventually — if priority or scheduling changes.
Why the distinction matters: the fixes are completely different. Livelock is fixed by adding randomization or backoff. Starvation is fixed by aging (making old threads more important). Deadlock requires prevention, avoidance, or detection — a structural change to how resources are acquired.

6.2 · Coffman's Four Necessary Conditions

In 1971, Edward Coffman and his colleagues published a landmark paper that gave the operating systems world a precise characterization of when a deadlock can occur. Their result is elegant and widely used — and it appears on every operating systems exam in existence.

Coffman's theorem states: a deadlock can occur if and only if all four of the following conditions hold simultaneously. If any one of them is broken, deadlock becomes impossible.

Condition Meaning How to break it
Mutual exclusion At least one resource is held in a non-sharable mode. Only one thread can use it at a time. Make the resource sharable, or virtualize it.
Hold and wait A thread holding at least one resource is waiting to acquire additional resources held by other threads. Require threads to request all resources at once, up front.
No preemption Resources cannot be forcibly taken from a thread that holds them. A resource is released only when the holder voluntarily releases it. Allow the kernel to preempt and forcibly take resources.
Circular wait There exists a cycle in the "waits-for" graph: T1 waits for a resource held by T2, T2 waits for a resource held by T3, …, Tn waits for a resource held by T1. Enforce a global lock ordering, so no cycle can form.
The practical significance: the first three conditions are usually inherent in the nature of the resources we're using. Two threads really cannot write to the same memory simultaneously (mutual exclusion). A thread that already holds a lock really does need to wait for another one (hold and wait). File descriptors are not something you can take away from a running process (no preemption). The only condition we can realistically break in a general-purpose system is the fourth one — circular wait. And that is exactly what lock ordering fixes.
Imagine this in the two-lock example above: if every thread in the system agreed to always acquire L1 before L2, and there were no exceptions, then Thread B's reverse ordering would be impossible. The cycle could not form. That is the essence of lock ordering — the single most powerful technique in the deadlock prevention toolbox, and one you will use constantly as a systems programmer.

6.3 · Resource Allocation Graphs

To reason about deadlocks precisely, we need a visual tool. The Resource Allocation Graph (RAG) is a directed graph that shows which threads hold which resources, and which threads are waiting for which resources.

The two types of nodes

  • Thread nodes (or process nodes): drawn as circles, labeled T1, T2, or P1, P2.
  • Resource nodes: drawn as rectangles, labeled R1, R2. A resource node may contain small dots — one per instance of that resource. For example, a printer resource with two physical printers has two dots.

The two types of edges

  • Request edge — Tᵢ → Rⱼ: a directed edge from a thread to a resource. It means the thread is currently waiting for an instance of that resource.
  • Assignment edge — Rⱼ → Tᵢ: a directed edge from a resource (specifically, from one of its instance-dots) to a thread. It means one instance of that resource is currently held by that thread.
Resource Allocation Graph: circles are threads, rectangles are resources. Solid arrows are assignments (Held), dashed arrows are requests (Waiting). A cycle in this graph means deadlock.

The fundamental theorem of RAG cycles

The RAG deadlock theorem:
  • If the RAG contains no cycle, no thread in the system is deadlocked.
  • If the RAG contains a cycle, and each resource in the cycle has only a single instance, then a deadlock definitely exists.
  • If the RAG contains a cycle, and some resources in the cycle have multiple instances, a deadlock may or may not exist — you need to look at the actual resource allocation, not just the graph.

This theorem is important enough to remember in those three precise forms. It is the basis of every deadlock detection algorithm in every operating system, and it directly shapes how we detect deadlocks in user space.

6.4 · Deadlock Prevention

The most direct approach is prevention: enforce a rule at design time such that at least one of Coffman's four conditions can never hold. Since we cannot usually change whether resources have mutual exclusion, hold-and-wait, or preemption, the practical target is almost always the fourth condition — circular wait.

Breaking circular wait — the lock-ordering discipline

The idea is simple: assign each resource a global ordering — say, a number. Then require that every thread acquires resources in strictly increasing order. With this rule, no cycle can ever form, because any thread's "waits for" chain would have to descend in a monotone sequence, and monotone sequences cannot contain a cycle. 

/* A simple lock-ordering discipline */
#define LOCK_ALPHA  1
#define LOCK_BETA   2
#define LOCK_GAMMA  3

/* Always acquire in the order ALPHA → BETA → GAMMA */
void work_with_all_three(void) {
    pthread_mutex_lock(&lock_alpha);
    pthread_mutex_lock(&lock_beta);
    pthread_mutex_lock(&lock_gamma);

    /* ... do the work ... */

    pthread_mutex_unlock(&lock_gamma);
    pthread_mutex_unlock(&lock_beta);
    pthread_mutex_unlock(&lock_alpha);
}

Notice that we also release the locks in reverse order — this is not strictly required to prevent deadlock, but it is a strong convention that makes the code easier to reason about and to maintain.

The ordering rule, precisely stated: if a thread must acquire locks A and B, and A has a smaller order number than B, then A must be acquired first. Whenever possible, acquire all the locks you need at the beginning of an operation, in one consistent sweep.

The other three conditions — briefly

Breaking mutual exclusion

Very hard. Some resources are inherently non-sharable — a printer cannot print two documents at once, a file descriptor is not something two processes can share cleanly. Where possible, we virtualize — spooling printers, ring buffers for data — but not all cases are feasible.

Breaking hold and wait

Require threads to request all their resources up front, before acquiring any. This works but is rarely practical — it forces threads to hold resources they don't yet need, reducing utilization and creating new starvation risks.

Breaking no preemption

Allow the OS to forcibly revoke a resource from a running thread. This works in some systems — a database can abort and roll back a transaction — but for memory and locks in general-purpose systems it is not feasible. It is one of the reasons database engines are so careful about deadlock handling.

Summary of prevention: in practice we almost always prevent deadlocks by preventing circular wait, through lock ordering. The other three conditions are usually fixed by the nature of the resource and cannot be changed.

6.5 · Deadlock Avoidance — Banker's Algorithm

Prevention is a design-time commitment. Avoidance is a runtime decision — the OS decides, at each resource-request moment, whether granting the request could lead to deadlock. If it could, the request is denied (the thread is told to wait); if it could not, the request is granted.

To do this, the OS must know in advance the maximum resources each thread will need. If it knows that, it can simulate the future and check whether the current state is safe.

Safe state — the key concept

A system is in a safe state if there exists at least one order in which all current threads can run to completion without ever exceeding the available resources. That order is called a safe sequence. If the system is in a safe state, no deadlock can occur — no matter how the threads interleave their future requests.

The avoidance contract: before granting a resource request, the OS checks whether the resulting state would still be safe. If it would, the OS grants. If it would not, the OS blocks the requesting thread and makes it wait, even though resources are physically available. Resource utilization suffers; deadlock becomes impossible.

The Banker's Algorithm

The Banker's Algorithm — named after the analogy with a banker who must keep enough cash on hand to satisfy all current depositors — is the classic avoidance algorithm. Introduced by Dijkstra in 1965, it generalizes easily to any number of threads and resource types.

The data structures

For a system with n threads and m resource types:

  • Available[m]: how many instances of each resource are currently unallocated.
  • Max[n][m]: the maximum number of each resource that each thread may request over its entire lifetime.
  • Allocation[n][m]: how many instances of each resource are currently held by each thread.
  • Need[n][m]: how many additional instances each thread still might need. Need[i][j] = Max[i][j] − Allocation[i][j].

The safety-check procedure

To determine whether the current state is safe, the algorithm tries to find a safe sequence:

  1. Let Work[m] be a copy of Available. Let Finish[n] be all false.
  2. Find a thread i such that Finish[i] == false and Need[i][*] ≤ Work[*] for every resource type. That is, thread i could finish using only the currently available resources.
  3. If such a thread exists: pretend it runs to completion and releases everything it holds. So set Work[*] += Allocation[i][*] and Finish[i] = true. Go back to step 2.
  4. If no such thread exists, check whether all threads are Finished. If yes, the state is safe, and the sequence of threads found in step 2 is a valid safe sequence. If no, the state is unsafe.

A small worked example

Consider a system with 3 resource types — A, B, and C — where A has 10 instances, B has 5, and C has 7. Five threads are running, and the current state is:

Thread Allocation (A, B, C) Max (A, B, C) Need = Max − Allocation
P00, 1, 07, 5, 37, 4, 3
P12, 0, 03, 2, 21, 2, 2
P23, 0, 29, 0, 26, 0, 0
P32, 1, 12, 2, 20, 1, 1
P40, 0, 24, 3, 34, 3, 1

Current allocation totals: A = 7, B = 2, C = 5. Since totals are A = 10, B = 5, C = 7, the currently available resources are Available = (3, 3, 2).

Now run the safety check. Initial Work = (3, 3, 2):

  • P0's Need is (7, 4, 3) — too large. Skip.
  • P1's Need is (1, 2, 2) — fits Work (3, 3, 2). Run P1. Work becomes (3+2, 3+0, 2+0) = (5, 3, 2).
  • P2's Need is (6, 0, 0) — too large. Skip.
  • P3's Need is (0, 1, 1) — fits Work (5, 3, 2). Run P3. Work becomes (5+2, 3+1, 2+1) = (7, 4, 3).
  • P4's Need is (4, 3, 1) — fits Work (7, 4, 3). Run P4. Work becomes (7+0, 4+0, 3+2) = (7, 4, 5).
  • P0's Need is (7, 4, 3) — fits Work (7, 4, 5). Run P0. Work becomes (7+0, 4+1, 5+0) = (7, 5, 5).
  • P2's Need is (6, 0, 0) — fits Work (7, 5, 5). Run P2. Work becomes (7+3, 5+0, 5+2) = (10, 5, 7).

All threads finished. So the state is safe, with a safe sequence (P1, P3, P4, P0, P2). Because the state is safe, we know no deadlock can occur from here, even if the threads make their future requests in the worst possible order.

Now suppose P1 requests one additional instance of A and two of C, i.e. request = (1, 0, 2). Is this grantable?

  • First, verify request ≤ Need[P1]: (1, 0, 2) ≤ (1, 2, 2). Valid.
  • Verify request ≤ Available: (1, 0, 2) ≤ (3, 3, 2). Valid.
  • Pretend the grant: Available = (2, 3, 0), Allocation[P1] = (3, 0, 2), Need[P1] = (0, 2, 0).
  • Run the safety check on this new state. Work = (2, 3, 0). P0's Need (7, 4, 3) — too large. P1's Need (0, 2, 0) — fits! Run P1. Work becomes (2+3, 3+0, 0+2) = (5, 3, 2). P3's Need (0, 1, 1) — fits. Run P3. Work = (7, 4, 3). P4's Need (4, 3, 1) — fits. Run P4. Work = (7, 4, 5). P0's Need (7, 4, 3) — fits. Run P0. Work = (7, 5, 5). P2's Need (6, 0, 0) — fits. Run P2. Work = (10, 5, 7).
  • All threads finish. The state is safe — the request is granted.
What Banker's Algorithm guarantees: if every thread declares its maximum resource needs up front, and the OS only grants requests that leave the system in a safe state, then deadlock is impossible. This is a provable theorem — one of the most elegant correctness results in operating systems.

Why isn't Banker's Algorithm used in real operating systems?

In theory, Banker's Algorithm is a beautiful solution. In practice, it has never been used in a general-purpose OS, for four reasons:

  • Threads must declare maximum needs in advance. Real programs rarely know this. A web server does not know how many file descriptors it will ultimately open. A compiler does not know how much memory it will eventually allocate.
  • Threads are not independent. They can synchronize via IPC, wait on each other, and spawn new threads — all of which break the simple model.
  • Resource-use patterns change dynamically. The maximum declared at start may not reflect reality later.
  • It is conservative. The algorithm denies requests that would still be fine in practice. This hurts utilization and is often considered unacceptable in production systems.

Banker's Algorithm lives on primarily in its pedagogical value — it teaches us to reason about "safe states" — and in specialized real-time systems where resource needs are, by design, known and bounded.

6.6 · Deadlock Detection & Recovery

Prevention and avoidance both try to prevent deadlocks from occurring. Detection accepts that they will occur, and adds two mechanisms: one to notice them, and one to recover from them.

Detection — using the wait-for graph

For single-instance resources, the RAG can be simplified into a wait-for graph: nodes are threads only, and a directed edge Tᵢ → Tⱼ means "thread Tᵢ is waiting for a resource held by thread Tⱼ." A cycle in this graph is a deadlock, period. Detection becomes cycle-finding, which is a well-studied problem in graph theory — O(n + e) with an appropriate algorithm.

For multi-instance resources, we run a variant of Banker's safety check — this time without needing the maximum-needs table. If the algorithm cannot find a sequence in which all threads finish, then some subset is deadlocked.

When to run detection

Periodically

Run the detection algorithm every second, or every minute. Simple and predictable, but you might notice the deadlock late. This is common in batch systems.

On demand

Run it when CPU utilization drops below a threshold, or when a timeout fires. Detects deadlocks quickly at the cost of more frequent checking. Common in interactive systems.

Recovery — what to do once you know

Once a deadlock is detected, the OS must break it. There are three main strategies. In order of increasing severity:

  1. Thread termination. Kill one thread in the cycle. Its resources are released, and the remaining threads can proceed. The cost is that the killed thread loses all its work. Some systems abort the entire thread family; others abort just one.
  2. Resource preemption. Take a resource away from one thread and give it to another. Only possible when the resource type supports preemption. The victim thread is usually either rolled back to a previous checkpoint, or terminated as a side effect.
  3. Rollback. If the system has been taking periodic checkpoints of thread state, we can roll back to a point before one of the threads had acquired a particular resource. This is common in database systems, which combine detection with transactions that can be cleanly aborted and retried.
The victim selection problem: when we have to kill or preempt, who should we choose? Ideally a thread that will cost the least to restart, that has done the least work so far, or that has held the most resources. Getting this choice wrong — repeatedly killing the wrong thread — leads to a new failure mode called livelock by repeated preemption. Real systems typically include the number of times a thread has been rolled back in the victim-selection heuristic.

Detection in practice — database systems

Databases are one of the few places where real deadlock detection is universally used. Every major database — PostgreSQL, MySQL, Oracle, SQL Server — has a background deadlock detector that:

  • Watches the transaction table for cyclic waits.
  • Runs every few hundred milliseconds.
  • When it finds a cycle, it aborts one transaction — typically the one that has done the least work — with a DEADLOCK DETECTED error.
  • The aborted transaction's client gets the error and is expected to retry.

This pattern — "abort and retry" — is so common in database systems that application developers are taught to write loops around their transactions to handle it gracefully. It is the practical alternative to prevention in an environment where prevention is impractical.

6.7 · The Dining Philosophers, Solved

In Week 4, we met the Dining Philosophers — five philosophers, five forks, each philosopher needs two forks to eat — as a preview of the deadlock problem. Now we have all the tools to solve it properly.

The five solutions

Each of these breaks one of Coffman's conditions, or uses a structural trick that makes deadlock impossible.

Solution 1 — Semaphore-based limit on seated philosophers

Allow at most N − 1 philosophers to try to eat at the same time. That is, use a counting semaphore initialized to 4 for 5 philosophers. Each philosopher tries to sem_wait the semaphore before grabbing forks, and sem_posts it after releasing them. With only 4 philosophers competing for 5 forks, at least one will always have access to both forks. 

#define N 5
sem_t seats;

void *philosopher(void *arg) {
    while (1) {
        think();
        sem_wait(&seats);              /* at most 4 at the table */
        take_fork(left);
        take_fork(right);
        eat();
        put_fork(right);
        put_fork(left);
        sem_post(&seats);
    }
}

Solution 2 — Asymmetric behavior

Break the symmetry between philosophers. Four of them pick up their left fork first and then their right; one picks up their right fork first and then their left. Now the circular wait cannot form, because one participant in each possible cycle uses the opposite order. This is the seed of the lock-ordering idea in disguise.

Solution 3 — The waiter (arbiter) approach

Add a single arbiter — the waiter — whose permission must be obtained before picking up forks. Only one philosopher can be picking up forks at any moment. This eliminates the circular wait by adding a global serialization point, at the cost of some parallelism.

Solution 4 — Atomic pickup of both forks

Combine the two forks into one resource that can be acquired atomically — a single mutex-protected "both forks" resource. A philosopher either has both forks or has neither. This breaks hold-and-wait, and it also breaks the circular wait, because there is no partial state to get stuck in.

Solution 5 — Chandy–Misra algorithm

A distributed deadlock detection and resolution algorithm that lets each philosopher detect and resolve deadlocks dynamically. Only needed in truly distributed settings, but it is the general solution to the class of problems that Dining Philosophers represents.

Solution Condition broken / trick used Trade-offs
Seat limit (N−1) Breaks circular wait structurally — one seat reserved. Simple. Slight reduction in parallelism.
Asymmetric Breaks circular wait — one philosopher uses reverse order. Very simple in code. Slightly uneven behavior.
Waiter (arbiter) Adds global serialization point. Clean, easy to reason about. Reduces concurrency.
Atomic both-fork Breaks hold-and-wait — never hold one and wait for the other. Requires merging resources. May not fit all cases.
Chandy–Misra Detects and resolves deadlocks after the fact. Full generalization. Complex to implement.
Which should you pick in practice? For most real code, the answer is asymmetric lock ordering. If you cannot pick a global order — for example because the lock acquisition is inside a library you do not control — the arbiter pattern is the next simplest choice. The seat-limit solution and atomic-both come after.

6.8 · Touch Lab — Banker's Algorithm in Python

Reading Banker's Algorithm is one thing; running it on real inputs and watching it make decisions is another. In this lab, we will build a small Banker's Algorithm simulator in Python and use it to evaluate fourteen predefined system states.

Step 1 — Create the script

$ nano banker.py

Paste the following code:

#!/usr/bin/env python3
"""
Banker's Algorithm — safe state checker.

Reads allocation, max, and available tables, then determines
whether the system is in a safe state and prints a safe sequence.
"""

import sys


def is_safe(allocation, max_need, available, n, m):
    """
    Return (True, safe_sequence) if the system is safe,
    or (False, None) otherwise.
    """
    need = [[max_need[i][j] - allocation[i][j] for j in range(m)]
            for i in range(n)]

    finish = [False] * n
    work = available[:]
    sequence = []

    while len(sequence) < n:
        found = False
        for i in range(n):
            if finish[i]:
                continue
            if all(need[i][j] <= work[j] for j in range(m)):
                # Thread i can run to completion
                for j in range(m):
                    work[j] += allocation[i][j]
                finish[i] = True
                sequence.append(i)
                found = True
                break

        if not found:
            # No progress possible
            return False, None

    return True, sequence


def main():
    # 5 threads, 3 resource types (A, B, C)
    n = 5
    m = 3

    # Total instances of each resource type
    total = [10, 5, 7]

    # Allocation table
    allocation = [
        [0, 1, 0],   # P0
        [2, 0, 0],   # P1
        [3, 0, 2],   # P2
        [2, 1, 1],   # P3
        [0, 0, 2],   # P4
    ]

    # Max need table
    max_need = [
        [7, 5, 3],   # P0
        [3, 2, 2],   # P1
        [9, 0, 2],   # P2
        [2, 2, 2],   # P3
        [4, 3, 3],   # P4
    ]

    # Compute Available as total - sum(Allocation)
    used = [sum(allocation[i][j] for i in range(n)) for j in range(m)]
    available = [total[j] - used[j] for j in range(m)]

    print("Banker's Algorithm — safety check")
    print("=================================")
    print(f"Total      : {total}")
    print(f"Used       : {used}")
    print(f"Available  : {available}")
    print()

    safe, sequence = is_safe(allocation, max_need, available, n, m)

    if safe:
        print("SAFE STATE")
        print(f"Safe sequence: {['P' + str(i) for i in sequence]}")
    else:
        print("UNSAFE STATE — deadlock may occur")
        return 1

    return 0


if __name__ == "__main__":
    sys.exit(main())

Step 2 — Run it

$ python3 banker.py

=================================

Used       : [7, 2, 5]
Available  : [3, 3, 2]

SAFE STATE

The output confirms what we computed by hand — the state is safe, and P1 → P3 → P4 → P0 → P2 is one valid safe sequence.

Now modify the script: change max_need[P0] from [7, 5, 3] to [8, 5, 3] — that is, P0 may need one additional instance of A. P0's Need becomes (8, 4, 3), which exceeds the total A = 10 even in the best case; the total demand exceeds availability.

=================================

Used       : [7, 2, 5]
Available  : [3, 3, 2]

Step 4 — Test a resource request

A more realistic use: given a current safe state, evaluate whether a specific request can be granted. Add this function to the script and call it: 

def try_request(allocation, max_need, available, n, m, i, request):
    """
    Test whether thread `i` can be granted `request`.
    Return (True, new_state) if the request is safe, else (False, None).
    """
    # Check request <= need
    need_i = [max_need[i][j] - allocation[i][j] for j in range(m)]
    if any(request[j] > need_i[j] for j in range(m)):
        print(f"Request exceeds declared max for P{i}")
        return False, None

    # Check request <= available
    if any(request[j] > available[j] for j in range(m)):
        print(f"Request exceeds currently available resources")
        return False, None

    # Pretend to grant
    new_alloc = [row[:] for row in allocation]
    new_avail = available[:]
    for j in range(m):
        new_alloc[i][j] += request[j]
        new_avail[j]   -= request[j]

    safe, seq = is_safe(new_alloc, max_need, new_avail, n, m)
    if safe:
        return True, (new_alloc, new_avail, seq)
    return False, None

Test it with try_request(..., i=1, request=[1, 0, 2]) — asking P1 for one A and two C. The result is a safe state with new sequence P1 → P3 → P4 → P0 → P2, so the request would be granted.

What this exercise teaches: the difference between a safe state and an unsafe state is a genuine notion, not a heuristic. By running the safety check repeatedly on the same data, you see it as a precise predicate, not as ambiguous advice.

Step 5 — Experiment on your own

  1. Change the total resources to [10, 5, 6] — one instance of C removed. Is the state still safe?
  2. Change the number of threads from 5 to 7 and add two more. How does that affect the safety outcome?
  3. Add a small print() statement inside the safety check's while loop that shows Work, Need, and Finish at each step. Watch the algorithm iterating through candidate threads.
  4. Make the workloads asymmetric — add a thread whose Need is enormous but whose Allocation is small. Observe how the safety check reacts.

6.9 · Touch Lab — Diagnosing a Deadlock

Banker's Algorithm teaches us the theory. Now let's see a real deadlock in the wild — a C program that deliberately deadlocks, and the tools we use to find and diagnose it.

Step 1 — A program that deadlocks on purpose

$ nano deadlock.c

Paste the following code:

#include <stdio.h>
#include <pthread.h>
#include <unistd.h>

static pthread_mutex_t lock_a = PTHREAD_MUTEX_INITIALIZER;
static pthread_mutex_t lock_b = PTHREAD_MUTEX_INITIALIZER;

void *thread_a(void *arg) {
    printf("[A] trying lock_a\n");
    pthread_mutex_lock(&lock_a);
    printf("[A] holding lock_a\n");

    sleep(1);

    printf("[A] trying lock_b\n");
    pthread_mutex_lock(&lock_b);

    printf("[A] holding both — never reaches here\n");
    pthread_mutex_unlock(&lock_b);
    pthread_mutex_unlock(&lock_a);
    return NULL;
}

void *thread_b(void *arg) {
    printf("[B] trying lock_b\n");
    pthread_mutex_lock(&lock_b);
    printf("[B] holding lock_b\n");

    sleep(1);

    printf("[B] trying lock_a\n");
    pthread_mutex_lock(&lock_a);

    printf("[B] holding both — never reaches here\n");
    pthread_mutex_unlock(&lock_a);
    pthread_mutex_unlock(&lock_b);
    return NULL;
}

int main(void) {
    pthread_t ta, tb;

    pthread_create(&ta, NULL, thread_a, NULL);
    pthread_create(&tb, NULL, thread_b, NULL);

    pthread_join(ta, NULL);
    pthread_join(tb, NULL);

    printf("Never prints — deadlock occurred\n");
    return 0;
}

Step 2 — Compile and run

$ gcc -Wall -pthread -o deadlock deadlock.c
$ ./deadlock
[A] trying lock_a
[A] holding lock_a
[B] trying lock_b
[B] holding lock_b
[A] trying lock_b
[B] trying lock_a
^C

The program prints both threads' first two lines, then hangs. Both threads have acquired one lock and are waiting for the other. The deadlock is visible — but only because we carefully designed the program to hang. In real code, you would see the freeze and know something is wrong, but not know what.

Step 3 — Diagnosing with gdb

Run the program again in the background, then use gdb to inspect it: 

$ ./deadlock &
[1] 6120
... hang ...
$ gdb -p 6120
(gdb) info threads
  Id   Target Id         Frame
* 1    Thread 0x7f...     __lll_lock_wait () at lowlevellock.S:135
  2    Thread 0x7f...     __lll_lock_wait () at lowlevellock.S:135

(gdb) thread apply all bt

Thread 2 (Thread 0x7f...):
#0  __lll_lock_wait () at lowlevellock.S:135
#1  __GI___pthread_mutex_lock (mutex=0x...<lock_b>) at pthread_mutex_lock.c:80
#2  thread_b (...) at deadlock.c:33
#3  start_thread (...)

Thread 1 (Thread 0x7f...):
#0  __lll_lock_wait () at lowlevellock.S:135
#1  __GI___pthread_mutex_lock (mutex=0x...<lock_a>) at pthread_mutex_lock.c:80
#2  thread_a (...) at deadlock.c:19
#3  start_thread (...)

(gdb) quit

Read that output carefully. This is the smoking gun:

  • Thread 1 is blocked in pthread_mutex_lock, waiting for a mutex whose address matches lock_a. The backtrace shows it was called from deadlock.c:19 — which is inside thread_a, at the line pthread_mutex_lock(&lock_b). So thread_a (originally holding lock_a) is now waiting for lock_b.
  • Thread 2 is blocked for a mutex at deadlock.c:33 — inside thread_b, at the line pthread_mutex_lock(&lock_a). So thread_b (holding lock_b) is now waiting for lock_a.

Thread 1 holds lock_a and waits for lock_b. Thread 2 holds lock_b and waits for lock_a. The cycle is complete. That is a textbook deadlock, and gdb has shown you the exact locations.

The diagnostic pattern: when a program hangs, run info threads, then thread apply all bt. If two or more threads are stuck in pthread_mutex_lock with mutex addresses that match each other's backtraces, you have a deadlock. This technique catches the vast majority of real-world cases.

Step 4 — pstack as an alternative

If you don't want to attach a full debugger, pstack prints a stack trace of every thread of a running process in one command. It is often installed as a wrapper for gdb, and it is what many sysadmins actually use day-to-day: 

$ pstack 6120
Thread 2 (Thread 0x7f...):
#0  __lll_lock_wait () at lowlevel...
#1  __GI___pthread_mutex_lock (...)
#2  thread_b (...) at deadlock.c:33
...

Thread 1 (Thread 0x7f...):
#0  __lll_lock_wait () at lowlevel...
#1  __GI___pthread_mutex_lock (...)
#2  thread_a (...) at deadlock.c:19
...

pstack gives you the same information as thread apply all bt, in one short command. It is your first tool to reach for when a multi-threaded process hangs.

Step 5 — Clean up

$ kill %1
[1]+  Terminated   ./deadlock

A deadlocked process does not respond to SIGTERM in some cases — the signal cannot be delivered to a thread that is blocked in pthread_mutex_lock if the mutex is in an uninterruptible state. If kill %1 does not work, use kill -9 %1 from a shell of any priority, or kill the parent shell.

Why this matters in production: the technique above works after the fact. It finds a deadlock that has already happened. The goal is to write code that cannot deadlock in the first place — using lock ordering, using timeouts (see pthread_mutex_timedlock), or using lock-free designs where feasible. Detection is a fallback, not a strategy.

Step 6 — Reproducing the fix

The fix is trivial. Change thread_b to acquire lock_a first, then lock_b: 

void *thread_b(void *arg) {
    printf("[B] trying lock_a\n");
    pthread_mutex_lock(&lock_a);   /* was lock_b */
    printf("[B] holding lock_a\n");

    sleep(1);

    printf("[B] trying lock_b\n");
    pthread_mutex_lock(&lock_b);   /* was lock_a */

    /* ... */
    pthread_mutex_unlock(&lock_b);
    pthread_mutex_unlock(&lock_a);
    return NULL;
}

Recompile and run a dozen times. The program terminates cleanly every time. Both threads now acquire the locks in the same global order — lock_a then lock_b — so no cycle can form. This is the lock-ordering discipline from section 6.4, applied to a real example.

The lesson: one line changed in thread_b, and the situation went from permanent freeze to guaranteed correctness. That is the power of the lock-ordering rule — it is small, precise, and universally effective for this class of bug.

Week 6 Summary

  • Deadlock: a set of threads, each waiting for an event that only another thread in the set can cause. A permanent standstill — no self-recovery possible.
  • Distinguish from: livelock (threads actively doing useless work), and starvation (one thread never getting its turn despite others making progress).
  • Coffman's four conditions: mutual exclusion, hold and wait, no preemption, circular wait. All four required for deadlock.
  • Prevention: break at least one condition at design time. In practice we break circular wait, using lock ordering — the single most important technique in the deadlock arsenal.
  • Avoidance — Banker's Algorithm: threads declare max needs; the OS grants only requests that leave the system in a safe state. Provably correct, but not used in practice.
  • Detection: build a wait-for graph (single-instance) or run a variant of safety checking (multi-instance). Recovery by terminating or preempting a thread in the cycle.
  • Dining Philosophers: the classic teaching problem. Five solutions exist, of which asymmetric lock ordering and the seat-limit approach are the most practical.
  • Diagnostic tools: gdb's info threads and thread apply all bt; the simpler pstack. Together they will let you find and fix real deadlocks in minutes, not hours.
