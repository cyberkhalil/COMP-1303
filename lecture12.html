12.1 · What is HTTP?

Last week we built a DNS server. We taught it to translate names into IP addresses, and we watched the system answer queries authoritatively for our own lab.local zone. That was the first piece of internet infrastructure we built from scratch. But DNS only tells you where a server lives. It does not tell you how to talk to it.

For that, we need a protocol. And for the web — which is where almost all of our day-to-day interaction with the internet happens — the protocol is HTTP: the HyperText Transfer Protocol.

One-sentence definition: HTTP is a text-based request-response protocol that runs on top of TCP, in which a client sends a request for a resource and a server sends back the resource (or an explanation of why it cannot).

The client-server model

HTTP is built on a simple model: a client initiates a request, and a server responds. Every interaction you have ever had with a web page is a series of such exchanges.

When you type an address into your browser, the browser is the client. It opens a TCP connection to the server, sends a request as text, and reads back the response also as text. There is no binary protocol here — you can literally watch the exchange with a tool like curl -v or telnet.

The client sends a text request. The server responds with a text response. Between requests, the server has no memory of the client — HTTP is stateless.

What runs underneath — HTTP and TCP

HTTP does not run directly on the network. It runs on top of TCP — the Transmission Control Protocol — which is responsible for the reliable, ordered byte stream that HTTP needs.

This means that before any HTTP request can be sent, a TCP connection must be established. That connection setup involves the classic three-way handshake — SYN, SYN-ACK, ACK — and costs one network round-trip. On a wide-area network, that is tens of milliseconds of latency.

Historically, HTTP/1.0 opened a new TCP connection for every single request. That was wasteful. Then HTTP/1.1 introduced persistent connections — keeping the TCP connection alive across multiple requests — which dropped latency significantly. We will look at this in more detail in section 12.5.

The port matters: by convention, HTTP runs on TCP port 80 and HTTPS — HTTP wrapped in TLS — runs on TCP port 443. These are just defaults; nothing stops you from running a web server on port 8080 or 3000 or 9999. But if a client asks for http://example.com, it will connect to port 80 unless you tell it otherwise.

But wait, what about HTTPS?

HTTPS is not a different protocol. It is HTTP, wrapped inside TLS — Transport Layer Security. The HTTP request-response cycle is exactly the same. The difference is that the TCP stream is encrypted, so an observer on the network cannot read the requests or responses, and the server presents a certificate that the client can verify.

From the perspective of a web application — and of an Nginx configuration — HTTPS is HTTP. You configure it using the same directives, with a few extra lines for the certificate and key. The details of TLS are a topic for another course; for now, know that HTTPS is HTTP + crypto and the structure we learn here applies to both.

A first look at an HTTP message

Let's look at what an HTTP request actually looks like on the wire. This is the request your browser sends when you visit the page at http://example.com/index.html: 

GET /index.html HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (X11; Linux x86_64)
Accept: text/html,application/xhtml+xml
Accept-Language: en-US,en;q=0.9
Connection: keep-alive

That is the entire request. It is text. Broken down:

  • The first line is the request line — it contains the method (GET), the path to the resource (/index.html), and the protocol version (HTTP/1.1).
  • The next several lines are headers — key-value pairs that carry metadata. The Host header is required in HTTP/1.1 and tells the server which virtual host the client is asking for.
  • A blank line separates the headers from the body. A GET request has no body.

And here is the response the server sends back: 

HTTP/1.1 200 OK
Date: Tue, 12 Nov 2024 10:22:14 GMT
Server: nginx/1.24.0
Content-Type: text/html; charset=UTF-8
Content-Length: 1256
Connection: keep-alive

<!DOCTYPE html>
<html>...the page content...</html>

Structure:

  • The first line is the status line — protocol version, status code (200), and reason phrase (OK).
  • Then more headers — metadata about the response.
  • A blank line.
  • The body — the actual file contents.
Everything about HTTP comes down to these two message formats. A request has a request line, headers, an optional blank line, and an optional body. A response has a status line, headers, a blank line, and an optional body. Once you internalize this structure, everything else — methods, status codes, headers, virtual hosts, reverse proxies — is a detail on top of it.

The stateless nature of HTTP

One more foundational concept. HTTP is stateless. This means that from the protocol's perspective, every request is completely independent of every other request. The server has no memory between requests.

But wait — how do web applications remember that you are logged in? How does a shopping cart survive across multiple page loads? The answer is that we keep state ourselves, on top of HTTP.

  • Cookies: the server sends a Set-Cookie header, and the browser sends the cookie back in every subsequent request. The server can identify the client by the cookie value.
  • Session IDs: a random identifier that the server associates with server-side state — user credentials, cart contents, and so on. The client only sees the identifier, not the state itself.
  • Tokens: used in modern stateless authentication. A JWT (JSON Web Token) is sent as a header with every request, and contains all the state the server needs to authenticate and authorize.

The statelessness of HTTP is a feature, not a bug. It makes caches possible, load balancers simple, and horizontal scaling straightforward. If your server needs to remember you, that is a design decision that lives above the protocol, not inside it.

12.2 · HTTP Methods

The first word in every HTTP request is the method. It tells the server what kind of action the client wants to take. The methods are the verbs of the protocol, and each one has specific semantics that servers and clients rely on.

The standard methods

Method Purpose Semantics
GET Retrieve a resource. Safe and idempotent. Should not cause side effects. Response should be cacheable.
HEAD Retrieve only headers, not body. Same as GET but the server omits the response body. Used to check if a resource exists or what its size is.
POST Submit data to be processed. Not idempotent. Usually creates a new resource or triggers a side effect.
PUT Create or replace a resource. Idempotent. If you PUT the same thing twice, the result is the same as PUT once.
PATCH Partially modify a resource. Not necessarily idempotent. Used to update specific fields.
DELETE Delete a resource. Idempotent. If the resource is already gone, no error.
OPTIONS Describe communication options. Returns what methods the server supports for a given resource. Used in CORS pre-flight requests.
TRACE Echo back the request. Used for diagnostics. Often disabled in production for security reasons.
CONNECT Establish a tunnel. Used by HTTPS proxies to tunnel encrypted traffic. Rarely seen in application code.

Safe and idempotent — the two key properties

Methods have two important properties, and understanding them helps clarify why certain methods are used in certain ways.

Safe methods

A method is safe if calling it does not change the state of the server. GET, HEAD, and OPTIONS are safe. That is why your browser can prefetch a page, or a web crawler can index your site, without worrying about modifying anything.

Idempotent methods

A method is idempotent if calling it multiple times has the same effect as calling it once. GET, PUT, and DELETE are idempotent. POST is not. That is why your browser sometimes warns you before re-submitting a form on refresh.

The idempotent property matters a lot for reliability. If a PUT request is lost due to a network failure, the client can safely retry it. If a POST request is lost, retrying it might create a duplicate resource. This is why well-designed APIs use PUT for create-or-replace operations and reserve POST for cases where duplicates would be a problem.

GET in detail

GET is by far the most common method. When you browse the web, virtually every request you make is a GET, or a sub-request that fetches images, CSS, and JavaScript for the page.

A GET request can include a query string — parameters appended to the path after a question mark. For example: 

GET /search?q=operating+systems&page=2 HTTP/1.1
Host: example.com

The query string is part of the URL. It is visible in your browser's address bar, in server logs, and in the browser's history. Never put sensitive information — passwords, tokens — in a query string.

Query strings are not private. They appear in server access logs, in browser history, in the referrer header sent to third-party sites, and in any proxy or gateway between you and the server. Sensitive data belongs in the request body or in headers — not in a URL.

POST in detail

POST is used when the client wants to send data to the server, usually to create something new. The data goes in the request body, not in the URL. 

POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 57

{"name": "Alice", "email": "alice@example.com"}

Unlike GET, POST requests are not supposed to be cached by default, and browsers handle them specially. When you refresh a page that resulted from a POST, the browser usually warns you that the form will be re-submitted. That is because re-submitting might create a duplicate resource.

The rule of thumb: use GET to read, POST to create, PUT to replace, PATCH to update, DELETE to remove. This pattern — sometimes called REST — is not the only way to design an API, but it is by far the most common, and it maps cleanly onto how HTTP is meant to work.

12.3 · Status Codes

Every HTTP response starts with a status code — a three-digit number that tells the client whether the request succeeded, and if not, what went wrong. The codes are organized into five classes, one for each hundreds digit.

The five classes of HTTP status codes. The first digit tells you whether the request succeeded and, if not, whether the fault is the client's or the server's.

The codes you will see every day

Code Reason Meaning
200 OK The request succeeded and the response contains the resource.
201 Created The request succeeded and created a new resource. Usually returned from a POST or PUT.
204 No Content The request succeeded but there is no body. Common for DELETE or for an AJAX update that does not need a response.
301 Moved Permanently The resource has permanently moved to a new URL. Clients should update their bookmarks.
302 Found Temporary redirect. The resource is at a different URL for now.
304 Not Modified The client's cached version is still fresh. The response has no body — the client uses the cache.
400 Bad Request The request is malformed — a syntax error or a missing required field.
401 Unauthorized The request needs authentication. (Yes, the name is misleading — it should be "unauthenticated".)
403 Forbidden The server understood the request but refuses to authorize it. You are authenticated but not allowed.
404 Not Found The resource does not exist at the requested URL.
405 Method Not Allowed The method is not supported for this resource. For example, POST on a static file.
429 Too Many Requests The client is rate-limited. Used by APIs to prevent abuse.
500 Internal Server Error Something went wrong inside the server. Usually a bug in the application.
502 Bad Gateway A proxy or gateway received an invalid response from the upstream server. Very common with reverse proxies (like Nginx) when the backend is down.
503 Service Unavailable The server is temporarily overloaded or down for maintenance. Clients should retry after a delay.
504 Gateway Timeout The proxy waited too long for the upstream server to respond.
502 vs 503 vs 504: these three are the ones you will encounter most often when working with Nginx as a reverse proxy. 502 means Nginx could not get a valid response from the backend — usually because the backend is not running on the expected port. 503 means Nginx itself refused to serve the request — usually because a rate limit or limit_req kicked in, or the upstream pool is exhausted. 504 means Nginx did get a connection but the backend took too long to respond — usually the backend is doing something slow and has hit a timeout.

Reading the status line

The status code appears at the beginning of the first line of the response, called the status line. Its format is: 

HTTP/1.1 200 OK
HTTP/1.1 404 Not Found
HTTP/1.1 500 Internal Server Error

Three parts: the protocol version, the status code, and the reason phrase — a short human-readable description. The reason phrase is mostly for humans — clients should rely on the code, not the phrase.

Reading a status code is the fastest way to diagnose a web request. If you run curl -I https://example.com, the first thing you should look at is the status line. 200 means it worked. 301 or 302 means the resource moved. 403 means you are not authorized. 404 means the URL is wrong. 500 or 502 means the server has a problem — and no amount of client-side debugging will fix that.

12.4 · Headers

Headers are the metadata of HTTP. They are simple key-value pairs, passed as plain text, one per line, separated from the body by a blank line. They carry information about the request, about the response, about the connection, and about the resource being transferred.

There are dozens of standard headers, plus non-standard ones defined by specific applications. We will look at the ones you will encounter every day.

Request headers — sent by the client

Header Meaning
Host The domain name the client is requesting. Required in HTTP/1.1. This is what makes virtual hosts (running multiple websites on one server) possible.
User-Agent Identifies the client software — browser name and version, operating system, and so on. Useful for analytics and for serving different content to different clients.
Accept The content types the client can handle — text/html, application/json, and so on. Servers should respect this when they have a choice.
Accept-Language The natural languages the client prefers, with quality values. Used for content negotiation.
Accept-Encoding The compression algorithms the client can handle — typically gzip, br (Brotli), or deflate.
Cookie Cookies that the client is sending back to the server. Set previously by a Set-Cookie response header.
Authorization Credentials for authenticated requests — usually in the form of a bearer token or basic auth.
Referer The URL of the page that linked to the current request. Often used for analytics. (Note the misspelling — it is historically "Referer", not "Referrer".)
If-Modified-Since Used for caching. If the resource has not changed since the given time, the server responds with 304 Not Modified.
Connection Whether to keep the TCP connection alive. keep-alive or close.

Response headers — sent by the server

Header Meaning
Content-Type The MIME type of the response body — text/html, application/json, image/png, and so on. This is what tells the browser how to render the response.
Content-Length The size of the response body in bytes. The client uses this to know when the response is complete.
Content-Encoding The compression used on the body — gzip, br, and so on. The client must decompress before rendering.
Cache-Control Caching directives — how long the response may be cached, whether it may be reused by proxies, and so on.
Set-Cookie Sets a cookie on the client. Can include flags like HttpOnly, Secure, SameSite, and an expiration.
Location Used with redirects — where the client should look for the resource.
Server Identifies the server software — nginx/1.24.0, Apache/2.4.52. Some administrators hide this for security reasons.
ETag A fingerprint of the resource. Used for caching — if the ETag matches what the client has cached, the resource has not changed.
Last-Modified The timestamp when the resource was last modified.
Strict-Transport-Security Tells the browser to always use HTTPS for this domain in the future.
X-Frame-Options Prevents the page from being embedded in a frame on another site. A basic defense against clickjacking.

A real-world example

Let's look at a complete request and response, using curl to see the headers. This is what your browser sends to example.com: 

$ curl -I http://example.com

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 1256
Server: nginx/1.24.0
Date: Tue, 12 Nov 2024 10:22:14 GMT
Cache-Control: max-age=3600
ETag: "abc123def456"
Last-Modified: Mon, 04 Nov 2024 09:15:30 GMT
Connection: keep-alive

The -I flag tells curl to send a HEAD request — the server sends headers but no body. That is exactly the shape of every HTTP response, minus the body.

Let me point out a few things. The Content-Type tells the browser this is an HTML document in UTF-8 encoding. The Content-Length tells the browser the exact size so it knows when the response is complete. The Server header leaks information — it is sometimes removed or replaced for security. The ETag and Last-Modified give the client things it can send back on subsequent requests to check for freshness.

Reading headers from a live site: you can do this with curl on any URL. Try curl -I https://github.com or curl -I https://www.google.com to see what real production sites send. You will see all kinds of security headers and caching directives that we do not have room to cover in detail — and they all follow the same simple key-value format.

Custom headers

HTTP allows arbitrary headers, as long as they follow the same format. Custom headers are usually prefixed with X- by convention, though this is not required. 

X-Request-ID: 8f7e6d5c-4b3a-2910-8f7e-6d5c4b3a2910
X-Forwarded-For: 192.168.1.100
X-Real-IP: 192.168.1.100
X-Custom-Auth: some-token-value

X-Forwarded-For is particularly important. When a request passes through a proxy or reverse proxy, the proxy adds this header to record the original client IP. This is how your backend application can know who is really making a request, even though it only sees the proxy's IP.

Custom headers are not for security. They are for metadata. Client-provided headers can always be forged, so never trust them for authentication or authorization. Use proper signed tokens or server-side session state instead.

12.5 · Connections & HTTP Versions

We have said that HTTP runs on top of TCP. That means every HTTP exchange begins with a TCP connection being established. How that connection is managed — whether it is reused across multiple requests or closed immediately — has a big impact on performance.

Non-persistent vs persistent connections

HTTP/1.0 — non-persistent

In the original HTTP/1.0 design, each request uses a fresh TCP connection. The client:

  • Opens a TCP connection (3-way handshake)
  • Sends one request
  • Receives one response
  • Closes the connection

Loading a page with 20 assets means 20 TCP connections. Each one pays the handshake cost.

HTTP/1.1 — persistent

HTTP/1.1 keeps the TCP connection open by default. The client can send multiple requests over the same connection. The client:

  • Opens one TCP connection
  • Sends multiple requests over time
  • Receives responses in order
  • Closes when done or after a timeout

The handshake cost is paid once, not once per request.

Why persistent connections matter: on a high-latency network — say, between a browser in Cairo and a server in Frankfurt — the three-way handshake takes around 40 milliseconds. With non-persistent connections, 20 assets cost 800 milliseconds just in handshakes. With persistent connections, it is 40 milliseconds total. That is a 20× improvement in a very important metric.
HTTP/1.0 opens a new TCP connection for every request. HTTP/1.1 reuses the same connection for multiple requests — saving handshakes and dramatically improving performance.

Head-of-line blocking

Persistent connections are not without problems. In HTTP/1.1, requests on a single connection are processed in order — a big response can block all subsequent requests behind it. This is called head-of-line blocking.

Browsers worked around this limitation for years by opening 6 to 8 parallel connections to each origin. That worked, but it was a hack. The protocol itself did not solve the problem.

HTTP/2 and HTTP/3 — the modern versions

HTTP/2 — standardized in 2015 — addresses head-of-line blocking by multiplexing multiple requests over a single connection. Each request and response is split into frames, and the frames can be interleaved. A big response cannot block smaller ones. HTTP/2 also adds header compression and server push.

HTTP/3 — standardized in 2022 — goes further. It moves from TCP to a protocol called QUIC, which runs over UDP. This eliminates the remaining TCP-level head-of-line blocking, and it reduces connection setup to zero round-trips in some cases.

Version Published Transport Key features
HTTP/1.0 1996 TCP Simple request-response. No persistent connections by default. No Host header.
HTTP/1.1 1997 TCP Persistent connections. Pipelining (rarely used). Chunked transfer. Required Host header.
HTTP/2 2015 TCP (with stream multiplexing) Multiplexing. Header compression (HPACK). Server push. Binary framing. Field still works over plain TCP.
HTTP/3 2022 QUIC (over UDP) Multiplexing without TCP head-of-line blocking. Faster connection setup. Header compression (QPACK).
What you actually need to know for this week: HTTP/1.1 is the version you will configure explicitly in Nginx. Nginx also supports HTTP/2 (with listen 443 ssl http2;) and HTTP/3. The concepts we are learning — methods, status codes, headers, virtual hosts, reverse proxies — apply equally to all versions. The protocol changes, but the semantics stay the same.

12.6 · Introducing Nginx

Now that we understand the protocol, let's look at how to serve HTTP. We need a web server — a program that listens on port 80, accepts HTTP requests, and sends HTTP responses. The most widely used web server on the internet today is Nginx.

Nginx — pronounced "engine-X" — was created in 2004 by Igor Sysoev to solve the C10K problem: how to handle ten thousand concurrent connections on a single server. Traditional web servers used a thread-per-connection model. Each connection required a thread, and threads are expensive. Nginx uses an event-driven, asynchronous architecture, which handles thousands of connections per worker process with very little memory.

Why Nginx?

Feature Description
High concurrency Handles tens of thousands of simultaneous connections with a small memory footprint.
Low memory An idle Nginx process uses a few megabytes. Under load, it stays predictable.
Reverse proxy Excellent built-in support for forwarding requests to backend applications and load balancing across multiple backends.
Static file serving Extremely efficient at serving files from disk — faster than most application servers.
SSL/TLS termination Comprehensive HTTPS support, including modern ciphers and certificate management.
Config simplicity Nginx configuration is readable and predictable. It is a small DSL, not a programming language.

Architecture: master and workers

Nginx uses a master-worker architecture. When you start Nginx, the master process reads the configuration and forks a small number of worker processes — typically one per CPU core. Each worker handles a subset of the incoming connections and processes them using asynchronous I/O.

The master process is not involved in handling requests. It only manages the workers — starting them at boot, reloading them when the configuration changes, restarting them if they crash. This separation is what makes Nginx easy to reload without dropping connections.

Nginx runs a single master process and one worker per CPU core. Workers handle requests asynchronously — no thread-per-connection, no context-switch overhead, no per-connection memory.

Installing Nginx on Ubuntu

On Ubuntu, Nginx is available in the default repositories. Installation is one command: 

sudo apt update
sudo apt install nginx

sudo systemctl enable nginx
sudo systemctl start nginx
systemctl status nginx

The package installs Nginx, sets it up as a systemd service, and starts it. By default, it listens on port 80 and serves a welcome page from /var/www/html.

Let's verify it works from the VM: 

curl -I http://localhost

HTTP/1.1 200 OK
Server: nginx/1.24.0
Date: ...
Content-Type: text/html
Content-Length: 612
Last-Modified: ...
Connection: keep-alive
ETag: "..."
Accept-Ranges: bytes

And from a client machine on the same network — if the firewall allows it: 

curl -I http://192.168.56.1
If you see 200 OK, Nginx is running. If you see "connection refused", check systemctl status nginx. If the service is not running, check the journal with journalctl -u nginx -n 50. The most common issue on a fresh install is a port conflict — something else already listening on port 80.

Configuration layout

Nginx's configuration lives in /etc/nginx/. The layout is: 

/etc/nginx/
├── nginx.conf                    ← main config file
├── conf.d/                       ← optional snippets
├── sites-available/              ← site configs (not yet active)
├── sites-enabled/                ← symlinks to active sites
├── snippets/                     ← reusable config fragments
└── mime.types                    ← MIME type mappings

The main file nginx.conf contains global settings and, importantly, includes from the other directories. On Ubuntu, the default includes are /etc/nginx/conf.d/*.conf and /etc/nginx/sites-enabled/*.

The shape of an nginx.conf

Nginx configuration is a tree of directives. Some directives are simple — a single line with a value. Others are blocks — they have braces and contain other directives. The main blocks you will use are http, server, and location. 

# Global context
user www-data;
worker_processes auto;

events {
    worker_connections 768;
}

http {
    # Directives applying to all sites
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    # Individual websites
    server {
        listen 80;
        server_name example.com;

        location / {
            root /var/www/example;
            index index.html;
        }
    }
}

Let me walk through the levels:

  • Main context — directives outside any block. These apply globally — like user and worker_processes.
  • events block — settings for the connection layer, like how many connections a single worker can handle.
  • http block — settings for the HTTP protocol layer, plus one server block per website.
  • server block — an individual site. listen says which port and address it listens on. server_name says which Host header it responds to. And location blocks define behavior for different URL prefixes.
The best way to learn Nginx config is to read the default one. After installing Nginx, open /etc/nginx/nginx.conf and /etc/nginx/sites-enabled/default. Read them top to bottom. They are heavily commented and every directive is documented in the official Nginx reference.

Testing the configuration

Before reloading Nginx after a configuration change, always test the configuration first: 

sudo nginx -t

nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful

If there is an error, Nginx will tell you which file and which line. Fix it before reloading. If you reload with a broken config, Nginx might refuse to reload entirely — or, worse, it might load a partial configuration. 

sudo systemctl reload nginx   # reload config without dropping connections
sudo systemctl restart nginx  # restart workers — brief downtime
sudo systemctl status nginx   # check service status
Always nginx -t before reload. On a production server, a typo in the configuration file combined with a reload could take the site down. The test command is cheap and catches 99% of configuration errors.

12.7 · Virtual Hosts & Document Roots

Here is a question. If a single machine has one IP address on port 80, how can it host more than one website?

The answer is virtual hosts. Nginx — and every other modern web server — can distinguish between requests for different sites based on the Host header inside the HTTP request. All requests arrive on the same port 80, but the server looks at the Host header and decides which site to serve.

This is why the Host header is mandatory in HTTP/1.1. Without it, virtual hosting would not be possible.

Virtual hosts let one server host many sites. All requests arrive at the same IP and port. Nginx picks the matching server block by looking at the Host header.

Configuring a virtual host

Each website gets its own file in /etc/nginx/sites-available/. That file contains a server block. To activate it, we create a symlink from /etc/nginx/sites-enabled/. The convention is available for the source file and enabled for the active symlink.

Here is a minimal virtual host for shop.example: 

server {
    listen 80;
    listen [::]:80;

    server_name shop.example;

    root /var/www/shop;
    index index.html index.htm;

    access_log /var/log/nginx/shop.access.log;
    error_log  /var/log/nginx/shop.error.log;

    location / {
        try_files $uri $uri/ =404;
    }
}

Let me walk through the directives.

  • listen 80 — accept connections on IPv4 port 80. The [::] version does the same for IPv6.
  • server_name — respond to requests whose Host header matches shop.example.
  • root — serve files from /var/www/shop. A request for /index.html reads the file /var/www/shop/index.html.
  • index — if a request is for a directory, serve one of these files if it exists.
  • access_log and error_log — where to write the request log and error log.
  • location / — how to handle requests for paths beginning with /. The try_files directive says: try the requested URI as a file; if not, try it as a directory; if neither, return 404.

To activate the site, create the symlink and reload: 

sudo ln -s /etc/nginx/sites-available/shop.example /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

The default server

What happens when a request arrives with a Host header that does not match any server_name? Nginx uses the default server — the first server block it finds that listens on the same port. Or, if you explicitly mark a block with default_server, that one. 

server {
    listen 80 default_server;
    server_name _;
    return 444;
}

The server_name _ is a convention — the underscore is not a valid hostname, so it never matches a real Host header. Combined with default_server, this block catches any request that does not match another server block, and returns status 444 — a special Nginx status code that means "close the connection without responding". Useful for blocking unwanted traffic.

The core idea: one IP, one port, many sites. The Host header is the discriminator, and server_name is the matcher. Everything else is standard HTTP — requests in, responses out.

Location blocks — the heart of Nginx configuration

Inside a server block, you can have multiple location blocks. Each one defines how to handle requests whose path matches a given prefix or pattern. This is where most of the interesting configuration happens. 

location / {
    root /var/www/shop;
    index index.html;
}

location /images/ {
    root /var/www/shop;
    expires 7d;
    add_header Cache-Control "public";
}

location /api/ {
    proxy_pass http://127.0.0.1:5000/;
}

location ~* \.(jpg|jpeg|png|gif|ico|css|js)$ {
    root /var/www/shop;
    expires 30d;
}

Walking through each:

  • location / — matches any path. The catch-all.
  • location /images/ — matches paths beginning with /images/. In this case we are telling the client to cache images for 7 days.
  • location /api/ — matches paths beginning with /api/, and forwards them to a backend application running on port 5000. We will cover this in the next section.
  • location ~* \.(jpg|...)$ — the ~* means case-insensitive regular expression match. This is a common way to serve static asset types with long caching headers.
Location matching priority: Nginx uses a specific order to match locations. Exact matches (=) win first, then prefix matches (^~), then regular expression matches (~ and ~*), then plain prefix matches. The longest matching prefix wins. This is a common source of confusion for beginners — but for most configurations you will only use a few location blocks and the rules work out naturally.

12.8 · Reverse Proxy & Load Balancing

So far, Nginx has been serving static files directly from disk. That is useful, but it is only half of what a modern web server does. The other half is being a reverse proxy — accepting requests from clients and forwarding them to a backend application.

Forward proxy vs reverse proxy

Two related but distinct concepts, often confused. Let's clarify.

Forward proxy

Sits between the client and the internet. The client is configured to send requests through the proxy. The proxy forwards them to arbitrary destinations on behalf of the client. Used for anonymity, content filtering, and caching. The proxy is transparent to the destination server.

Reverse proxy

Sits between the internet and a set of backend servers. Clients do not know they are talking to a proxy — they think they are talking to the actual site. The proxy decides which backend serves the request. Used for load balancing, SSL termination, caching, and routing.

The names are from the perspective of the network path. A forward proxy sits forward of the client, on the way out. A reverse proxy sits forward of the server, on the way in.

Why use a reverse proxy?

You might ask: why not have the application listen directly on port 80? Why put Nginx in front?

Benefit Description
SSL termination Nginx handles the HTTPS handshake and decrypts the request. The backend sees plain HTTP. This simplifies the application code significantly.
Static file handling Nginx serves images, CSS, JS, HTML files directly from disk — much faster than the application can. The backend only handles dynamic requests.
Load balancing Nginx distributes requests across multiple backend servers. This is invisible to clients and requires no changes to the application.
Caching Nginx can cache backend responses and serve them without re-querying the backend.
Rate limiting Nginx can throttle clients — per IP, per user, per resource — before they ever reach the backend.
Security Nginx can hide the backend's identity, block specific User-Agents, filter requests by IP, and more.
Zero-downtime deploys You can restart the backend while Nginx keeps accepting connections and serving static files or a maintenance page.
The reverse proxy hides the backend from the internet. The backend sees requests coming from Nginx only — not from the actual client IP.

A minimal reverse proxy configuration

Here is a simple Nginx config to proxy all requests to a backend on port 5000: 

server {
    listen 80;
    server_name app.example;

    location / {
        proxy_pass http://127.0.0.1:5000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

The key directive is proxy_pass. It tells Nginx: for requests matching this location, forward them to the given URL and return whatever comes back. The default behavior is to rewrite the request line — the backend sees the original path, method, headers, and body.

The proxy_set_header directives are also important. They modify the request headers before passing them to the backend:

  • Host $host — forwards the original Host header, so the backend knows which site was requested. Many frameworks use this to build URLs.
  • X-Real-IP $remote_addr — the actual client IP. Set as a custom header, because otherwise the backend only sees Nginx's IP.
  • X-Forwarded-For $proxy_add_x_forwarded_for — the full chain of proxies the request has passed through. This is the standard header for this purpose.
  • X-Forwarded-Proto $scheme — whether the original request came in over HTTP or HTTPS. This matters when the backend needs to generate URLs.
The trailing slash trap: proxy_pass http://127.0.0.1:5000/; with a trailing slash will strip the matched prefix from the path before forwarding. So a request for /api/users with location /api/ and a trailing-slash proxy_pass becomes /users at the backend. Without the trailing slash, it stays /api/users. This behavior trips up almost everyone at least once.

Load balancing across multiple backends

A single backend is a single point of failure. Nginx can distribute requests across several backends using an upstream block: 

upstream app_backend {
    server 127.0.0.1:5001;
    server 127.0.0.1:5002;
    server 127.0.0.1:5003;
}

server {
    listen 80;
    server_name app.example;

    location / {
        proxy_pass http://app_backend;
    }
}

Nginx distributes requests across the servers using weighted round-robin. You can also use least_conn — send each request to the backend with the fewest active connections — or IP hash — pin a given client IP to a specific backend.

Method Behavior
round-robin Default. Each backend is used in turn, in order.
least_conn Pick the backend with the fewest active connections. Good for slow or variable requests.
ip_hash Hash the client IP; the same client always goes to the same backend. Useful for session stickiness.
weight=N Specify a weight per server. Useful when backends have different capacities.

Health checks

If a backend goes down, Nginx will keep sending it requests, and clients will see errors. There are two ways to handle this in the open-source version of Nginx.

  • Passive health checks: Nginx notices when a backend starts failing, and temporarily stops sending it requests. Configured with max_fails and fail_timeout.
  • Active health checks: Nginx periodically sends a request to a configured path — say, /health — and removes backends that do not respond. Active checks in Nginx require the commercial subscription or the open-source OpenResty bundle.
upstream app_backend {
    server 127.0.0.1:5001 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:5002 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:5003 down;   # temporarily disabled
}

With max_fails=3 and fail_timeout=30s, Nginx will stop sending traffic to a backend after three failures in a row, for at least 30 seconds. After that, it retries — if the backend responds well, it rejoins the pool; if not, it is removed again.

What you have built so far: a public-facing server that terminates HTTP, optionally handles HTTPS, serves static files, and routes dynamic requests to one or more backend applications, all behind a single endpoint. This is exactly the architecture of every serious web service — from a small startup to a global platform.

12.9 · Deep Lab — Serving Two Static Sites

In this lab, we will build two complete virtual hosts on our Ubuntu VM. Each will have its own document root, its own content, and its own log files. This is the classic setup of a small web hosting environment.

We will use the host-only network interface we already have at 192.168.56.1 — the one we configured back in Week 10 for the DHCP lab.

Step 1 — Create the document roots

sudo mkdir -p /var/www/shop.example

sudo chown -R www-data:www-data /var/www/shop.example

Nginx runs as the www-data user by default. It must be able to read the files in these directories.

Step 2 — Create index pages

sudo tee /var/www/shop.example/index.html > /dev/null <<'EOF'
<!DOCTYPE html>
<html>

Step 3 — Create the site configurations

sudo nano /etc/nginx/sites-available/shop.example

Paste the following:

server {

12.10 · Deep Lab — Reverse Proxy to a Backend

Now let's put Nginx in front of an application. We will build a tiny Python web app, run it on localhost:5000, and have Nginx forward requests to it. We will also verify the headers that Nginx sets, and configure a status code path.

Step 1 — Create a simple backend

sudo apt install python3 python3-pip -y
pip3 install flask --break-system-packages
sudo mkdir -p /opt/myapp
sudo tee /opt/myapp/app.py > /dev/null <<'EOF'
from flask import Flask, request
import socket

app = Flask(__name__)

@app.route('/')
def index():
    return f"""<h1>My Backend App</h1>
    <p>Hello from {socket.gethostname()}</p>
    <p>Client IP: {request.headers.get('X-Real-IP', 'unknown')}</p>
    <p>Forwarded for: {request.headers.get('X-Forwarded-For', 'none')}</p>
    <p>Forwarded proto: {request.headers.get('X-Forwarded-Proto', 'none')}</p>
    """

@app.route('/health')
def health():
    return 'OK', 200

if __name__ == '__main__':
    app.run(host='127.0.0.1', port=5000)
EOF

Note the host='127.0.0.1' in the last line. That is deliberate. The backend listens only on the loopback interface, so it is not directly reachable from the network. The only way to reach it is through Nginx. That is the standard security posture.

Step 2 — Run the backend

python3 /opt/myapp/app.py &

Verify it works locally: 

curl http://127.0.0.1:5000

Step 3 — Configure Nginx as reverse proxy

sudo nano /etc/nginx/sites-available/app.example
server {
    listen 80;
    server_name app.example;

    # Static files served directly by Nginx
    location /static/ {
        root /var/www/app.example;
        expires 7d;
        access_log off;
    }

    # Everything else proxied to the backend
    location / {
        proxy_pass http://127.0.0.1:5000;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;

        # Timeouts
        proxy_connect_timeout 5s;
        proxy_send_timeout    30s;
        proxy_read_timeout    30s;
    }
}

Step 4 — Enable and reload

sudo ln -s /etc/nginx/sites-available/app.example /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

Step 5 — Test through Nginx

curl -H "Host: app.example" http://localhost/

You should see the backend's response — the "My Backend App" page. The interesting part is the X-Real-IP and X-Forwarded-For headers — they should show the real client IP, which is 127.0.0.1 in this local test, but would be the actual client's IP in a real deployment.

To see the headers more clearly: 

curl -H "Host: app.example" -v http://localhost/ 2>&1 | grep -E "X-|GET|HTTP"

Step 6 — Verify the backend is not directly reachable

From the client VM, try to hit port 5000 directly: 

curl http://192.168.56.1:5000

This should fail with a connection refused. The backend is bound to 127.0.0.1, so it is unreachable from the network. This is by design. Nginx is the only public endpoint.

Step 7 — Test the health check endpoint through Nginx

curl -H "Host: app.example" http://localhost/health

Returns OK. In a real deployment, this is the endpoint a load balancer or monitoring system would poll.

Step 8 — Read the logs

Now that we have a reverse proxy, the log flow is interesting. Let's look at both logs. 

sudo tail -f /var/log/nginx/access.log

The Nginx log shows the client's real IP. Now check the backend's stdout: 

jobs              # find the background job
# Or just reconnect to the terminal

The backend's log shows Nginx's IP (127.0.0.1), not the client's. This is exactly why we set the X-Real-IP and X-Forwarded-For headers — so the backend can find out the real client IP from the headers, even though the connection came from Nginx.

The pattern is now complete: clients talk to Nginx. Nginx serves static files directly and forwards dynamic requests to the backend. The backend is protected — it is not reachable from the network. Logs tell you what happened at both layers. This is the canonical production web stack, and you built it by hand.

Step 9 — Add caching

Nginx can cache backend responses, so repeated requests for the same resource do not need to re-query the backend. This is a simple but powerful optimization.

First, define a cache zone in /etc/nginx/nginx.conf — inside the http block: 

proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=app_cache:10m
                 max_size=1g inactive=60m use_temp_path=off;

Then use it in the server block: 

location / {
    proxy_cache app_cache;
    proxy_cache_valid 200 5m;
    proxy_cache_valid 404 1m;
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
    add_header X-Cache-Status $upstream_cache_status;

    proxy_pass http://127.0.0.1:5000;
    # ... other proxy_set_header lines ...
}

Let me explain the important directives.

  • proxy_cache app_cache — use the cache zone named app_cache. Recall that CFS used a red-black tree — Nginx's cache uses a similar idea: levels=1:2 means two nested directories, creating a tree that does not have too many files in any one directory.
  • proxy_cache_valid 200 5m — cache successful responses for 5 minutes.
  • proxy_cache_valid 404 1m — cache 404s for 1 minute. This absorbs request floods for a URL that does not exist.
  • proxy_cache_use_stale — if the backend is down, serve the cached version. This is a common resilience pattern.
  • add_header X-Cache-Status $upstream_cache_status — include the cache status in the response, so you can see if a request was a HIT, MISS, or BYPASS.
sudo mkdir -p /var/cache/nginx
sudo chown www-data:www-data /var/cache/nginx

sudo nginx -t
sudo systemctl reload nginx

Now test the cache: 

curl -H "Host: app.example" -I http://localhost/
curl -H "Host: app.example" -I http://localhost/

The first request should show X-Cache-Status: MISS. The second should show X-Cache-Status: HIT. You have just added caching to a reverse-proxied application without changing a single line of application code.

Step 10 — Clean up

# Kill the Flask backend
pkill -f /opt/myapp/app.py

# Remove the site config
sudo rm /etc/nginx/sites-enabled/app.example
sudo rm /etc/nginx/sites-available/app.example
sudo systemctl reload nginx

Week 12 Summary

  • HTTP is a text-based request-response protocol built on top of TCP. Every request and response has a defined structure: a start line, headers, a blank line, and an optional body.
  • Methods are the verbs of HTTP: GET reads, POST creates, PUT replaces, PATCH updates, DELETE removes. Two properties matter: safe methods have no side effects, and idempotent methods can be retried safely.
  • Status codes are three-digit numbers in five classes. 2xx means success, 3xx means redirection, 4xx means client error, 5xx means server error.
  • Headers carry metadata about requests and responses. Host is required in HTTP/1.1 and enables virtual hosts. X-Forwarded-For and X-Real-IP carry the original client IP through proxies.
  • Connections — HTTP/1.1 uses persistent TCP connections by default. HTTP/2 adds multiplexing. HTTP/3 moves to QUIC over UDP.
  • Nginx is an event-driven web server. It runs one master process and one worker per CPU core. It is particularly good at serving static files and acting as a reverse proxy.
  • Virtual hosts let one server host many sites. Nginx selects the server block by matching the Host header against server_name.
  • Location blocks define how to handle different URL prefixes — serving from a document root, applying caching headers, or proxying to a backend.
  • Reverse proxy puts Nginx between the internet and a backend application. This enables SSL termination, load balancing, caching, rate limiting, and a clean separation between static and dynamic content.
  • Upstream blocks define pools of backend servers. Nginx distributes requests across them using round-robin, least_conn, or ip_hash.
  • Testing and reloading: always nginx -t before systemctl reload nginx. A syntax error in the config combined with a reload can take the site down.
