4.1 · Race Conditions and Critical Sections

In Week 3 you saw the dangerous side of threads: shared memory without coordination trivially corrupts data. You saw the classic counter++ example produce non-deterministic results, and you learned the vocabulary — race condition, critical section, mutual exclusion. Now it is time to build the tools that let us take control of that chaos.

Week 4 in one sentence: this week we learn how to make concurrent code correct — predictably, provably, and efficiently.

The three properties we want from any solution

Before looking at mechanisms, let us define what a good solution must guarantee. Any correct synchronization primitive must provide all three:

Property Meaning If missing…
Mutual exclusion At most one thread is inside the critical section at any time. Race conditions — data corruption.
Progress If no thread is inside the critical section, and some thread wants in, one of them must be allowed to enter — eventually. Starvation or livelock.
Bounded waiting There is a limit on how many times other threads can enter the critical section before a waiting thread gets its turn. Some thread may wait forever even though the system is technically making progress.

Why a simple flag variable doesn't work

Suppose you try to build a lock with a simple boolean flag: 

/* A broken attempt at a lock */
volatile int lock = 0;   /* 0 = free, 1 = held */

void acquire(void) {
    while (lock == 1) { /* spin — wait */ }
    lock = 1;           /* now claim the lock */
}

void release(void) {
    lock = 0;
}

This is called a spinlock attempt, and it is broken. Two threads can both check the flag, both see it as 0, both decide to take the lock, and both enter the critical section. The check and the set are not atomic — they suffer from exactly the same interleaving problem as counter++.

Why we can't just "check then set": between the check and the set, another thread can run. The instruction pair is not atomic at the hardware level. To fix this, we need hardware support — a way to test and set a value in a single, uninterruptible instruction.

Hardware primitives: the foundation of every lock

Modern CPUs provide atomic primitives that make correct locks possible. The most important ones are:

  • Test-and-set: atomically returns the old value of a variable and sets it to 1.
  • Compare-and-swap (CAS): atomically sets a variable to a new value, but only if its current value matches an expected value.
  • Load-linked / store-conditional (LL/SC): a pair of instructions used on RISC architectures, with the same effect as CAS.
  • Fetch-and-add: atomically adds a value and returns the old value — used for atomic counters.

Every lock, semaphore, and condition variable in every operating system is ultimately built out of these primitives. They are the hardware's contribution to correct concurrency.

Good news: you rarely write spinlocks by hand. The C standard, pthread library, and Linux kernel all provide correct, tested implementations. But you must know what they are built on — because the guarantees they provide are the guarantees you rely on when you use them.

4.2 · Locks and Mutexes

A lock — or mutex, for mutual exclusion — is the most fundamental synchronization primitive. Its interface is simple and beautiful: 

lock_t mutex;              /* create a lock variable */

lock(&mutex);              /* try to acquire — blocks if held */
    /* critical section — only one thread at a time can be here */
unlock(&mutex);            /* release */

Any code between lock and unlock runs with the guarantee that no other thread can be inside the same locked region. If a second thread calls lock while the first one holds it, the second thread will block, waiting on that specific lock, until the first calls unlock.

What does "block" actually mean?

There are two possible implementations of lock() when the lock is held:

Spinlocking

The waiting thread sits in a tight loop, repeatedly checking whether the lock has been released. This wastes CPU cycles, but it avoids any context-switch overhead — useful when the lock is held for extremely short periods.

Blocking (sleeping)

The waiting thread asks the kernel to put it to sleep until the lock becomes available. The CPU is then free to run other threads. This is the default in pthreads — efficient when the lock is held for a while.

Linux's pthread mutexes use a hybrid strategy: they briefly spin (a few microseconds) and then block. This is because short critical sections are common, and sleeping has a real cost of its own.

The pthread_mutex API

#include <pthread.h>

pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_timedlock(pthread_mutex_t *mutex,
                            const struct timespec *abs_timeout);
int pthread_mutex_unlock(pthread_mutex_t *mutex);
int pthread_mutex_destroy(pthread_mutex_t *mutex);

pthread_mutex_lock blocks until the mutex is acquired. pthread_mutex_trylock returns immediately — either acquiring the lock or returning EBUSY. pthread_mutex_timedlock gives up after a specified absolute timeout.

Golden rules for mutexes:
  • Always call unlock on every path out of the locked region (including error paths and return statements).
  • Never lock the same mutex twice from the same thread — this is undefined behavior, often a self-deadlock.
  • Never unlock a mutex you did not lock.
  • Keep the critical section as short as possible — holding a lock blocks other threads.

The corrected counter example

#include <stdio.h>
#include <pthread.h>

static pthread_mutex_t counter_lock = PTHREAD_MUTEX_INITIALIZER;
static volatile long counter = 0;

void *worker(void *arg) {
    for (long i = 0; i < 100000; i++) {
        pthread_mutex_lock(&counter_lock);
        counter++;                       /* now safe */
        pthread_mutex_unlock(&counter_lock);
    }
    return NULL;
}

int main(void) {
    pthread_t t1, t2;

    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);

    pthread_join(t1, NULL);
    pthread_join(t2, NULL);

    printf("counter = %ld  (expected 200000)\n", counter);
    return 0;
}

Run this a hundred times — the output is always 200,000. The lock has made the increment atomic from the perspective of the two threads, and the lost update is gone.

What we just did: we took the broken code from Week 3, wrapped the problematic line in a mutex, and turned a non-deterministic bug into deterministic correctness. That is the essence of synchronization.

Performance reality check

A mutex is not free. Every lock and unlock is an atomic operation — typically tens of nanoseconds if uncontended. If the lock is contended, the cost grows dramatically — waiting threads may sleep, requiring a context switch to wake them.

Operation Approximate cost Notes
Uncontended mutex lock/unlock ~15–25 ns A single atomic instruction, no syscall
Contended mutex (sleep-based) ~1,000–10,000 ns Involves futex syscall and context switch
Contended mutex (spin-based) ~50–500 ns Burns CPU, but avoids context switch — good for very short critical sections

This is why real-world code prefers fine-grained locking — many small locks protecting small pieces of data — over one giant global lock. It is also why advanced data structures (lock-free queues, RCU, atomics) exist — to avoid locking altogether where it matters.

4.3 · Semaphores

A semaphore is a generalization of a lock. Instead of a simple "held or free" state, a semaphore has an integer counter that can be any non-negative value.

A semaphore supports two atomic operations:

  • wait(sem) — also called P or down. Decrements the counter. If the counter would become negative, the calling thread blocks until another thread increments the value.
  • post(sem) — also called V or up. Increments the counter. If any thread is blocked waiting on the semaphore, exactly one is woken up.
sem_wait(&sem);    /* decrement; block if 0 */
    /* critical section or resource use */
sem_post(&sem);    /* increment; wake a waiter */

Two uses of semaphores

The beautiful thing about semaphores is that a single mechanism plays two very different roles depending on how you initialize them.

As a lock — init to 1

If you start a semaphore at 1, wait decrements to 0, blocking every other caller until the first one calls post. This behaves exactly like a mutex. 

sem_t mutex;
sem_init(&mutex, 0, 1);
sem_wait(&mutex);
/* critical section */
sem_post(&mutex);

As a counter — init to N

Initialize to N to limit concurrency to at most N threads. Each thread decrements on entry and increments on exit. This is called a counting semaphore. 

sem_t slots;
sem_init(&slots, 0, 3);  /* 3 slots */
sem_wait(&slots);
/* at most 3 threads here */
sem_post(&slots);

The POSIX semaphore API

#include <semaphore.h>

sem_t sem;
sem_init(&sem, 0, initial_value);   /* 0 = process-private */

sem_wait(&sem);                     /* P / down */
sem_trywait(&sem);                  /* non-blocking version */
sem_post(&sem);                     /* V / up */
sem_getvalue(&sem, &val);           /* read current value */

sem_destroy(&sem);

Unix-style systems also provide named semaphores accessible across processes through the file system, but anonymous semaphores (initialized with sem_init) are what you use inside a single process.

Semaphores as a signaling mechanism

Where semaphores really shine is ordering work between threads. Unlike a mutex, which only guarantees mutual exclusion, a semaphore can be used to force one thread to run before another.

Consider a scenario: thread A must fully initialize a resource before thread B may use it. Thread B doesn't know how long initialization will take, and thread A doesn't know when B wants to start. 

sem_t initialized;
sem_init(&initialized, 0, 0);   /* initially "unsignaled" */

/* Thread A — producer of the signal */
do_heavy_init();
sem_post(&initialized);         /* signal "init done" */

/* Thread B — consumer of the signal */
sem_wait(&initialized);         /* block until signaled */
use_resource();
The key insight: because the semaphore starts at 0, thread B will block on sem_wait until thread A has called sem_post. This gives us a way to enforce ordering between threads — something a mutex alone cannot do.

4.4 · Condition Variables

Locks give us mutual exclusion. Semaphores give us counters and signaling. But neither is quite right for the most common pattern in concurrent code: "wait until some condition becomes true, then continue."

That pattern — waiting for a condition — is what condition variables are for. They are almost always used together with a mutex, and the pair is what makes coordinated waiting correct.

The interface

#include <pthread.h>

pthread_cond_t cond = PTHREAD_COND_INITIALIZER;
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

/* Wait until someone signals the condition */
pthread_cond_wait(&cond, &mutex);

/* Wake one waiting thread */
pthread_cond_signal(&cond);

/* Wake all waiting threads */
pthread_cond_broadcast(&cond);

The magic of pthread_cond_wait

pthread_cond_wait is not an ordinary wait. Its contract is precise, and it is essential to understand what it does atomically:

  1. Release the mutex.
  2. Block until the condition is signaled.
  3. Re-acquire the mutex before returning.

The first two steps happen atomically — there is no window during which the thread has released the mutex but is not yet actually waiting. This atomicity is what makes condition variables correct: without it, a signal sent between "release the lock" and "start waiting" would be lost.

You must always call pthread_cond_wait with the mutex held. If you don't, the atomic release-and-wait protocol is broken, and you may lose wakeups or corrupt the mutex state.

The canonical wait-while pattern

Here is the pattern you should use every time you wait on a condition variable: 

pthread_mutex_lock(&mutex);

/* ALWAYS use while, never if! */
while (!condition_is_true()) {
    pthread_cond_wait(&cond, &mutex);
}

/* Now the condition holds, and we hold the lock. */
do_something_that_requires_the_condition();

pthread_mutex_unlock(&mutex);

The producer — the thread that makes the condition true — signals after modifying the shared state: 

pthread_mutex_lock(&mutex);

make_condition_true();

pthread_cond_signal(&cond);    /* or broadcast */

pthread_mutex_unlock(&mutex);

Why while and not if?

This is one of the most-asked questions in concurrency, and the answer has three parts.

Spurious wakeups

POSIX explicitly allows pthread_cond_wait to return even without a signal. This is called a spurious wakeup, and it can happen on real systems for various low-level reasons. With if, you would proceed as if the condition were true; with while, you loop and check again.

Multiple waiters

If three threads are waiting on the same condition, and only one condition "slot" is available, pthread_cond_signal wakes exactly one. That one consumes the resource. The other two, if woken later, would find no resource — while loops them back to sleep. if would let them proceed and corrupt state.

The condition can be false again

Even a properly-signaled wakeup may find the condition false again, if another thread "stole" the resource between the signal and this thread acquiring the mutex. Only by re-checking in a loop do we handle this safely.

Rule to memorize: always wrap pthread_cond_wait in a while loop that re-checks the predicate. If you use if, your code may appear to work in testing and fail catastrophically in production.

signal vs broadcast

Primitive Meaning When to use
pthread_cond_signal Wake at most one waiting thread. When any waiting thread can make progress — e.g., one item was added to a queue.
pthread_cond_broadcast Wake all waiting threads. When the state change is relevant to many threads — e.g., shutting down, or the queue was resized.

Broadcasting is safer (you never accidentally miss a thread that needs to wake) but less efficient — every waiter wakes up, contends for the mutex, and most go right back to sleep. Signal is more efficient but requires you to be sure exactly one waiter needs to run.

4.5 · Classic Problems

Three classic problems appear in every operating systems course, every systems textbook, and every job interview. They capture the essence of synchronization, and their solutions are used in real code every day.

The Producer–Consumer Problem (Bounded Buffer)

One or more producer threads generate items and place them in a shared buffer of fixed size. One or more consumer threads take items out. The rules are:

  • A producer must wait if the buffer is full.
  • A consumer must wait if the buffer is empty.
  • No producer and no consumer should ever corrupt the buffer state.

This pattern is literally everywhere: web servers reading network requests, video players decoding frames, databases flushing write-ahead logs, operating systems moving data between disks and memory. If you understand Producer–Consumer, you understand the heart of concurrent systems.

A solution with mutex + condition variables

#define BUF_SIZE 8

typedef struct {
    int items[BUF_SIZE];
    int count;             /* current number of items */
    int in, out;           /* next write / read index */

    pthread_mutex_t mutex;
    pthread_cond_t  not_full;
    pthread_cond_t  not_empty;
} bounded_buffer_t;

void bb_init(bounded_buffer_t *bb) {
    bb->count = bb->in = bb->out = 0;
    pthread_mutex_init(&bb->mutex, NULL);
    pthread_cond_init(&bb->not_full, NULL);
    pthread_cond_init(&bb->not_empty, NULL);
}

void bb_put(bounded_buffer_t *bb, int value) {
    pthread_mutex_lock(&bb->mutex);

    while (bb->count == BUF_SIZE) {
        pthread_cond_wait(&bb->not_full, &bb->mutex);
    }

    bb->items[bb->in] = value;
    bb->in = (bb->in + 1) % BUF_SIZE;
    bb->count++;

    pthread_cond_signal(&bb->not_empty);
    pthread_mutex_unlock(&bb->mutex);
}

int bb_get(bounded_buffer_t *bb) {
    pthread_mutex_lock(&bb->mutex);

    while (bb->count == 0) {
        pthread_cond_wait(&bb->not_empty, &bb->mutex);
    }

    int value = bb->items[bb->out];
    bb->out = (bb->out + 1) % BUF_SIZE;
    bb->count--;

    pthread_cond_signal(&bb->not_full);
    pthread_mutex_unlock(&bb->mutex);

    return value;
}
Notice the pattern: one mutex protects the shared state, and two condition variables represent the two events we can wait for — buffer became non-empty and buffer became non-full. This is the canonical solution and worth memorizing.

The Reader–Writer Problem

A shared data structure — say, a database or an in-memory cache — is accessed by two kinds of threads:

  • Readers want to read the current value. Multiple readers can be active at the same time without conflict.
  • Writers want to change the value. A writer must be completely alone — no other reader or writer can be active while it runs.

The rule is: many readers, or one writer, but never a mix. This pattern is common in databases and caches, where reads vastly outnumber writes.

Variant Rule Potential issue
Reader-priority Writers wait until no readers are active. Readers can always enter. Writer starvation if readers keep arriving.
Writer-priority Once a writer is waiting, no new readers are admitted. Reader starvation if writers keep arriving.
Fair (FIFO) Arrival order is respected, regardless of type. Slightly more complex to implement.

On Linux, the same guarantee is provided by pthread_rwlock_t — a ready-made reader-writer lock you can use instead of building your own. 

pthread_rwlock_t rwlock = PTHREAD_RWLOCK_INITIALIZER;

pthread_rwlock_rdlock(&rwlock);   /* many readers can hold this */
   read_shared_data();
pthread_rwlock_unlock(&rwlock);

pthread_rwlock_wrlock(&rwlock);   /* exclusive */
   modify_shared_data();
pthread_rwlock_unlock(&rwlock);

The Dining Philosophers

Five philosophers sit around a round table. Between each pair of neighbors lies one fork — five forks total. Each philosopher needs two forks to eat. They alternate between thinking and eating. The problem: design a protocol so that no philosopher starves.

The philosophers represent processes, the forks represent shared resources, and the problem abstracts the pattern of grabbing multiple shared resources. Naïve solutions lead to deadlock — every philosopher grabs their left fork and waits forever for their right.

We will study deadlock prevention and the Dining Philosophers in detail in Week 6. For now, remember the pattern: whenever a thread must acquire two or more locks, the order of acquisition matters, and getting it wrong leads to deadlock.

Lock ordering rule: if two locks A and B must both be acquired, every thread that acquires both must acquire them in the same order — A then B, or B then A, but never mixed. This single discipline prevents the most common form of deadlock.

4.6 · Monitors and Modern Languages

Directly managing mutexes and condition variables is fragile. It's easy to forget an unlock, use the wrong variable in a while, or introduce a subtle lock-ordering bug. In the 1970s, computer scientists Tony Hoare and Per Brinch Hansen proposed a higher-level abstraction to make this safe: the monitor.

What is a monitor?

A monitor is a programming-language construct that bundles:

  • Shared data (the state of the monitor).
  • Procedures that operate on that data.
  • A mutex that the language automatically acquires on entry to any procedure, and releases on exit.
  • Condition variables associated with the monitor for waiting and signaling.

The crucial part: the programmer never writes lock or unlock. The language guarantees that only one thread is inside any monitor procedure at a time. This removes the entire class of "forgot to unlock" bugs by construction.

The shift in thinking: instead of "protect this data with a mutex I manage", you write "here is a piece of data with its own procedures, and the language protects it". It is synchronization by language design, not by programmer discipline.

Monitors in modern languages

Every one of these features is a monitor in disguise:

Language Construct Notes
Java synchronized methods and blocks; wait() and notify() on Object. Every Java object is a monitor with an implicit lock.
C# lock statement; Monitor.Wait / Monitor.Pulse. Very similar to Java.
Python threading.Lock, threading.Condition. GIL limits real parallelism but monitors work as expected.
Go Channels (chan) plus sync.Mutex and sync.Cond. Channels embody a different philosophy — communication instead of shared state.
Rust Mutex<T> that owns the data it protects. The type system enforces that you cannot access the data without holding the lock.

The Rust philosophy: encode correctness in the type system

Rust takes monitors to their logical conclusion. In Rust, a Mutex<T> is a container that owns the data it protects. You literally cannot access the data except by locking the mutex — the compiler will not let you. There is no way to "forget to lock", because the code would not compile. 

use std::sync::Mutex;

let counter = Mutex::new(0);   // the mutex owns the data

{
    let mut guard = counter.lock().unwrap();
    *guard += 1;                // must go through the guard
}
// guard drops here — the lock is automatically released

Notice that there is no unlock call — Rust's RAII drops the guard when it goes out of scope, automatically releasing the lock. This is how the type system makes an entire class of bugs impossible.

The lesson for beginners: whenever you write C with pthreads, remember that you are doing manually what modern languages do automatically. Every pthread_mutex_lock must have a matching unlock on every code path. Every cond_wait must sit inside a while. The languages that do this for you exist because humans forget.

4.7 · Touch Lab — Producer–Consumer in C

Now let's put everything together. We will write a real, working Producer–Consumer program using pthread_mutex and pthread_cond. This is the exact pattern used inside real servers, buffers, and thread pools.

Step 1 — Create the source file

$ nano prodcons.c

Paste the following code:

#include <stdio.h>
#include <pthread.h>
#include <stdlib.h>
#include <unistd.h>

#define BUF_SIZE   8
#define N_ITEMS    20

typedef struct {
    int items[BUF_SIZE];
    int count, in, out;

    pthread_mutex_t mutex;
    pthread_cond_t  not_full;
    pthread_cond_t  not_empty;
} buffer_t;

static buffer_t buf;

void bb_init(buffer_t *bb) {
    bb->count = bb->in = bb->out = 0;
    pthread_mutex_init(&bb->mutex, NULL);
    pthread_cond_init(&bb->not_full, NULL);
    pthread_cond_init(&bb->not_empty, NULL);
}

void bb_put(buffer_t *bb, int value) {
    pthread_mutex_lock(&bb->mutex);
    while (bb->count == BUF_SIZE) {
        pthread_cond_wait(&bb->not_full, &bb->mutex);
    }
    bb->items[bb->in] = value;
    bb->in = (bb->in + 1) % BUF_SIZE;
    bb->count++;
    printf("[PRODUCER] put %2d  (count=%d)\n", value, bb->count);
    pthread_cond_signal(&bb->not_empty);
    pthread_mutex_unlock(&bb->mutex);
}

int bb_get(buffer_t *bb) {
    pthread_mutex_lock(&bb->mutex);
    while (bb->count == 0) {
        pthread_cond_wait(&bb->not_empty, &bb->mutex);
    }
    int value = bb->items[bb->out];
    bb->out = (bb->out + 1) % BUF_SIZE;
    bb->count--;
    printf("[CONSUMER] got %2d  (count=%d)\n", value, bb->count);
    pthread_cond_signal(&bb->not_full);
    pthread_mutex_unlock(&bb->mutex);
    return value;
}

void *producer(void *arg) {
    for (int i = 1; i <= N_ITEMS; i++) {
        bb_put(&buf, i);
        usleep(50000);   /* 50 ms — simulate producing */
    }
    return NULL;
}

void *consumer(void *arg) {
    for (int i = 0; i < N_ITEMS; i++) {
        int v = bb_get(&buf);
        usleep(80000);   /* 80 ms — simulate consuming */
        (void)v;
    }
    return NULL;
}

int main(void) {
    pthread_t t_prod, t_cons;

    bb_init(&buf);

    pthread_create(&t_prod, NULL, producer, NULL);
    pthread_create(&t_cons, NULL, consumer, NULL);

    pthread_join(t_prod, NULL);
    pthread_join(t_cons, NULL);

    pthread_mutex_destroy(&buf.mutex);
    pthread_cond_destroy(&buf.not_full);
    pthread_cond_destroy(&buf.not_empty);

    printf("\nDone. Everything consumed cleanly.\n");
    return 0;
}

Step 2 — Compile

$ gcc -Wall -pthread -o prodcons prodcons.c

Step 3 — Run it

$ ./prodcons
[PRODUCER] put  1  (count=1)
[CONSUMER] got  1  (count=0)
[PRODUCER] put  2  (count=1)
[PRODUCER] put  3  (count=2)
[CONSUMER] got  2  (count=1)
...
[PRODUCER] put 20  (count=1)
[CONSUMER] got 20  (count=0)

Done. Everything consumed cleanly.

Everything is deterministic in outcome, even though the interleaving is not. Every item produced is exactly one item consumed. The buffer never overflows or underflows. The program always terminates cleanly with the same final line.

Try to break it: run the program ten times in a row. Every run must end with the same "Done" message and the same total count of puts and gets. If it ever hangs or crashes, you have found a bug — and the diagnosis will teach you something. This is exactly how production-quality code is validated: by running it again and again under stress.

Experiment: what happens if you use `if` instead of `while`?

Open the file and change the two while loops to if statements. Recompile and run it several times. You may observe:

  • Buffer underflow — the consumer reads a slot that has never been written.
  • Buffer overflow — the producer overwrites a slot before it is consumed.
  • Occasional hangs — the program sits forever because one side missed its wakeup.

This is a powerful demonstration of why the while loop is not optional. It is not defensive coding — it is necessary for correctness.

4.8 · Touch Lab — Debugging with Helgrind

Manually inspecting concurrent code for race conditions is unreliable — even experts miss bugs that only appear once in ten million executions. This is where dynamic analysis tools come in. The most widely used tool for concurrency bugs in C is Helgrind, part of the Valgrind suite.

Installing Valgrind

$ sudo apt update
$ sudo apt install valgrind
$ valgrind --version
valgrind-3.22.0

Running Helgrind on a correct program

Let's use our corrected counter from section 4.2 — the one with the mutex — to verify that Helgrind finds nothing wrong: 

$ valgrind --tool=helgrind ./counter_mutex
...

==12345== Using Valgrind-3.22.0 and LibVEX; rerun with -h for copyright info

counter = 200000  (expected 200000)

==12345== For lists of detected and suppressed errors, rerun with: -s
==12345== ERROR SUMMARY: 0 errors from 0 contexts (suppressed: 0 from 0)

The line we care about is at the very bottom: 0 errors from 0 contexts. Helgrind has checked for lock ordering issues, data races, and misuses of synchronization primitives — and found nothing. Our code is correct.

Running Helgrind on a buggy program

Now let's deliberately remove the mutex — the classic race condition from Week 3 — and see what Helgrind reports: 

$ valgrind --tool=helgrind ./counter_nomutex
...
==12345== Possible data race during write of size 8 at 0x... by thread #3
==12345==    at 0x10916B: worker (counter_nomutex.c:10)
==12345==    by 0x483F9C8: start_thread (pthread_create.c:470)

==12345==

==12345==
==12345== ERROR SUMMARY: 13762 errors from 2 contexts ...

The output tells you clearly what happened:

  • Possible data race during write of size 8 — Helgrind noticed two threads writing to the same address without synchronization.
  • worker (counter_nomutex.c:10) — the exact source file and line number of the problematic access.
  • 13762 errors — the actual number of unsynchronized accesses observed during the run.
  • counter = 143982 — the program itself produced the wrong result, confirming that Helgrind is not just paranoid — it caught a real bug.
Even one error is too many. A program with even a single Helgrind-reported race is not correct. It may run fine for a million executions and corrupt memory on the million-and-first. Never ship code that fails Helgrind.

Understanding Helgrind's limitations

Helgrind is extremely valuable but not omniscient. Be aware of these limitations:

  • It can only detect races it actually observes. If the buggy interleaving does not occur during your test run, Helgrind will not report it. This is why we run test programs many times, on many machines, with different workloads.
  • It cannot detect misused locks directly. It reports improper lock ordering, but it cannot know that you are holding the "wrong" lock for a given piece of data.
  • It slows execution by 20–100×. Not something you leave running on production code. It is a debugging tool, not a runtime monitor.
  • It has false positives. Some correct code, like lock-free algorithms, may trigger Helgrind warnings because the tool cannot track the correctness of the pattern. Annotations exist to help with these cases.

Helgrind vs other tools

Tool Purpose Command
Helgrind Data races, lock ordering, synchronization misuse. valgrind --tool=helgrind ./prog
DRD Alternative race detector, sometimes detects different bugs. valgrind --tool=drd ./prog
ThreadSanitizer Similar to Helgrind, but compiled into the program — much faster. gcc -fsanitize=thread -g ./prog.c
AddressSanitizer Detects memory errors — not concurrency-specific, but useful together. gcc -fsanitize=address -g ./prog.c

In practice, serious development uses ThreadSanitizer (TSan) more often than Helgrind because it is 10–20× faster and can be integrated into continuous integration. But Helgrind is bundled with Valgrind, works on compiled programs without recompilation, and is the standard tool when you need to inspect an already-built binary.

Practice exercise: audit your own code

  1. Take the Producer–Consumer program from the previous lab. Run it under Helgrind: valgrind --tool=helgrind ./prodcons
  2. Confirm the corrected version reports zero errors.
  3. Modify the code to make a mistake — for example, switch one while to if. Run Helgrind again. Note that Helgrind may not directly detect the logic error (because the code is still "synchronized" technically), but pthread_cond misuse sometimes shows up as lock order violated or similar warnings.
  4. Modify the code further — for example, remove the mutex entirely. Observe how Helgrind now reports races on every access to the shared count, the buffer array, and every other piece of shared state.
Why this matters: writing correct concurrent code is hard. Every professional systems programmer uses a race detector as a routine part of their workflow. Adding valgrind --tool=helgrind to your testing process will save you days of mysterious bug hunting.

Week 4 Summary

  • Race conditions occur when two threads access shared data without synchronization. The three requirements of any correct solution are mutual exclusion, progress, and bounded waiting.
  • Locks (mutexes) provide mutual exclusion. Built on hardware atomic primitives like test-and-set and compare-and-swap. Use pthread_mutex_lock and pthread_mutex_unlock — always paired, always balanced.
  • Semaphores are counters with atomic wait/post operations. Can act as locks (init=1) or as counting mechanisms (init=N). Excellent for signaling and resource counting.
  • Condition variables let threads wait for a predicate to become true. Must always be used with a mutex. Always check the condition in a while loop.
  • Producer–Consumer is solved with one mutex and two condition variables — not_full and not_empty. This pattern is the heart of most concurrent systems.
  • Reader–Writer allows many readers or one writer. Provided by the OS as pthread_rwlock_t.
  • Monitors are a language-level abstraction that bundles data, procedures, and locking. Java's synchronized, Rust's Mutex<T>, and Go's channels are modern descendants.
  • Helgrind — valgrind --tool=helgrind — detects data races and synchronization misuse. Essential for any serious concurrent code.
