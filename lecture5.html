5.1 · Why Scheduling Matters

In the last four weeks, we built up a stack of abstractions: the OS as resource manager, the process as an isolated unit of execution, the thread as a lightweight unit of parallelism, and locks, semaphores, and condition variables as tools for making concurrent code correct. There is one crucial piece missing. We have never asked: when there are more runnable threads than CPUs, who actually gets to run?

That question is the entire subject of CPU scheduling. It sounds simple, but it lies at the heart of every performance complaint you will ever hear about a computer — a sluggish UI, a slow build, a server that drops connections under load. All of these are, at bottom, consequences of scheduling decisions made billions of times per second by the kernel.

One-sentence definition: the CPU scheduler is the part of the kernel that decides which ready thread runs next on each CPU core, and how long it is allowed to run before being preempted.

The scheduling problem in context

Imagine a system with a single CPU core and three runnable threads, all wanting nothing more than to run to completion. The scheduler has to answer two questions:

  • Which one runs first? This determines the order of completion.
  • How long does each one run before being preempted? This determines whether a thread is interrupted mid-work or allowed to finish.

Different answers to those two questions produce dramatically different performance, fairness, and responsiveness — and different workloads demand different answers. A batch processing machine at a financial firm wants maximum throughput; a smartphone wants minimum response time to touches; a scientific cluster wants fairness under heavy load; a real-time system needs guaranteed deadlines. No single scheduler wins everywhere.

Preemptive vs non-preemptive

Before comparing algorithms, we need one key distinction.

Non-preemptive

Once a thread starts running on a CPU, it keeps running until it either finishes, blocks on I/O, or voluntarily calls sched_yield(). The scheduler has no power to take the CPU away from a running thread. Simple to implement, but a poorly behaved thread can hog the CPU indefinitely.

Preemptive

The scheduler can interrupt a running thread at any moment — typically at the end of a time slice (also called a time quantum) driven by a periodic timer interrupt. This is what every modern general-purpose OS uses. It guarantees fairness, at the cost of more context switches.

Which is right? All modern desktop, server, and mobile operating systems use preemptive scheduling. Non-preemptive schedulers appear only in tiny embedded systems and in historical batch operating systems.
Non-preemptive scheduling lets each thread finish uninterrupted. Preemptive scheduling chops execution into time slices, allowing fair interleaving.

Where does the scheduler run?

The scheduler is just a piece of kernel code. It gets invoked in a few situations:

  • A thread blocks. If a thread issues a syscall that cannot complete immediately (reading a file, waiting on a mutex), it moves to Waiting and the CPU is free. The scheduler picks someone else.
  • A thread becomes ready. When an interrupt fires — the timer tick, a disk completing I/O, a network packet arriving — a waiting thread may become runnable. The scheduler may preempt the current thread if the new one is more urgent.
  • A thread finishes. Nothing to schedule — but the scheduler must still pick the next thread to run.
  • The time slice ends. A periodic timer interrupt fires and the scheduler checks whether the running thread has consumed its quantum. If yes, it preempts and picks the next one.

The first and third cases are unavoidable. The second and fourth are where scheduler design actually matters — they are the moments when the scheduler must decide.

5.2 · Scheduling Criteria & Metrics

Before we can compare algorithms, we need ways to measure them. The literature and the textbooks use a standard set of metrics. Learn these — they appear in every exam question about scheduling.

Metric Definition What optimises it
Arrival time The moment a thread first becomes ready to run. Not controllable — it is an input.
Burst time How long the thread needs on the CPU to finish, if it ran uninterrupted. Usually estimated from history.
Completion time The moment the thread finishes. Depends on the algorithm.
Turnaround time completion − arrival. The total time from when a thread was submitted to when it finished. Minimised by Shortest-Job-First family.
Waiting time The total time the thread spent in the ready queue, not running. Minimised by SJF for the average case.
Response time first_run − arrival. How long the user waited before the system did anything. Minimised by Round Robin.
Throughput How many threads the system completes per unit of time. Maximised by minimising context switches and idle time.
CPU utilisation Percentage of time the CPU is doing useful work. High utilisation means good scheduling for batch workloads.
The most important distinction: turnaround time and response time optimise very different things. Turnaround measures total time to completion; response measures how long until the user sees the first sign of life. Batch jobs want low turnaround; interactive systems want low response. These two goals are often in direct conflict.

Worked example — always use a Gantt chart

Throughout this week, when we compare algorithms, we will do so on the same workload so the differences are real. Here is our standard test workload — four threads, all arriving at t = 0:

Thread Arrival Burst Notes
P1 0 20 Long job
P2 0 5 Short job
P3 0 3 Very short
P4 0 8 Medium

All four arrive simultaneously. The algorithm decides the order in which they execute. We will compute average waiting time and average turnaround time for each algorithm so you can see exactly how much the choice matters.

5.3 · Classical Algorithms: FCFS, SJF, SRTF

The three simplest policies were described in the 1960s and are still the vocabulary of every scheduling discussion. Everyone knows their names; every interview asks about them.

FCFS — First Come, First Served

The simplest possible policy. Threads are placed in a FIFO queue. When the CPU becomes available, the thread at the front runs — and keeps running until it finishes or blocks. This is a non-preemptive algorithm.

On our test workload, the order is P1, P2, P3, P4 because they all arrived simultaneously and FCFS breaks ties by thread order.

FCFS: P1 runs first, blocking everyone else for its full 20-unit burst.

Computing the metrics:

Thread Burst Waiting Completion Turnaround
P12002020
P25202525
P33252828
P48283636
Average 18.25 27.25

The problem with FCFS is obvious from this table: the short jobs wait behind the long job. This is called the convoy effect — a single long-running job delays everything behind it, even though the job could have been deferred. FCFS has the property that its average waiting time depends heavily on the order of arrival; a single heavy job at the front can triple the average latency.

The convoy effect: imagine a supermarket with one checkout lane and one customer whose cart contains a hundred items. Every customer behind them waits, even if they are only buying a bottle of water. FCFS produces exactly this behaviour. That is why no real OS uses it for general-purpose scheduling.

SJF — Shortest Job First

The fix is straightforward. When the CPU becomes free, pick the ready thread with the shortest burst time. This minimises the average waiting time — a result provable mathematically for any fixed set of jobs whose burst times are known in advance.

On our workload, the order becomes P3 (3), P2 (5), P4 (8), P1 (20):

Thread Burst Waiting Completion Turnaround
P33033
P25388
P4881616
P120163636
Average 6.75 15.75

Average waiting time fell from 18.25 to 6.75. This is not a small improvement — it is a factor of nearly three. SJF is provably optimal for minimising average waiting time on a fixed workload, and this is one of the classic results of operating systems theory.

The catch — and it is a big one: SJF needs to know the burst time of each thread in advance. Real operating systems do not have that information. We can only estimate it, usually by averaging recent CPU usage from a thread's history. This is called exponential averaging, and it is what real schedulers use as a heuristic.

SRTF — Shortest Remaining Time First

SRTF is the preemptive version of SJF. When a new thread arrives, its remaining burst time is compared against the running thread's remaining burst time. If the new one needs less, the current thread is preempted. This is the theoretically optimal algorithm for average waiting time, under the same unrealistic assumption that burst times are known in advance.

Another problem: starvation. A thread with a long burst time may never run if short threads keep arriving. This becomes acute in an interactive system where user threads are short and a background job is long.

Algorithm Preemptive? Optimal for Main problem
FCFS No Simplicity Convoy effect — terrible for interactive loads
SJF No Average waiting time Burst times unknown; starves long threads
SRTF Yes Average waiting time (preemptive) Same as SJF, plus starvation is worse

5.4 · Round Robin & Priority Scheduling

FCFS, SJF, and SRTF all optimise average statistics — but average turnaround is not what a user of an interactive computer experiences. When you type a keystroke and wait for a character to appear, you care about response time — how long until the system does something. For that, we need a very different policy.

Round Robin

Round Robin assigns each thread a fixed time slice — typically 1 to 100 milliseconds in a real system. Ready threads are arranged in a circular queue. The scheduler runs the front of the queue for at most one slice; if the thread is not finished, it goes to the back again.

With a time slice of, say, 4 units and our workload, the execution looks like this: 

P1 (0-4)  P2 (4-8)  P3 (8-11, done)  P4 (11-15)
P1 (15-19)  P2 (19-23, done)  P4 (23-27)  P1 (27-31)
P4 (31-35, done)  P1 (35-39)

Every thread gets serviced within the first slice of its neighbor — no thread waits behind a long job. Average turnaround suffers compared to SJF, but response time is dramatically better. This is why Round Robin is the base of every general-purpose OS scheduler.

Small time slice

  • Lower response time — every thread gets the CPU quickly.
  • Better timesharing fairness.
  • But more context switches — overhead grows.

Large time slice

  • Fewer context switches — better throughput.
  • But a thread that arrives just after a slice start waits a full quantum.
  • Behaviour approaches FCFS as the slice grows.

The choice of time slice is a careful trade-off. On typical Linux systems it is on the order of a few milliseconds, and it is dynamically adjusted — a key feature of modern schedulers we will see shortly.

Priority Scheduling

Round Robin treats all threads equally. But real systems want to express "this thread is more important than that one". Priority scheduling attaches an integer priority to each thread and always runs the highest-priority ready one.

  • Priorities may be preemptive (a newly-ready higher-priority thread immediately preempts the running one) or non-preemptive (the running thread finishes its slice first).
  • In most systems, lower numbers mean higher priority — this is the Linux convention.
  • Priority can be static (set by the administrator or by the thread itself) or dynamic (adjusted by the kernel based on behavior — e.g., I/O-bound threads get a boost).
Starvation and aging: priority scheduling has one famous failure mode — a low-priority thread may never run if higher-priority threads keep arriving. The fix is called aging: the kernel gradually increases the priority of threads that have been waiting a long time, so that no thread waits forever. This is used in every production scheduler.

Priority in the real world

Every operating system exposes some form of priority to user space:

Platform Priority mechanism
Linux — nice value Each thread has a nice value from −20 (highest) to +19 (lowest). Changing it requires privileges for decreases below 0. Higher nice = "nicer to others" = less CPU.
Linux — real-time SCHED_FIFO and SCHED_RR offer real-time priorities from 1 to 99. Used only for latency-critical threads.
Windows Priority classes 0–31. The REALTIME_PRIORITY_CLASS and thread priority boosts for I/O-bound threads.
macOS / iOS Quality of Service classes (User Interactive, User Initiated, Utility, Background). The user never sees raw numbers.

Modern operating systems hide the raw priority model behind simpler abstractions (QoS classes, cgroups, scheduling policies selected by role). The idea — a thread's importance can be expressed and the scheduler uses it — is universal.

5.5 · Multi-Level Feedback Queue (MLFQ)

All the algorithms so far need to know something they usually cannot know: whether a thread is CPU-bound or I/O-bound, short or long, interactive or batch. SJF needs burst times. Priority scheduling needs priorities. Neither is reliably available in advance.

The Multi-Level Feedback Queue — MLFQ — sidesteps the problem entirely. Instead of being told what kind of thread each one is, the scheduler infers it from behaviour. Threads that yield often (interactive, I/O-bound) are treated as important; threads that hold the CPU for full slices (CPU-bound) are demoted. The scheduler learns the workload.

The structure

MLFQ uses several queues, each with its own priority and time slice. New threads start in the highest queue; long-running threads sink to lower ones.

The rules (in their simplest form)

  1. New threads go to the highest queue (Q0). We assume each thread starts out interactive until proven otherwise.
  2. The scheduler always prefers higher-priority queues. Only if Q0 is empty does it consider Q1, then Q2, and so on. Round Robin runs within each queue.
  3. If a thread uses its entire time slice, it is demoted — moved to the queue below it. This punishes threads that are truly CPU-bound.
  4. If a thread yields the CPU before its slice ends — typically because it is waiting for I/O, waiting on a lock, or simply being interactive — it stays at its current level, or is even promoted in some variants.

Priority boost — the anti-starvation rule

With just those four rules, MLFQ would eventually starve threads that sank to the lowest queue. If a long CPU-bound job lands in Q3, and new interactive jobs keep filling Q0, the long job never runs. Real MLFQ adds one more rule:

  1. After a fixed period of time — say, every second of CPU time — every thread is moved back to the top queue. This prevents starvation and adapts to changing thread behaviour.
The cleverness of MLFQ: the OS does not need to know whether a thread is interactive or CPU-bound. It learns it. If the thread yields often, it keeps running at the top. If it hogs the CPU, it sinks. The behavior of the thread determines its own priority, without any explicit classification.

MLFQ in practice

MLFQ-style schedulers have been used in Windows, Solaris, and BSD for decades. Linux's O(1) scheduler — used from 2.6 through 2.6.22 — was a form of MLFQ. Even the modern CFS, which we will look at next, is philosophically descended from MLFQ's idea that the scheduler should infer behaviour rather than require explicit classification.

5.6 · Linux CFS — The Completely Fair Scheduler

Modern Linux does not use MLFQ. Since kernel version 2.6.23 (2007), the default scheduler is the Completely Fair Scheduler — CFS. It is worth studying because it is a genuinely different approach to scheduling, and because it tells you something important about Linux's design philosophy.

The core idea — virtual runtime

CFS does not assign explicit priorities or time slices. Instead, it tracks one number per thread: virtual runtime — usually written vruntime. Virtual runtime is the total CPU time the thread has consumed, weighted by its priority. A thread with a high priority accrues virtual runtime more slowly than a low-priority thread.

The scheduler's rule is beautifully simple: always run the thread with the smallest virtual runtime. That is it. The thread that has had the least CPU relative to its priority runs next.

The insight: no explicit time slice, no priority queue, no aging. Just a single comparison — "whose vruntime is smallest?" — executed billions of times per second. The result is a system that is very nearly fair, and that scales from a Raspberry Pi to a supercomputer without redesign.
CFS maintains runnable threads in a red-black tree sorted by virtual runtime. The leftmost node is always the thread to run next — an O(log n) operation.

How the tree helps — and why it scales

CFS maintains its runnable threads in a red-black tree. It is a self-balancing binary search tree, which guarantees O(log n) insert, delete, and leftmost-node lookup. That is why CFS scales smoothly from a handful of threads to tens of thousands.

When a thread runs for a while, its vruntime increases. When it is preempted, it is re-inserted into the tree at its new vruntime. When the scheduler needs the next thread, it takes the leftmost node. No linear scans, no priority queues, no time slices — a single, elegant structure doing all the work.

The scheduler latency parameter

Though CFS has no fixed time slice, it does have a target called sched_latency — typically 6 milliseconds on desktop systems. The idea: the scheduler tries to run every runnable thread at least once within that window. If there are n runnable threads, each gets sched_latency / n of CPU time.

When n grows large, the per-thread slice would become too small for efficiency (context switches would dominate). CFS protects against this with min_granularity — often 0.75 ms. If the calculated slice falls below this value, it clamps it. The scheduler latency and the minimum granularity together determine the actual time slice each thread receives.

CFS scales its time slice dynamically: fewer threads means longer slices, but a minimum granularity prevents slices from becoming too short to be efficient.

Nice values, weighted by CFS

CFS does not ignore priority — it interprets it as a weight affecting how fast vruntime grows. A thread with a nice value of −5 has a much larger weight than a thread with nice +5. This means it can stay ahead of the lower-priority thread in the tree for longer, even though both accumulate wall-clock CPU time at the same rate.

In practice, changing a thread's nice value by 5 points roughly multiplies its CPU share by a known factor — that is the whole point of the nice scale. A thread with nice 0 gets a base share. A thread with nice −10 gets more CPU; a thread with nice +10 gets less.

Why the name "completely fair"? In the limit where every thread has the same nice value, CFS gives every thread exactly the same share of CPU time — regardless of when it arrived, how long it has been running, or what it is doing. Fairness is the default; any priority difference is a purposeful deviation from that baseline.

5.7 · Touch Lab — Priority in Practice with nice & chrt

Let's now touch the scheduler from user space. Linux exposes its scheduling priorities through two commands: nice for ordinary threads, and chrt for real-time policies. We will use both, and we will verify the effect with top.

Step 1 — Inspect your current nice value

$ nice
0

$ ps -o pid,ni,pri,comm -p $$
PID    NI  PRI COMMAND
4523    0   19 bash

The NI column is the nice value — 0 by default. The PRI column shows the kernel's internal priority — a number derived from nice. Lower PRI means higher priority.

Step 2 — Start a CPU-intensive job at the default priority

$ yes > /dev/null &
[1] 4700

The yes command prints y characters forever — but by redirecting the output to /dev/null, we just made it a pure CPU hog. It runs at nice 0.

Step 3 — Start a CPU-intensive job at a lower priority

$ nice -n 19 yes > /dev/null &
[2] 4701

This second yes runs at nice 19 — the lowest possible priority. If the scheduler does its job, this one gets dramatically less CPU time than the first.

Step 4 — Observe the difference in top

$ top -p 4700,4701

  PID USER   PR  NI    %CPU  TIME+    COMMAND
 4700 student 20  0   99.7  0:15.23  yes
 4701 student 39 19    4.3  0:00.68  yes

Look carefully at the numbers:

  • %CPU — the first thread is using about 100% of a core. The second is using about 4%. The scheduler is giving the first thread almost all the CPU.
  • NI — the nice values differ: 0 vs 19.
  • PR — the kernel's reported priority: 20 vs 39. Lower is higher priority. The 19 point difference in nice corresponds to a 19 point difference in PR — this is the base of the Linux nice model.
What you are seeing: the two yes processes are trying to run exactly as often. The scheduler is honouring the nice values, so the first one wins the CPU far more often. Try running only one yes, then starting a second at nice 0 — the two will split the CPU roughly evenly. Then change one to nice 19 and watch it collapse.

Step 5 — Change a running process's nice value

$ sudo renice -n 10 -p 4700
4700 (process ID) old priority 0, new priority 10

The first yes now runs at nice 10. Its CPU share will shift slightly. Note that lowering priority (increasing the nice number) does not require root — it is the safe direction. Raising priority (decreasing the nice number, or going negative) requires sudo, because otherwise any user could starve the system.

Step 6 — Real-time scheduling with chrt

$ chrt -p $$
pid 4523's current scheduling policy: SCHED_OTHER
pid 4523's current scheduling priority: 0

chrt is the tool for inspecting and setting a process's scheduling policy. Let's see the options:

  • SCHED_OTHER — the default. This is what almost everything uses, and it is the CFS policy.
  • SCHED_BATCH — for non-interactive CPU-bound threads. Tells CFS to allow longer slices and less frequent preemption.
  • SCHED_IDLE — runs only when nothing else wants the CPU. Extremely low priority.
  • SCHED_FIFO — real-time, first-in-first-out. A running thread keeps the CPU until it voluntarily blocks or yields. There is no time slice.
  • SCHED_RR — real-time, round robin. Same as FIFO, but each thread gets a time slice.
Careful with SCHED_FIFO. Real-time threads run before every other thread on the system. If a SCHED_FIFO thread enters an infinite loop and never yields, it can freeze the entire system — the shell, the scheduler daemon, even the timer handling. This is the classic way to lock up a Linux machine. Use real-time scheduling only when you truly understand it, and always as a bounded, well-behaved task.

Step 7 — Bounded real-time experiment

Let's run a real-time thread for a controlled length of time so we can observe the effect without risking the system: 

$ sudo chrt -f 10 timeout 5s yes > /dev/null &
[1] 5100

This starts a SCHED_FIFO thread with real-time priority 10, but caps its runtime at 5 seconds with the timeout command. While it runs, open another terminal and try typing. You may notice slightly slower response — the shell is being preempted by the real-time thread.

After the 5 seconds, the real-time thread exits and the system returns to normal.

Step 8 — Verify with ps

$ ps -o pid,ni,pri,cls,rtprio,comm -p 5100
  PID  NI PRI CLS RTPRIO COMMAND
 5100   -   -  FF     10 yes
  • CLS — the scheduling class: TS for SCHED_OTHER, FF for SCHED_FIFO, RR for SCHED_RR, B for SCHED_BATCH, IDL for SCHED_IDLE.
  • RTPRIO — the real-time priority, from 1 to 99.
  • NI is empty for real-time threads — nice values do not apply to them.

Step 9 — Clean up

$ kill %1 %2
$ jobs
[1]-  Terminated   ...
[2]+  Terminated   ...

Always clean up background jobs at the end of a lab. A stray yes process will happily consume 100% of a core until you notice it — usually because the fan on your laptop suddenly started spinning at full speed.

Why does nice only go from −20 to +19? The scale was chosen decades ago as an arbitrary range that felt natural. What matters is not the numbers themselves, but the relative weights they map to inside the kernel. In CFS, the mapping is non-linear — each step of nice represents a fixed ratio, not a fixed amount.

5.8 · Touch Lab — Observing the Scheduler with top & /proc

In the previous lab we changed nice values and confirmed the effect. Now let's look at how the scheduler actually reveals itself through system monitoring tools. Everything in this lab is read-only — you can safely run it on any Linux machine, including your course VM.

Load average — the systemic overview

The first thing to look at is load average. In top or with the uptime command, you will see three numbers: 

$ uptime
14:35:12 up  2:14,  2 users,  load average: 0.42, 0.31, 0.28

These are the average number of runnable (or uninterruptible) threads over the last 1, 5, and 15 minutes:

  • If load < number of cores → the system is not fully loaded. Some cores are idle.
  • If load ≈ number of cores → the system is fully utilized, but not overloaded.
  • If load > number of cores → threads are waiting in the ready queue. The scheduler is running at capacity.

On a 4-core system, a load average of 0.5 means half of one core is being used on average. A load average of 4.0 means all four cores are fully loaded. Any number above that means you have more runnable threads than cores — the scheduler genuinely has to choose.

The CPU usage breakdown

In top, the CPU line looks like this: 

%Cpu(s):  3.2 us,  0.8 sy,  0.0 ni, 95.6 id,  0.4 wa,  0.0 hi,  0.0 si,  0.0 st

Each of these categories is a place the CPU time went. Understanding them is essential for diagnosing performance issues:

Label Meaning What high values indicate
us User time — running user-space code. Typical for compute-heavy or application workloads.
sy System time — running kernel code. Excessive syscalls, heavy I/O, too many context switches.
ni Time spent running nice-adjusted user processes. Only nonzero if you use nice values consistently.
id Idle — the CPU had nothing to do. Good for servers, expected on desktops.
wa I/O wait — CPU idle waiting for disk or network. Slow disk, network bottleneck, or heavily-loaded storage.
hi Time handling hardware interrupts. Heavy network traffic or misbehaving device.
si Time handling software interrupts. Heavy network traffic, especially small packets.
st Steal time — time the hypervisor took from this VM. Only visible inside virtual machines, like ours.
The most underrated number: wa — I/O wait. A system with 90% I/O wait and 5% user time looks almost idle, but is actually crippled by slow storage or network. If your application feels sluggish and top shows idle CPU, check the I/O wait before assuming the problem is elsewhere.

Per-CPU view

In top, press 1 to toggle the per-CPU view. You will see one line for each core, with its own usage. This is where the scheduler's work becomes visible: on a multi-core system, the load should spread across cores fairly evenly when there is enough work.

If one core is at 100% while the others are idle, you may be looking at a single-threaded workload that cannot be parallelized — not a scheduler problem. This is a critical diagnostic distinction: the scheduler can only distribute work that is actually available.

Reading /proc for scheduling information

The /proc/<pid>/sched file exposes per-thread scheduler statistics — accumulated runtime, context switches, wakeup count, and more: 

$ cat /proc/$$/sched

bash (4523, #threads: 1)
-------------------------------------------------------------------
se.exec_start                                :    34219.4325
se.vruntime                                  :      321.419
se.sum_exec_runtime                          :       12.837
se.nr_migrations                             :          3
nr_switches                                  :        184
nr_voluntary_switches                        :         42
nr_involuntary_switches                      :        142
prio                                         :        120
clock-delta                                  :         24

A few fields worth understanding:

  • se.vruntime — the CFS virtual runtime we discussed earlier. This is the number CFS uses to order threads in the red-black tree.
  • se.sum_exec_runtime — the total CPU time consumed by this thread, in milliseconds.
  • nr_voluntary_switches — times the thread voluntarily gave up the CPU (typically because it blocked on I/O). High values are typical of I/O-bound threads.
  • nr_involuntary_switches — times the thread was preempted by the scheduler. High values are typical of CPU-bound threads being rotated out of the CPU.
  • se.nr_migrations — how many times this thread has been moved between CPU cores. Too many migrations indicate poor cache locality — the scheduler is shuffling the thread between caches.

Putting it together — a diagnostic exercise

  1. Start three CPU-intensive jobs in the background at the default priority: yes > /dev/null & (three times).
  2. Run top and press 1 to see per-CPU usage. On a 4-core machine, all three cores should show high usage. On a 2-core machine, one job will be waiting.
  3. Note the load average — it should climb to roughly the number of active jobs.
  4. Now renice one of them to +19 and watch its %CPU drop in top.
  5. Simulate I/O load with dd if=/dev/zero of=/tmp/testfile bs=1M count=2000. Watch the wa column in top.
  6. Stop everything with kill %1 %2 %3.
When you can predict what top will show before you run it, you understand scheduling. That is the goal of this lab — not just reading the numbers, but anticipating them from first principles.

Week 5 Summary

  • What scheduling does: decides which ready thread runs next on each CPU core, and for how long before being preempted. Happens billions of times per second on a live system.
  • Preemptive vs non-preemptive: all modern general-purpose OSes are preemptive — the kernel can interrupt a running thread at the end of its time slice.
  • Metrics: turnaround time (total), waiting time (queued), response time (to first execution), throughput, utilisation. Turnaround and response often conflict.
  • FCFS: simple, no preemption, but suffers from the convoy effect — a single long job delays everyone behind it.
  • SJF / SRTF: provably optimal for average waiting time, but require knowing burst times — practically unattainable. Approximation via exponential averaging.
  • Round Robin: fixed time slice per thread, minimises response time. The basis of every general-purpose scheduler.
  • Priority scheduling: explicit priorities, subject to starvation — fixed by aging. Linux exposes it through nice values and real-time classes.
  • MLFQ: multiple priority queues, demotion on full-slice use, promotion on yield, periodic priority boost. Learns thread behaviour without being told.
  • Linux CFS: no explicit time slices — order threads in a red-black tree by virtual runtime, always run the smallest. Scales to any workload. Regulated by sched_latency and min_granularity.
  • Tools: nice, renice, chrt, top, uptime, /proc/<pid>/sched — everything you need to observe and control scheduling from user space.
