1.1 · What is an Operating System?

An operating system (OS) is the piece of software that sits between the user (and the applications they run) and the physical hardware of the computer. It is not just a program among many — it is the foundation on which every other program runs.

When you open your laptop, start a browser, or run a Python script, you are interacting with the operating system the whole time — even if you never see it directly.

Two complementary roles of an OS

Resource Manager

The OS manages the computer's finite resources and decides who gets them, when, and how much:

  • CPU time (scheduling)
  • Memory (allocation, paging)
  • Storage (file systems)
  • I/O devices (disks, network cards)

Abstraction Layer

The OS hides the messy hardware complexity behind clean, standardized interfaces:

  • Files instead of raw disk blocks
  • Sockets instead of raw network packets
  • Processes instead of CPU registers
  • Virtual memory instead of physical addresses
Key idea: The OS is both a resource manager and an abstraction provider. You cannot separate the two roles — they are two faces of the same coin.

A brief history (in one paragraph)

Early computers had no OS — programmers directly manipulated hardware with plugboards and punch cards. Mainframe batch systems introduced the first simple monitors to schedule jobs. Time-sharing systems in the 1960s (CTSS, Multics) brought interactive multi-user computing. Unix, born in 1969 at Bell Labs, shaped the modern OS landscape — and it inspired Linux, macOS, and (indirectly) even Windows. Today, operating systems range from tiny embedded kernels to massive cloud-scale datacenter OSes.

1.2 · User Mode vs Kernel Mode

If every application could execute any machine instruction — including resetting the CPU, modifying page tables, or writing directly to disk sectors — the system would collapse in seconds. To prevent this, modern processors provide (at least) two privilege levels.

The dual-mode model

Aspect User Mode Kernel Mode
Who runs here Applications, libraries, your Python / C / Java code Operating system kernel code only
Privilege level Restricted (Ring 3 on x86) Full (Ring 0 on x86)
Allowed instructions Only non-privileged instructions All instructions, including privileged ones
Hardware access Must request via system calls Direct access to devices, memory, and CPU registers
Risk if buggy The application crashes — but the system survives A bug can crash the entire machine (kernel panic)

How the CPU knows which mode it is in

The processor has a special mode bit (also called the CPL — Current Privilege Level). When the CPU is in user mode, the bit is set to 1 (or 3 in x86 rings). When it enters kernel mode, that bit is cleared. If user-mode code attempts to execute a privileged instruction, the CPU raises a trap and transfers control to the kernel — which typically terminates the offending process.

Dual-mode operation: the application can only enter kernel mode through a controlled trap.
Important: User mode is not the same as “user account.” Even the root user in Linux runs in user mode. Only the kernel itself runs in kernel mode. Root has more permissions — but still cannot execute privileged CPU instructions directly.

1.3 · System Calls, Interrupts, and Traps

Applications do not access hardware directly — they ask the kernel to do it. That request is a system call. The mechanism that transfers control from user code to the kernel is a trap. And the hardware signals that need the kernel's attention are interrupts. Let's disentangle these three concepts.

The three control-transfer mechanisms

Mechanism Triggered by Synchronous? Typical example
System call The application itself Yes — caused by the program's own instruction read(), write(), fork()
Interrupt An external device (disk, keyboard, network card, timer) No — asynchronous, can happen any time Keyboard press, disk I/O completion, timer tick
Exception / Trap The CPU detecting an error or special condition during execution Yes — synchronous with the executing instruction Division by zero, page fault, invalid opcode
Note on terminology: The word trap is used confusingly in the literature. In some books (Silberschatz, for example), a “trap” is any software-generated interrupt — including system calls. In others (Linux kernel docs), a “trap” is specifically an exception. In this course, we will use the broader meaning: a trap is a software-triggered transfer to kernel mode.

How a system call actually works (step by step)

  1. The application sets up the arguments and places the syscall number in a designated register (e.g., rax on x86-64).
  2. It executes a special instruction: syscall (x86-64) or int 0x80 (32-bit).
  3. The CPU switches to kernel mode and jumps to the kernel's syscall entry point.
  4. The kernel looks up the syscall number in the syscall table and calls the corresponding handler.
  5. The handler performs the requested operation — often touching hardware through drivers.
  6. The kernel returns the result and executes a return-from-trap instruction.
  7. The CPU switches back to user mode, and the application continues from where it left off.
The takeaway: A system call is not a function call between two libraries — it is a privilege transition. That is why they are relatively expensive (typically hundreds of nanoseconds to a few microseconds).

Commonly seen syscalls

read(fd, buf, count)      /* read bytes from a file or device */
write(fd, buf, count)     /* write bytes to a file or device */
open(path, flags, mode)   /* open or create a file */
close(fd)                 /* close a file descriptor */
fork()                    /* create a new process */
execve(path, argv, envp)  /* replace current process image */
waitpid(pid, status, opt) /* wait for a child process */
mmap(addr, len, prot)     /* map memory or files into the address space */
socket(domain, type, protocol)  /* create a communication endpoint */

Most of these syscalls are wrapped by the C standard library (glibc), so you rarely write the raw syscall instruction yourself — but the transition behind the scenes is exactly as described above.

1.4 · Kernel Architectures

The kernel has to do many things at once: manage memory, schedule processes, handle devices, provide system calls. How all of that is organized internally is what we call the kernel architecture. There is no single “right” design — each choice trades off performance, modularity, and safety.

The three main families

Architecture Core idea Advantages Examples
Monolithic All kernel services run in a single, large kernel address space. Very fast — no message passing overhead. Linux, traditional Unix
Microkernel Only the minimal core stays in kernel; everything else runs as user-space servers. More robust, easier to debug, better isolation. Minix, QNX, L4, seL4
Hybrid Practical mixture: monolithic-style kernel plus some user-space services. Balanced trade-off between speed and modularity. Windows NT, macOS (XNU)

Monolithic kernels — the Linux way

Linux is a monolithic kernel. Everything — device drivers, file systems, network stack — runs inside the same kernel address space. This makes it fast, but also means a buggy driver can crash the entire system. To reduce that risk, Linux supports loadable kernel modules (LKMs): pieces of code that can be loaded and unloaded at runtime (e.g., a new driver for a USB device) — without recompiling or rebooting the kernel.

Microkernels — less is more

In a microkernel design, only the truly essential services (basic scheduling, memory management, and IPC) live in kernel mode. Everything else — drivers, file systems, network stacks — is moved to user space as separate, isolated processes. If a driver crashes, only that driver restarts; the whole system stays alive. The price is more context switches and message passing, which historically made microkernels slower than monolithic ones. Modern research kernels (like seL4) have largely closed that gap.

Hybrid kernels — pragmatic middle ground

Real-world operating systems rarely fit a textbook category. Windows NT and macOS's XNU kernel are examples of hybrid designs: they lean monolithic (for performance) but include some microkernel-inspired modularity. This is closer to how OS engineering actually works in practice.

What about Linux? You will often hear Linux described as “monolithic with modular support.” This is accurate: the codebase is monolithic, but the ability to load and unload modules gives it many of the practical benefits of a modular design without the performance costs of a pure microkernel.

1.5 · Touch Lab — Setting Up Your Ubuntu Server VM

Throughout this course, you will work in a virtual machine (VM) running Ubuntu Server. Using a VM keeps your experiments isolated — if you break the system, you simply restore a snapshot or re-create the VM. It also lets you safely experiment with services like DNS and HTTP later in the course.

What you will do in this lab

  1. Download and install VirtualBox (free, cross-platform) — or use VMware if you prefer.
  2. Download the Ubuntu Server LTS ISO (the latest LTS release, e.g. 24.04).
  3. Create a new VM with at least:
    • 2 CPUs
    • 4 GB RAM
    • 25 GB disk
    • NAT + Host-Only network adapters (for later networking labs)
  4. Boot the VM from the ISO and complete the Ubuntu Server installation:
    • Choose a language and keyboard
    • Set a hostname (e.g. os-lab)
    • Create a non-root user with a strong password
    • Enable OpenSSH server — we will use it later
  5. Reboot into your new system and log in for the first time.
Tip: Run sudo apt update && sudo apt upgrade -y right after the first login to bring your VM up to date. Then take a snapshot so you can always return to a clean, working baseline.

1.6 · Touch Lab — Your First Linux Commands

Now that your VM is running, let's explore it through the shell. The commands below form the foundation of everything else in this course — you will use them every week from now on.

The starter kit

man ls           # read the manual page of a command
ls               # list files in the current directory
ls -la           # list all files (including hidden) with details
pwd              # print the current working directory
cd /etc          # change directory to /etc
cd ..            # go up one level
uname -a         # show kernel and system information
whoami           # print the current user
hostname         # show this machine's name
uptime           # show how long the system has been running
df -h            # show disk usage in a human-readable format
free -h          # show memory usage

How to read a man page

Every Linux command comes with a manual page. Learning to read man output is one of the most valuable skills you can develop in this course.

Try man ls and pay attention to the structure: NAME (one-line description), SYNOPSIS (usage pattern), DESCRIPTION (detailed behavior), and OPTIONS (flags).

Inside a man page, press q to quit, / to search forward, and n to jump to the next match.

Week 1 Summary

  • What an OS is: Both a resource manager and an abstraction layer — sitting between applications and hardware.
  • Dual-mode operation: Applications run in user mode; the kernel runs in kernel mode. The transition is controlled and rare.
  • System calls: The mechanism applications use to request kernel services — an expensive privilege transition, not a normal function call.
  • Interrupts vs Traps: Interrupts are asynchronous and hardware-driven; traps and exceptions are synchronous and software-driven.
  • Kernel architectures: Monolithic (Linux, Unix) for speed; microkernel (Minix, QNX) for isolation; hybrid (Windows NT, macOS) as a practical middle ground.
