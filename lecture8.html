8.1 · Files & Directories

For seven weeks, we have built up the theory of a modern operating system: processes, threads, synchronization, scheduling, deadlocks, and memory. But we have never asked where the data actually lives between runs. When you close your laptop and open it the next morning, your documents are still there — even though RAM is volatile and every process that ran yesterday is long gone.

The answer is the file system. It is the abstraction that lets programs store and retrieve data across power cycles, in a way that survives crashes, and that scales from the tiny embedded ROM of a router to the multi-petabyte distributed file systems of cloud providers.

One-line definition: a file system is the part of the OS that provides the abstractions of files and directories, and manages the mapping of those abstractions onto the raw block storage of the hardware.

The file abstraction

A file is the most fundamental persistent abstraction in the OS. It is a named sequence of bytes, stored on a non-volatile medium — usually a disk or SSD — and accessible through system calls rather than through memory addresses.

Crucially, a file is not just "bytes on disk." It carries with it several important properties:

Attribute What it means
Name A human-readable identifier. The file system maps names to underlying storage locations.
Size How many bytes the file contains. The kernel tracks this, and it changes as the file is written to.
Type Regular file, directory, symbolic link, device, socket, FIFO. The type determines how the file's contents are interpreted.
Permissions Who can read, write, or execute it — the rwx bits we will meet in Week 9, split across owner, group, and others.
Owner / group Which user and group the file belongs to.
Timestamps Creation, last access, last modification. Used by backup tools, build systems, and caches.
Inode number A unique identifier assigned by the file system to the file's metadata record.

The two ways to name a file

On every Unix-like system — including Linux — every file has two names:

The pathname

A human-readable string, like /home/student/notes.txt, that the file system resolves step by step as it walks the directory tree. This is what users think of as the file's name.

The inode number

A machine-readable integer, like 1234567, that uniquely identifies the file's metadata record within the file system. This is what the kernel actually uses. Multiple pathnames can point to the same inode — those are called hard links.

Directories

A directory is a special kind of file whose contents are a mapping from names to inode numbers. That is the whole idea. A directory does not contain the bytes of the files it "points to" — it contains just a table of name → inode entries.

This design has one beautiful consequence. When you rename a file — mv a.txt b.txt — the file system does not move any data. It just changes one entry in one directory. Renaming a 10 GB file costs the same as renaming a 10-byte file. This is why Unix files are not "in" directories — they are merely referenced by them.

A directory is a table of name → inode entries. The actual file data is stored in the inode's data blocks, which can live anywhere on disk.

The file operations — the system call surface

The Unix file API is famously small. A handful of system calls cover everything from opening a text file to writing a database record. Here are the ones you will use every day:

Syscall What it does
open(path, flags) Opens a file and returns a file descriptor — a small integer the kernel uses to identify the open file. Creates the file if the flag O_CREAT is set.
read(fd, buf, n) Reads up to n bytes from the current file offset into the user buffer.
write(fd, buf, n) Writes n bytes from the user buffer to the current file offset.
lseek(fd, offset, whence) Moves the file offset. This is what makes random-access files possible.
close(fd) Releases the file descriptor. Does not necessarily flush writes — see fsync.
stat(path, buf) Returns metadata about the file — size, permissions, owner, timestamps, inode number.
unlink(path) Removes a directory entry, decrementing the file's link count. The file is actually deleted when the count reaches zero.
fsync(fd) Forces all buffered writes to be flushed to stable storage. Essential for durable data.
The buffering trap: when you call write(), the kernel usually just copies the data into the page cache and returns immediately. The data has not yet reached the disk. If the machine loses power a moment later, the data is gone. To force durability, you must call fsync(). Many applications that "lost data after a crash" simply forgot this call.

8.2 · Allocation Methods

The problem with disk storage is that it is fundamentally different from RAM. Disks are organized in blocks — typically 512 bytes or 4 KB each — and accessing a random block costs a mechanical seek plus a rotational delay. For a spinning disk, that is on the order of 5 to 10 milliseconds. For an SSD, a few tens of microseconds. Either way, it is far slower than RAM access, and the file system's job is to minimize the number of blocks it has to touch.

Given that constraint, how should the file system decide where to place a file's data blocks on disk? Over the decades, three main strategies have been tried.

Method 1 — Contiguous allocation

The simplest design. When a file is created, the file system reserves a run of consecutive blocks large enough to hold it. The file's location is described by a starting block plus a length.

Advantages

  • Very fast sequential and random access. The blocks are adjacent, so the disk head barely needs to move.
  • Trivial to implement — a file is just a range of blocks.
  • Minimal storage overhead — only the starting block and length are needed.

Disadvantages

  • External fragmentation — same problem we saw with RAM in Week 7.
  • Hard to grow a file in place. If the space after the file is used, growth requires relocating the entire file.
  • Requires the file system to know the maximum size in advance, or to leave slack at the end.

Method 2 — Linked allocation

The other extreme. Each block of a file stores not just file data, but also a pointer to the next block in the chain. A file is described as a linked list of blocks, with the first block's location stored in the inode or directory entry.

Advantages

  • No external fragmentation — any free block will do.
  • Files can grow easily — just append a new block and update the previous block's pointer.
  • No need to know the maximum file size in advance.

Disadvantages

  • Random access is slow — reaching block N requires reading N-1 previous blocks.
  • Each block loses space to the pointer — 4 bytes of every 512-byte block, or 8 of every 4 KB block.
  • A single damaged pointer loses the rest of the file chain.

Method 3 — Indexed allocation (the modern solution)

The best of both worlds. The file system keeps an index block — a table of pointers to the file's data blocks — and stores that index in the file's inode. The inode knows the data block numbers directly, so random access requires zero chain-following.

Unix uses indexed allocation. The inode contains a small array of pointers — typically 12 direct pointers, one single-indirect pointer, one double-indirect, and one triple-indirect — that together allow a file to grow to enormous sizes while keeping small files cheap.

Method Random access Growth Fragmentation Examples
Contiguous Excellent — O(1) Hard — may require relocation External Old mainframes, ISO 9660 CD-ROMs
Linked Poor — O(n) to reach block n Easy — just append None FAT on MS-DOS floppies; historically also FAT32
Indexed Excellent — O(1) Easy — allocate a new index block None (small internal from index blocks) Unix ext2/3/4, XFS, ZFS, APFS, NTFS
Contiguous is fast but rigid. Linked is flexible but slow for random access. Indexed combines the best of both — the whole reason Unix, NTFS, and modern file systems use it.

8.3 · Inodes & FAT — Two Design Philosophies

There are two broad architectural styles for a file system. Unix uses inodes, and MS-DOS/Windows historically used the File Allocation Table, or FAT. Understanding both tells you how the two families of file systems think about storage.

The Unix inode

An inode — short for "index node" — is a fixed-size record on disk that stores everything the file system knows about a file except its name and its data. Every file, directory, device, or special node on a Unix-like system has an inode.

The inode is fixed-size, which is what makes the file system's metadata simple and fast to access. A field layout that is typical of Linux's ext4 file system: 

struct inode {
    uint16_t  i_mode;        /* file type and permissions */
    uint16_t  i_uid;         /* owner user ID */
    uint32_t  i_size;        /* file size in bytes */
    uint32_t  i_atime;       /* last access time */
    uint32_t  i_mtime;       /* last modification time */
    uint32_t  i_ctime;       /* last inode change time */
    uint16_t  i_links_count; /* number of hard links to this file */
    uint32_t  i_blocks;      /* number of 512-byte blocks allocated */
    uint32_t  i_block[15];   /* pointers to data blocks */
       /* 12 direct + 1 single-indirect + 1 double + 1 triple */
};

The i_block[15] array is the heart of the design. The first twelve entries point directly at data blocks. The thirteenth points at a block full of pointers to more data blocks. The fourteenth points at a block full of pointers to blocks full of pointers. The fifteenth goes one level deeper.

This tiered structure allows one inode to describe a file of almost any size, while keeping small files cheap. If a file fits in twelve blocks, no indirection blocks are ever allocated. Only as the file grows do the indirect blocks come into play.

Level Points to Maximum blocks reachable
Direct (12 entries)Data blocks directly12
Single indirectA block of 256 pointers (4 KB / 16-byte entries)256
Double indirectA block pointing to single-indirect blocks256 × 256 = 65,536
Triple indirectA block pointing to double-indirect blocks256³ = 16,777,216
Total reachable with 4 KB blocks~64 GB

The FAT file system

FAT takes the opposite approach — it moves the linkage information out of the blocks and out of the inodes, into one central table at the start of the volume.

The File Allocation Table is exactly that — a table with one entry per block on the disk. Each entry says either "this block is free," "this block is the last in a file," or "the next block of this file is at block N." To locate a file's data, the file system reads the directory entry to find the first block, then follows the table chain.

FAT advantages

  • Simple — one table, easy to understand.
  • The entire table can be cached in RAM, so chain traversal is fast once it is loaded.
  • Supported by virtually every OS and removable media device.

FAT disadvantages

  • For a large disk, the table itself becomes huge — a 1 TB FAT32 volume has a 64 MB partition table.
  • Hard links are not supported — a block belongs to exactly one file.
  • Fragmentation tends to be worse than in inode-based file systems.
  • Metadata (permissions, ownership, timestamps) is limited.
Which is better? For a modern general-purpose OS, Unix's inode design wins easily — it is faster, more flexible, supports hard links and permissions, and scales to very large volumes. FAT survives today mostly on USB sticks and camera SD cards, where simplicity and universal compatibility matter more than performance.

8.4 · Journaling & Crash Consistency

So far we have been assuming that the disk always does what we ask it to. But there is a nastier problem: what happens when the power goes out in the middle of a write?

Consider what it takes to create a file. The file system must, at minimum:

  1. Allocate an inode and mark it in use.
  2. Write metadata about the file to that inode — size zero, current time, permissions.
  3. Add a directory entry mapping the new name to that inode number.
  4. Update the file system's free-space bitmap.
  5. Update the free-inode count in the superblock.

These are several separate writes to different parts of the disk. If the machine crashes between write 3 and write 4, what is the state of the file system? The directory now thinks the file exists. The free-space bitmap thinks the inode is up for grabs. If a new file reuses that inode number, you now have two directory entries pointing to the same inode — silent and dangerous corruption.

The crash-consistency problem: a single operation on a file system is actually multiple disk writes, and no atomic "do all of them or none" primitive exists at the hardware level. Without a strategy, every crash can leave the file system in a state that was never designed to exist.

The classic fix — fsck

The historical approach, used by ext2 and other classic Unix file systems, was to accept that crashes leave the disk inconsistent, and to run a checking program — fsck — at boot. The checker would scan the entire file system, looking for anomalies: orphaned inodes, mismatched link counts, directory entries pointing to freed blocks, and so on. It would then repair them as best it could.

The cost was time. For a large file system, fsck could take minutes or hours. And it could not always distinguish between inconsistent states caused by a crash and legitimate states — so some repairs were guesses.

The modern fix — journaling

Modern file systems — ext3, ext4, XFS, NTFS, APFS, and many others — use journaling. The idea is to never let the disk be inconsistent, by writing each pending change to a special append-only region called the journal first, before applying it to the actual file system.

The sequence for any metadata operation becomes:

  1. Write-ahead: write the intended changes to the journal. This is one contiguous write, fast and easy to complete atomically.
  2. Checkpoint: mark the journal entry as complete by writing a commit record.
  3. Apply: perform the actual change to the real file system metadata.
  4. Free: once the change has been applied, mark the journal entry as completed.

If a crash happens at any point, the recovery procedure is simple: scan the journal from the last known-good point. Any entry with a commit record is rolled forward to completion; any entry without a commit record is discarded as if it had never been started.

Why this is so much better: recovery after a crash takes seconds or less, because the kernel does not have to scan the entire file system — just the journal. And it never leaves the file system in an inconsistent state, because every change either fully commits or is fully discarded.

Three modes of journaling

Not all journaling is the same. Linux ext3 and ext4 offer three modes, differing in what gets journaled:

Mode What is journaled Speed Safety
Journal Both metadata and file data. Slowest Strongest — no inconsistency possible.
Ordered (default) Metadata only, but file data is written first. Balanced Good — file data never points at stale blocks.
Writeback Metadata only, file data can be written any time. Fastest Weakest — file data may be stale after a crash.

Linux uses ordered by default. It is a middle ground: metadata is journal-ed, and file data is written before the metadata commit, so that a file's directory entry never points at blocks that have not yet been written.

8.5 · RAID — Redundant Array of Independent Disks

File systems decide how to organize bytes on one disk. But modern servers do not use one disk — they use many. RAID is the family of techniques for combining multiple physical disks into what looks to the operating system like a single, faster, and/or more reliable logical volume.

RAID is not one thing — it names a collection of standard configurations, each optimized for a different trade-off between performance, capacity, and reliability.

RAID 0 — Striping (no redundancy)

Split each file's data across multiple disks in stripes. If you write a 1 MB file across four disks, each disk stores 256 KB. Read and write throughput scale roughly linearly with disk count, because the disks work in parallel.

The catch: zero redundancy. If any one disk fails, the entire array is gone — every byte of every file is unreadable, because the missing pieces are exactly the pieces on the dead disk.

RAID 1 — Mirroring (maximum redundancy, minimum usable capacity)

Every write goes to two (or more) disks. The disks are exact copies of each other. If one fails, the system keeps running from the other.

Reliability is very high, but usable capacity is cut in half. RAID 1 with two 1 TB disks gives you 1 TB of usable space, not 2 TB. Read performance is good — both disks can serve reads — but writes must go to all mirrors.

RAID 5 — Striping with distributed parity

Stripe data across N disks, but reserve space on each disk (effectively) for one parity block per stripe. The parity is computed with XOR: if you know the parity block and N−1 data blocks, you can reconstruct the missing one.

This means that a RAID 5 array of N disks can survive exactly one disk failure — the missing disk's data can be reconstructed on the fly from the parity. Capacity overhead is only 1/N — with four 1 TB disks you get 3 TB of usable space, not 2 TB like RAID 1.

The RAID 5 catch: if a second disk fails while the array is still rebuilding after the first failure, you lose everything. Modern large disks take hours to rebuild, so RAID 5 is increasingly being replaced by RAID 6 (two parity blocks, tolerates two simultaneous failures) or by RAID 10.

RAID 10 — Mirroring + striping (the enterprise favorite)

Combine RAID 1 and RAID 0. Data is striped across multiple mirrored pairs. You get the performance benefits of striping and the reliability of mirroring, at the cost of 50% capacity overhead — the same as RAID 1.

Modern databases and cloud storage frequently use RAID 10, because the rebuild time after a failure is very short: you just copy from the surviving mirror of the failed disk.

Four RAID configurations: RAID 0 strips for speed, RAID 1 mirrors for safety, RAID 5 stripes with distributed parity for a middle ground, and RAID 10 combines both strategies.

8.6 · Disk Scheduling

A spinning disk has one moving part: the read/write head, which must physically travel to the track containing the requested block. This motion is called a seek, and it takes on the order of 5 to 10 milliseconds on a modern hard drive. Once the head is on the right track, the disk must rotate to the correct sector — the rotational latency, on the order of 2 to 4 milliseconds.

When multiple I/O requests are queued up, the order in which the head services them can make a difference of two or three times in overall throughput. That is what disk scheduling algorithms are for.

The standard example — a disk with pending requests

Throughout this section, we will use the same workload: a disk with 200 cylinders, and these pending requests (in the order they arrived). The head is currently at cylinder 53 and moving toward larger numbers. 

Pending cylinder numbers, in arrival order:
98, 183, 37, 122, 14, 124, 65, 67

Starting position: cylinder 53, moving right (toward higher numbers)

FCFS — First Come, First Served

The block requests are serviced in the order they arrived. This is fair — no request starves — but the head sweeps wildly back and forth across the disk, wasting enormous amounts of time on seeks.

On our example: the head moves 53 → 98 → 183 → 37 → 122 → 14 → 124 → 65 → 67. Total head movement: 45 + 85 + 146 + 85 + 108 + 110 + 59 + 2 = 640 cylinders.

SSTF — Shortest Seek Time First

Always serve the closest pending request. This minimizes the total head movement on the current step, but not necessarily overall. It can also starve requests that are far from the current head position, if new nearby requests keep arriving.

On our example, starting at 53: 53 → 65 → 67 → 37 → 14 → 98 → 122 → 124 → 183. Total head movement: 12 + 2 + 30 + 23 + 84 + 24 + 2 + 59 = 236 cylinders.

That is a factor of nearly three better than FCFS. But notice the starvation risk: a request at cylinder 199 will always be deferred if there are requests at 100 or 50 arriving.

SCAN — the elevator algorithm

The head moves in one direction, serving all requests it encounters along the way. When it reaches the end of the disk, it reverses direction and sweeps back. It is exactly like an elevator: it goes up until there are no more requested floors, then goes down until there are no more.

On our example, starting at 53 moving right: 53 → 65 → 67 → 98 → 122 → 124 → 183 → 199 (end) → 37 → 14. Total head movement: 12 + 2 + 31 + 24 + 2 + 59 + 16 + 162 + 23 = 331 cylinders.

SCAN is more predictable than SSTF — the maximum wait time for any request is bounded by the time to complete one full sweep. This makes it a good choice for systems where predictability matters.

C-SCAN — circular SCAN

A small improvement on SCAN. Instead of reversing direction when the head reaches the end, it quickly returns to the other end of the disk and sweeps again. The return sweep does not service any requests — the head moves straight back, ignoring everything until it starts a new sweep.

The advantage is that C-SCAN treats all cylinders more fairly — SCAN slightly favors the cylinders near the middle of the disk, because the head decelerates and reverses there. C-SCAN gives more uniform service times.

Algorithm Behaviour Head movement (our example) Key property
FCFS Arrival order. 640 Fair but slow.
SSTF Closest request first. 236 Fast but starves far requests.
SCAN Elevator — sweep, then reverse. 331 Predictable, good throughput.
C-SCAN Sweep one way, jump back, repeat. ~382 Uniform service times.
Do modern systems still use disk scheduling? For SSDs, no — SSDs have no moving parts, so there is no seek and no rotational latency. Linux's I/O scheduler for SSDs is essentially a queue that does not reorder by position. But for spinning disks, and for the underlying storage that backs many cloud services, SCAN-style algorithms remain important.

8.7 · Touch Lab — Exploring the File System

Now it is time to see the theory in action. Linux exposes every part of the file system through standard commands — the same ones sysadmins use to diagnose disk problems, detect leaks, and understand how storage is really laid out.

Step 1 — What is mounted? df and mount

$ df -h
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        20G  4.2G   15G  23% /
tmpfs            2.0G     0  2.0G   0% /dev/shm
/dev/sda15      105M  6.1M   99M   6% /boot/efi
tmpfs            400M  1.1M  399M   1% /run

The df command shows every mounted file system — the underlying storage device, its total size, how much is used, and where it is mounted in the directory tree.

  • Filesystem — the device node, such as /dev/sda1. For virtual file systems (proc, tmpfs, devtmpfs), this may just be an identifier.
  • Size / Used / Avail — capacity, consumption, remaining free space.
  • Use% — percent used. Watch out when this approaches 100%; some services misbehave badly on a completely full partition.
  • Mounted on — where in the directory tree this device appears.

Step 2 — Inodes: ls -i and df -i

$ ls -i /etc/hostname
1310732 /etc/hostname

$ ls -li /etc/ | head -5
1310725 drwxr-xr-x  3 root root  4096 Nov 12 10:14 acpi
1310726 drwxr-xr-x  4 root root  4096 Nov 12 10:14 alsa
1310727 -rw-r--r--  1 root root  3000 Nov 12 10:14 adduser.conf
1310728 drwxr-xr-x  2 root root  4096 Nov 12 10:14 alternatives
1310729 drwxr-xr-x  3 root root  4096 Nov 12 10:14 apm

The first column in the ls -i output is the inode number. Every file and directory on this system has a unique one. The -i flag is what tells ls to show it.

The other columns of ls -l are worth reading carefully:

  • First character — file type: d for directory, - for regular file, l for symbolic link, b for block device, c for character device, s for socket, p for FIFO.
  • Next 9 characters — permissions in three groups: owner, group, others.
  • Link count — how many names point to this inode.
  • Owner, group — who the file belongs to.
  • Size — the file's size in bytes.
  • Modification time — last time the file was written.

Now let's check inode consumption across file systems: 

$ df -i
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/sda1      1310720 134125 1176595   11% /
tmpfs           262144      1  262143    1% /run
/dev/sda15           0      0       0     -  /boot/efi

The df -i command shows inode usage per file system. This catches a classic sysadmin emergency: a file system whose inodes are exhausted but whose disk space is nowhere near full. If you create a million zero-byte files, you can fill up the inode table without using any disk space at all.

Step 3 — mount and the file system tree

$ mount | head -5
sysfs on /sys type sysfs (rw,nosuid,nodev,noexec,relatime)
proc on /proc type proc (rw,nosuid,nodev,noexec,relatime)
udev on /dev type devtmpfs (rw,nosuid,relatime,size=1984856k,nr_inodes=496214,mode=755)
devpts on /dev/pts type devpts (rw,nosuid,noexec,relatime,gid=5,mode=620,ptmxmode=000)
tmpfs on /run type tmpfs (rw,nosuid,nodev,noexec,relatime,size=404436k,mode=755)

The mount command with no arguments lists every active mount. Each line has the form: device type mount_point (options).

A few of these are especially interesting:

  • sysfs, proc, devtmpfs — virtual file systems. They do not exist on disk at all — they are synthesized by the kernel on every read. This is what we saw with /proc back in Week 2.
  • tmpfs — a RAM-backed file system. Writes go to memory; nothing is persisted across a reboot. Used for /run, /tmp, and occasionally for entire server root file systems.
  • ext4, xfs, btrfs — real on-disk file systems. These are what you would normally install your data on.

Step 4 — Hard links and symbolic links

$ echo "hello" > original.txt
$ ln original.txt hardlink.txt          # hard link
$ ln -s original.txt softlink.txt       # symbolic link

$ ls -li original.txt hardlink.txt softlink.txt
1310752 -rw-r--r-- 2 student student 6 Nov 12 10:22 hardlink.txt
1310752 -rw-r--r-- 2 student student 6 Nov 12 10:22 original.txt
1310753 lrwxrwxrwx 1 student student 12 Nov 12 10:22 softlink.txt -> original.txt

Notice the difference carefully:

  • Hard link — the inode number is identical (1310752). The link count is 2, because two directory entries point to the same inode. The file data actually exists only once. If you delete one name, the other still works.
  • Symbolic link — its own inode (1310753), with a different type character l. Its contents are the target path. If you delete the target, the symlink becomes a dangling reference.
Try this: delete original.txt. What happens to hardlink.txt and softlink.txt? The hard link still works — its inode still has one reference. The symbolic link is now broken, because the file it points to no longer exists. That is the difference between a hard link and a symbolic link in one experiment.

8.8 · Touch Lab — Reading the Kernel's View of Storage

Everything df and mount showed us comes from somewhere. The kernel exposes the raw truth under /proc — and reading those files is the most authoritative way to understand what is really going on.

Step 1 — /proc/partitions

$ cat /proc/partitions
major minor  #blocks  name

   8        0   20971520 sda
   8        1   20480000 sda1
   8        2          1 sda2
   8        5    1024000 sda5
   253       0   20971520 dm-0
   253       1    1024000 dm-1

Every block device the kernel knows about appears here. The major number identifies the driver — 8 is the SCSI/SATA disk driver, 253 is device-mapper — and the minor number identifies the specific device. The #blocks column is the size of the partition in 1 KB blocks.

Notice the difference between sda — the whole disk — and sda1, sda2, sda5 — the partitions on it. The numbers after the disk name are the partition indices, with 1–4 reserved for primary partitions and 5 and up for logical partitions in an extended partition scheme.

Step 2 — /proc/mounts

$ cat /proc/mounts | head -8
sysfs /sys sysfs rw,nosuid,nodev,noexec,relatime 0 0
proc /proc proc rw,nosuid,nodev,noexec,relatime 0 0
udev /dev devtmpfs rw,nosuid,relatime,size=1984856k,nr_inodes=496214,mode=755 0 0
devpts /dev/pts devpts rw,nosuid,noexec,relatime,gid=5,mode=620,ptmxmode=000 0 0
tmpfs /run tmpfs rw,nosuid,nodev,noexec,relatime,size=404436k,mode=755 0 0
/dev/sda1 / ext4 rw,relatime,errors=remount-ro 0 0
securityfs /sys/kernel/security securityfs rw,nosuid,nodev,noexec,relatime 0 0

/proc/mounts is the kernel's own view of the mount table — the one mount, df, and every other utility ultimately queries. Each line has these fields:

  1. Device — /dev/sda1, or a virtual device name.
  2. Mount point — where it is attached in the tree.
  3. File system type — ext4, xfs, tmpfs, proc, and so on.
  4. Mount options — the flags in effect.
  5. Dump and pass — legacy fields, rarely used.

Look carefully at the mount options. errors=remount-ro for the root partition means: if the kernel detects file system corruption, remount read-only instead of continuing to write into a damaged structure. relatime tells the kernel to update access timestamps less aggressively, saving disk bandwidth. These small flags have a big impact on system behavior.

  • Filesystem state — clean means it was unmounted properly; anything else means it may need a check.
  • Filesystem UUID — a unique identifier assigned at creation time. This is what /etc/fstab typically uses to identify file systems, because it is more stable than device names.
  • Inode count vs Free inodes — the total and remaining inode slots. Just like disk space, inodes can run out.
  • Block size — the file system's fundamental allocation unit, typically 4 KB.
  • Mount count — how many times it has been mounted since the last check. Some systems automatically run fsck after a certain number of mounts.
Modern practice: while ext4 is still by far the most common Linux file system, alternatives exist — XFS for large files and high parallelism, Btrfs and ZFS for snapshotting and checksumming, bcachefs as a modern competitor. Each has strengths, and the choice depends on the workload. For this course, though, ext4 is the reference implementation and what you will actually work with most often.

Week 8 Summary

  • Files and directories: a file is a named sequence of bytes carrying metadata; a directory is a table mapping names to inode numbers.
  • Inodes vs FAT: Unix keeps per-file metadata in inodes; MS-DOS keeps the linkage in a central table. Inodes scale better and support hard links; FAT is simpler and more universally supported.
  • Allocation methods: contiguous (fast but rigid), linked (flexible but slow), indexed (modern — used by ext, XFS, NTFS).
  • Journaling: write-ahead logging on a dedicated region keeps the file system consistent across crashes. Recovery is fast — scan the journal, roll forward commits, discard incomplete entries.
  • RAID: RAID 0 (striping, no safety), RAID 1 (mirroring), RAID 5 (distributed parity), RAID 10 (mirror + stripe). The correct choice depends on the balance of safety, speed, and capacity you need.
  • Disk scheduling: FCFS, SSTF, SCAN, and C-SCAN. All are optimizations for moving heads. SSDs do not need them.
  • Tools: df -h, df -i, mount, ls -li, ln, /proc/partitions, /proc/mounts, tune2fs -l.
