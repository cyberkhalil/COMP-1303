Project Overview

Over the last four weeks of Phase 2, you have built four separate Linux services in isolation: DHCP (Week 10), DNS (Week 11), HTTP with Nginx (Week 12), and MariaDB (Week 13). Each one runs, each one works, and each one was tested on its own.

This week, you consolidate them into one integrated three-tier web application that runs end-to-end on your VM. This is not a new lab — it is the assembly of everything you have built, plus the discipline of testing, documenting, and validating a real system the way a professional engineer would deliver it.

The core idea: in Phase 2 you learned how each service works. In this project, you learn how services work together. That is the difference between "I can install a service" and "I can run a service" — and it is what the industry hires for.

Pre-Flight Checklist

Before you attempt any integration, verify each service works in isolation.

# DNS — should return 192.168.56.1 with an "aa" flag
dig @127.0.0.1 app.lab.local A

# Nginx — should respond to the virtual host
curl -I -H "Host: app.lab.local" http://localhost/

# Backend — should return OK (verifies DB connectivity)
curl http://127.0.0.1:5000/health

# Database — should return a count without error
mysql -u app -p app_db -e "SELECT COUNT(*) FROM customers;"

# Client — should resolve our internal name through our own BIND9
dig app.lab.local A
Do not proceed if any of these fail in isolation. Integration of broken pieces only multiplies confusion. Fix the broken layer first, then integrate.

Part I — The Working Stack (50 points)

Component Checklist

  1. DNS layer. BIND9 running and authoritative for lab.local. The zone file must resolve:
    • ns1.lab.local → 192.168.56.1
    • app.lab.local → 192.168.56.1
    • db.lab.local → 192.168.56.1
    Recursion must be restricted to 127.0.0.1/32 and 192.168.56.0/24 only.
  2. HTTP layer. Nginx running with a virtual host for app.lab.local. The virtual host must:
    • Accept HTTP on port 80
    • Reverse-proxy all requests to 127.0.0.1:5000
    • Set Host, X-Real-IP, X-Forwarded-For, and X-Forwarded-Proto headers
  3. Backend layer. Flask application running on 127.0.0.1:5000, listening on loopback only (not 0.0.0.0). It must expose:
    • GET / — a friendly HTML page
    • GET /health — returns OK and proves DB connectivity
    • GET /api/customers — JSON array of all customers
    • GET /api/customers/<id> — one customer, or 404
    • POST /api/customers — creates a customer (201 or 409)
  4. Database layer. MariaDB with:
    • Database app_db using utf8mb4 collation
    • Tables customers and orders with a foreign key and ON DELETE CASCADE
    • Application user app@localhost with only SELECT, INSERT, UPDATE, DELETE on app_db
    • MariaDB bound to the Unix socket — not listening on the network
  5. Client validation. From the client VM, the following commands must all succeed: 
dig app.lab.local A

curl http://app.lab.local/api/customers

curl -X POST http://app.lab.local/api/customers \
    -H "Content-Type: application/json" \
    -d '{"name":"Your Name","email":"you@lab.local"}'

curl http://app.lab.local/api/customers

The money test: after the POST from the client succeeds, the new row must be present in MariaDB when you query it directly with mysql from the server. That proves end-to-end persistence.

Part II — Documentation (30 points)

Required Documents

1. Service Inventory

A single table listing every service in the stack. Must include:

  • Host or bind address
  • Role (DNS / HTTP / backend / database)
  • Port or socket
  • Systemd unit name or process ID
  • Log file location
  • Configuration file path(s)

2. Technical Report (2–4 pages)

Four sections, in this order:

  1. What was built. One paragraph of architecture plus the stack diagram.
  2. How it works. Walk through one concrete request end-to-end. Specific commands, specific files, specific log lines.
  3. How you prove it works. The evidence, with each item captioned.
  4. How you would debug it. The bottom-up walk, and the symptom-to-layer cheat sheet.

3. Diagrams

Include the stack diagram. You may redraw the SVG from this page, or produce an equivalent diagram of your own.

Failure Injection (10 pts)

Perform three of the following failure experiments. For each, capture the client error and the server-side log entry that identified the failing layer.

Experiment Command Expected Client Symptom
Stop MariaDB systemctl stop mariadb 500-level error; server log shows DB connection failure
Kill Flask backend pkill -f app.py 502 Bad Gateway; Nginx error log shows "connection refused"
Break DNS on client echo "nameserver 192.0.2.1" | sudo tee /etc/resolv.conf "Could not resolve host" from client; server side is unaffected
Break Nginx server_name Edit server_name to wrong value, reload Client sees default Nginx page; DNS + backend still work

For each experiment, undo the change, verify the stack works again, and document the cycle: break → observe → diagnose → fix → verify.

Project Summary

  • You are assembling four previously-built services into one working three-tier system.
  • The stack runs entirely on one server VM at 192.168.56.1, with a client VM talking to it over the host-only network.
  • The client must be able to resolve a name via your DNS, make an HTTP request, have it reverse-proxied to the Flask backend, and see data persisted in MariaDB — with all of it visible in the corresponding logs.
  • You must produce a service inventory, a technical report, evidence captures for each layer, and a failure analysis of three deliberately-broken layers.
  • The project is graded 50 / 30 / 20 across the working stack, documentation, and evidence/failure analysis. Extra credit is available for HTTPS, JOIN endpoints, systemd-wrapped backends, or automated backups.
  • This project feeds directly into your Week 15 final project. The demo you prepare here is the demo you present at the end of the course.
