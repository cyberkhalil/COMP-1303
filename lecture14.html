14.1 · The Full Stack Architecture

For four weeks, we have been building services one at a time. In Week 10, we built a DHCP server and learned how addresses are assigned. In Week 11, we built a DNS server that resolves names for our own internal domain. In Week 12, we deployed Nginx to serve HTTP and reverse-proxy requests to a Python backend. And last week, in Week 13, we installed MariaDB, created a database with users and privileges, and connected it to that same backend.

Each service works in isolation. But real systems do not live in isolation. A real service — the kind that powers a website, an audit system, an inventory tracker, a library catalogue — is composed of many of these pieces, working together, chosen and wired around a real business need.

This week is the integration week. We are going to stop thinking about DNS, HTTP, and MariaDB as separate services, and start thinking about them as layers of one coherent application. And we are going to build that application end to end.

The core idea behind this week: in a real system, no service stands alone. DNS tells clients where to connect. HTTP tells clients how to exchange data. The database remembers what happens. Each layer is useful on its own, but the integration is where real value is created.

The three-tier application — one more time

Every serious web service in the world is built as a layered stack. Different companies use different tools, and they may have dozens of components rather than three. But at the highest level, they all share the same shape: a client-facing layer, an application layer, and a persistence layer.

Every real web service has this shape — a client-facing DNS layer, an HTTP layer that serves and proxies, and a persistence layer that stores the data. Everything else is a detail on top.

Three tiers. Each one has a single, clear responsibility. Each one can be understood, tested, and debugged independently. And together they make something much more useful than any one of them alone.

Why integration is not just "add one more service"

When we built each service in isolation, we could test it in isolation. Start BIND9, run dig, look at the output. Start Nginx, run curl, look at the response. Start MariaDB, connect, run SQL.

Integration changes that. When three services are running at once, a failure in any one of them produces a symptom that might point at any of the others. That is the essential challenge of operations — and it is exactly what this week's lab is going to teach.

The main skill this week: when the full stack fails, knowing which service is actually responsible. That skill is what separates an engineer who can "install a service" from one who can "run a service."

14.2 · Planning the Integrated Environment

Before touching a single configuration file, we plan. This is not busy work — it is the difference between a lab that takes an hour and one that takes a week. Every serious infrastructure project starts with a short written plan that answers a handful of specific questions.

The five questions to answer first

  1. What is the domain name we are using internally? We have been using lab.local. That is a convention — the .local TLD is reserved for mDNS (multicast DNS), so using it in private DNS zones is safe and it will never conflict with a real domain.
  2. What is each machine's address and role? We have one or two VMs. Each has an IP address. Each has one or more roles. We need to write this down.
  3. What hostnames do we need? The application has a name. The mail host has a name. The name servers have names. All of these must resolve in DNS.
  4. What TCP ports are involved? DNS is 53. HTTP is 80. HTTPS is 443. The backend is on 5000. MariaDB is on 3306 but should not be reachable from the network. Being explicit about ports prevents confusion during debugging.
  5. Where do logs go? Nginx access and error logs. MariaDB error logs. BIND9 journal entries. The Flask application's own output. Being explicit about this is what lets you debug at 2 AM.

Our lab layout

Component Where Port Notes
DNS (BIND9) Server VM · 192.168.56.1 53/udp, 53/tcp Authoritative for lab.local, forwards everything else
HTTP (Nginx) Server VM · 192.168.56.1 80/tcp Reverse proxy for app.lab.local
Backend (Flask) Server VM · 127.0.0.1 5000/tcp (loopback only) Only reachable from Nginx via loopback
Database (MariaDB) Server VM · 127.0.0.1 3306/tcp (loopback) or Unix socket Not reachable from the network
Client Client VM · DHCP from server — Uses server as DNS resolver; tests the full stack
The single-VM vs multi-VM decision. For this lab, everything can run on one VM — DNS, Nginx, backend, and MariaDB — with a client VM connecting to it. That keeps the setup manageable and keeps the debugging on one machine. If you have enough memory, you can alternatively split the database onto a second VM, which is closer to a real production layout. The choice is yours. The critical thing is: write down what you chose, and stick to it while debugging.

What we will NOT do in this lab

There is a temptation, when building an integrated stack, to pile on extra features: TLS, rate limiting, load balancing across multiple backends, replication. Resist that temptation. The point of the integrated lab is to build one correct stack, and prove it works end to end. Every feature you add is another surface where something can break, and every break makes the integration harder to debug.

So in this lab we will not:

  • Configure HTTPS with real certificates. We will use plain HTTP on port 80. TLS is a Week 12 topic, and we already know how to add it later.
  • Implement load balancing across multiple backends. One backend is enough to demonstrate the pattern.
  • Set up DNSSEC, zone transfers, or secondary name servers. One authoritative server is enough.
  • Configure database replication.

Each of these is a real feature that production systems use. But each deserves its own focused learning week. Our goal here is integration — pulling the pieces we already know into a system that works. Add complexity only after correctness.

One server VM provides all four services. The client VM talks to the server only through the network — it never sees the internal proxy or database.

14.3 · The DNS Layer — Service Discovery

DNS is the first layer the client touches. Before any HTTP request is made, the client needs to translate a name — app.lab.local — into an IP address — 192.168.56.1. If that translation fails, nothing else in the stack can help.

What the zone needs

In the Week 11 lab, we built a minimal lab.local zone. For the integrated lab, we need it to serve a few specific records:

Record Type Value
lab.local SOA Zone apex, with current serial and reasonable timers
lab.local NS ns1.lab.local.
ns1 A 192.168.56.1
app A 192.168.56.1
db A 192.168.56.1

Notice that both app.lab.local and db.lab.local point at the same address — 192.168.56.1 — because in our lab everything lives on one VM. In a real layout with separate servers, they would point at different addresses. But the client does not need to know — the client just uses names.

The architectural win of DNS: the client never needs to know the IP address of the application. It only needs a name. If you decide to move the application to a different server tomorrow, you change one record in the zone and update the serial. The client needs no changes at all. This is what "service discovery" means, and it is why DNS is such an important layer of the stack.

What DNS gives us in this lab

  • Stable names for services. The client uses app.lab.local; the application server can move or change without the client noticing.
  • A place to test DNS resolution. We can run dig from the client and confirm the record is correct before debugging HTTP or the database.
  • A dependency the other layers rely on. Nginx's virtual host uses server_name app.lab.local. So does the client's HTTP request. If the DNS resolution and the server_name do not agree, Nginx will serve the wrong virtual host or reject the request.

The DNS integration checklist

  1. Is BIND9 running? systemctl status named.
  2. Does the zone file parse? named-checkzone lab.local /etc/bind/db.lab.local.
  3. Is the zone loaded? journalctl -u named -n 20 — look for "zone lab.local/IN: loaded serial ...".
  4. Does the record resolve? dig @127.0.0.1 app.lab.local A from the server.
  5. Does it resolve from the client? dig app.lab.local A from the client — this confirms that the client is pointed at our server as its resolver, and that the resolver actually answers authoritatively for the zone.

Run these five checks every time you make a DNS change. They take thirty seconds, and they tell you exactly where a problem lives.

The #1 DNS integration mistake: the client is still pointed at a public resolver — like 8.8.8.8 — instead of our own BIND9. In that case, app.lab.local will resolve to nothing, and the client will fail on step 1 of the stack. Always verify with cat /etc/resolv.conf on the client that the first nameserver line is 192.168.56.1, not a public IP.

14.4 · The HTTP Layer — Nginx and the Backend

DNS tells the client where the application lives. HTTP is how the client actually talks to it. In our stack, Nginx listens on port 80, accepts the client's request, and either serves a static file directly or forwards the request to the Flask backend.

The Nginx virtual host

The virtual host configuration is the exact pattern from Week 12, with the specifics adjusted for our lab: 

server {
    listen 80;
    server_name app.lab.local;

    # Static files served directly by Nginx
    location /static/ {
        root /var/www/app.lab.local;
        expires 7d;
        access_log off;
    }

    # Everything else is proxied to the Flask backend
    location / {
        proxy_pass http://127.0.0.1:5000;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 5s;
        proxy_read_timeout    30s;
    }
}

Let me draw attention to the connection between this file and the DNS layer. The server_name app.lab.local directive must match exactly the name the client uses in its HTTP request. If DNS resolves app.lab.local but the request goes to a different server_name — perhaps because of a typo, or because the client is using app.local instead — Nginx will fall through to its default server, and the client will get the wrong response.

The two-layer handshake that surprises beginners: Nginx has no way to know that the client intends app.lab.local unless the client actually sends that in the HTTP Host header. This is what makes curl http://192.168.56.1/ behave differently from curl http://app.lab.local/ — the first sends a Host header with an IP address, the second sends a Host header with the name. When you test the stack, always use the name, not the IP. Otherwise you are not testing the integration.

The Flask backend — what it exposes

The backend is a small application that talks to MariaDB and returns JSON. For the integrated lab, the essential endpoints are:

Route Method Purpose
/ GET A friendly HTML page confirming the service is up
/health GET A short status check that also verifies DB connectivity
/api/customers GET Returns a JSON array of all customers
/api/customers/<id> GET Returns a single customer's JSON, or 404
/api/customers POST Creates a new customer from a JSON body; returns 201 or 409

Every one of these endpoints goes through the full stack: client → DNS → Nginx → Flask → MariaDB → Flask → Nginx → client. The /health endpoint is the fastest way to verify that all the layers are working — if it returns OK, you know the connection from Flask to MariaDB is alive.

The HTTP integration checklist

  1. Is Nginx running? systemctl status nginx.
  2. Does the config parse? sudo nginx -t.
  3. Is the virtual host enabled? ls -l /etc/nginx/sites-enabled/ — you should see a symlink to app.lab.local.
  4. Does Nginx respond locally? curl -H "Host: app.lab.local" http://localhost/ on the server.
  5. Does it respond from the client by name? curl http://app.lab.local/ from the client VM.
  6. Is the backend reachable? curl http://127.0.0.1:5000/health from the server — this tests the backend directly, bypassing Nginx.
The #1 HTTP integration mistake: the backend is running, Nginx is running, but curl from the client returns a 502 Bad Gateway. That is almost always because Nginx cannot reach the backend — usually because the backend is not running, is on a different port, or is bound to a different interface. Check with sudo ss -tlnp | grep 5000 on the server.

14.5 · The Database Layer — MariaDB

The database is the layer the client never sees, and that is exactly why it matters. The client asks for a customer. The application answers. The database remembers. If the database is not durable, the memory of the customer is lost the moment the application restarts.

The database schema

For the integrated lab, we use the same schema we built in Week 13 — a small set of tables that demonstrate real relationships and real use of SQL: 

CREATE DATABASE app_db
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;

USE app_db;

CREATE TABLE customers (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    name       VARCHAR(100) NOT NULL,
    email      VARCHAR(255) NOT NULL UNIQUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;

CREATE TABLE orders (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    customer_id  INT NOT NULL,
    total        DECIMAL(10,2) NOT NULL,
    placed_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
        ON DELETE CASCADE
) ENGINE=InnoDB;

The application user

The application connects with a specific user, restricted by host and privilege: 

CREATE USER 'app'@'localhost' IDENTIFIED BY 'a-strong-password';

GRANT SELECT, INSERT, UPDATE, DELETE
    ON app_db.*
    TO 'app'@'localhost';

FLUSH PRIVILEGES;

Four privileges. Nothing more. The application cannot drop tables, cannot create users, cannot read or write outside its own database. This is the principle of least privilege in action, and it is what limits the damage if the application is ever compromised.

Why not just use root? Because if the application runs as root, and an attacker finds a way to exploit the application, they instantly have full control of the database. Every table, every user, every other database on the same server. Least privilege is not paranoia — it is proportionate risk management.

The database integration checklist

  1. Is MariaDB running? systemctl status mariadb.
  2. Does the app user exist with the right grant? SHOW GRANTS FOR 'app'@'localhost';
  3. Is the database reachable from the backend? Run mysql -u app -p app_db -e 'SELECT 1;' on the server.
  4. Do the tables exist? SHOW TABLES; inside the app_db database.
  5. Does the health endpoint see the DB? curl http://127.0.0.1:5000/health should return OK.
The #1 database integration mistake: the database is running, but the application cannot reach it — because the credentials are wrong, because the user does not have a grant on the right database, or because the host in the user's @host part does not match where the app actually connects from. Check with SHOW GRANTS and remember: if the app connects via the Unix socket, localhost is correct; if it connects via TCP to 127.0.0.1, it needs a user granted on 127.0.0.1 as well.

14.6 · Wiring the Three Together

We have each layer in isolation. Now let us look at what actually connects them. This is the part most tutorials skip, and it is the part that matters most for operations.

The five connections between the layers

From To What flows
Client DNS (BIND9) DNS queries for app.lab.local · UDP port 53
Client Nginx HTTP requests · TCP port 80 · with Host: app.lab.local
Nginx Flask HTTP requests with proxy headers · TCP port 5000 · loopback only
Flask MariaDB SQL queries · Unix socket (or TCP 3306 on loopback)
All layers Logs journal, files under /var/log, application stdout

Every single one of these connections is a place where integration can break. And notice something important: the client only knows about two of them — the DNS query and the HTTP request. The client has no idea that Nginx proxy-passes to Flask, or that Flask talks to MariaDB. That invisibility is by design: it means the internal architecture can change without the client ever needing to know.

The configuration files involved

Here is every file we touch, and which layer of the stack each one belongs to: 

/etc/bind/named.conf.options          — DNS resolver options, forwarders
/etc/bind/named.conf.local            — zone declarations
/etc/bind/db.lab.local                — forward zone file

/etc/nginx/sites-available/app.lab.local  — virtual host & reverse proxy
/etc/nginx/sites-enabled/app.lab.local    — symlink (activation)

/opt/myapp/app.py                     — Flask application

MariaDB internal schema: app_db, customers, orders, app user

Each of these files is small. Each of them can be read end to end in under a minute. That is the point. A well-designed stack is not a maze of code — it is a small number of files, each doing one job, in a place where an operator can find it.

A mental model that will save you time: when you have to change something in this stack, always start from the file that owns the thing you want to change. Want to serve a different domain? Zone file for the hostname, Nginx for the server_name. Want to move the backend port? Flask for the port, Nginx for the proxy_pass. Want to add a column? SQL. Never guess — the ownership is always clear when you look at the file.

The startup order

When you bring up the full stack, order matters. If Nginx starts before the backend, it will fail to proxy the first requests. If the application starts before MariaDB, it will fail to connect on the first query.

The correct order of activation:

  1. MariaDB — enable and start. Verify with systemctl status mariadb.
  2. DNS (BIND9) — enable and start. Verify with systemctl status named.
  3. Flask backend — start it. Verify with curl http://127.0.0.1:5000/health.
  4. Nginx — enable and start. Verify with curl -H "Host: app.lab.local" http://localhost/.

Reverse the order to cleanly take the system down. This order minimizes the noise in the logs during startup, and it makes it obvious which layer a startup problem belongs to.

Automation hint: in a real deployment, you would enforce this order with systemd dependencies — a unit file for the Flask app with After=mariadb.service and After=named.service. For the lab, you can do it manually. But remember that ordering exists, because the alternative is a class of mysterious startup failures.

14.7 · End-to-End Testing

An integrated stack is not proven by any single test. It is proven by a sequence of tests, each confirming one layer, and a final test that confirms the whole chain. This section gives you that sequence.

Layer-by-layer verification

Run these on the client VM. Each one isolates one layer.

Layer 1 — Name resolution

dig app.lab.local A

# Expected: a NOERROR response with an A record for 192.168.56.1
# and the "aa" flag (authoritative answer).

If this fails, the problem is DNS. Check cat /etc/resolv.conf on the client, and check BIND9 on the server.

Layer 2 — HTTP transport

curl -v http://app.lab.local/

# Expected: HTTP/1.1 200 OK, plus HTML from the backend, plus
# a small set of response headers from Nginx.

If this fails, the problem is HTTP or the reverse proxy. Check Nginx and the backend on the server.

Layer 3 — Backend without Nginx

Run this on the server itself: 

curl http://127.0.0.1:5000/health

# Expected: "OK" — the backend is alive and can reach MariaDB.

If this fails but the previous step succeeded, the problem is inside the backend or its connection to the database.

Layer 4 — Database directly

On the server: 

mysql -u app -p app_db -e "SELECT COUNT(*) FROM customers;"

# Expected: a number >= 0.

If this fails, the problem is database access — privileges, credentials, or the database not being reachable.

The full round-trip test

Once each layer works in isolation, do the full integration test. This is what your deliverable is really about. 

# From the client VM:

# 1. Verify DNS resolution
dig app.lab.local A

# 2. Create a customer through the whole stack
curl -X POST http://app.lab.local/api/customers \
    -H "Content-Type: application/json" \
    -d '{"name":"Layla","email":"layla@lab.local"}'

# Expected: 201 Created, with the new customer JSON.

# 3. Read it back through the whole stack
curl http://app.lab.local/api/customers

# Expected: JSON array including Layla.

# 4. Verify directly in the database
# (on the server)
mysql -u app -p app_db -e "SELECT * FROM customers WHERE email='layla@lab.local';"

# Expected: Layla's row.

The key insight in step 4: even though you created the customer via the client through the full stack, the data is really there in the database. Persistence is not an abstraction — it is a fact about where the bytes are.

This is the "money test" of the week: you create data from a client that knows nothing about the internal architecture, and then you find that data sitting in a database on a different layer of the stack. That is what a real service does. That is what you built.

Failure injection — the most educational tests

A working stack is good. A stack you can debug is better. The way to learn to debug is to break things on purpose. Here are five experiments, each of which fails one layer and creates a recognisable symptom:

1. Stop MariaDB

systemctl stop mariadb
curl http://app.lab.local/api/customers

The client sees a 500-level error. Nginx logs at 500. The backend logs show a DB connection error. This teaches you that a 500 in the client log always means some internal layer failed, not necessarily the one you are looking at.

2. Stop the Flask backend

pkill -f app.py
curl http://app.lab.local/

The client sees 502 Bad Gateway — the classic "Nginx could not reach the backend" status. The Nginx error log names the exact problem: connection refused. Learning to distinguish 502 from 500 in the client log is the difference between blaming the wrong layer and fixing the right one.

3. Break DNS

# On the client, temporarily use a bad resolver
echo "nameserver 192.0.2.1" | sudo tee /etc/resolv.conf
curl http://app.lab.local/

The client cannot even resolve the name — the error is "Could not resolve host." Nothing on the server is wrong. This teaches you that when the failure is name resolution, no amount of looking at Nginx logs will help.

4. Break the Nginx config

# Introduce a typo in the server_name,
# then reload and test

The client gets the default Nginx page instead of the app. The DNS resolution works, the backend works, but the virtual host selector no longer matches. This teaches the difference between "the service is running" and "the service is answering this particular request."

After each of these experiments, undo the change and confirm the stack works again. That cycle — break, observe, diagnose, fix, verify — is the loop that every operations engineer runs for a living.

14.8 · Diagnosing Failures Across Layers

The hardest part of operations is not building the stack. It is diagnosing it when something goes wrong. This section gives you a structured methodology that works on any three-tier stack, not just the one we built.

The bottom-up diagnostic walk

When a request fails, walk the stack from the bottom up. At each layer, ask the same three questions: is the service running, is it reachable, is it configured for this request?

Layer Is it running? Is it reachable? Is it configured right?
DNS systemctl status named dig @127.0.0.1 app.lab.local Zone file has the right A record; serial is up to date
Nginx systemctl status nginx curl -H "Host: app.lab.local" http://localhost/ server_name matches; proxy_pass points at the right port
Backend ps aux | grep app.py curl http://127.0.0.1:5000/health Connection string points at the right DB; user credentials are correct
MariaDB systemctl status mariadb mysql -u app -p app_db -e 'SELECT 1;' User has the right grant; database and tables exist

Diagnose in this order. When you find the first layer that fails its check, that layer is the problem — or something even lower down. Fix it, then re-run the client test. Do not try to solve multiple layers at once.

Where the logs live

Every layer of our stack produces its own logs, and every log answers a specific question:

Log Question it answers
journalctl -u named Did BIND9 load the zone? Did it reject any queries?
/var/log/nginx/access.log Did the client's request arrive at Nginx? What was the status code?
/var/log/nginx/error.log Why did Nginx fail to serve the request — bad config, unreachable backend, or a client-side problem?
Backend stdout / journal Did Flask receive the request? Did it fail? What was the exception?
journalctl -u mariadb Did MariaDB refuse a connection? Was there an SQL error?
The single most useful debugging habit: before you change anything, read the logs in order. Start with the log of the highest layer that logged an error, and work down. Nine times out of ten, the first error message in the highest layer's log contains exactly the pointer to the layer below that is broken.

Symptom-to-layer cheat sheet

A quick reference for the most common failure symptoms:

  • "Could not resolve host" → DNS layer. Check /etc/resolv.conf on the client, then BIND9 on the server.
  • "Connection refused" on port 80 → Nginx is not listening, or is listening on a different interface. ss -tlnp | grep :80.
  • 502 Bad Gateway → the backend is unreachable from Nginx. ss -tlnp | grep :5000 on the server.
  • 500 Internal Server Error → the application itself failed. Read the backend's log — SQL error, bad request, unhandled exception.
  • 504 Gateway Timeout → the backend is running but is too slow to respond within the proxy's read timeout.
  • Wrong page (default Nginx page) → the virtual host did not match the request's Host header. Check server_name in Nginx.
  • Data disappears after restart → the database is not the one you think it is — probably you are running SQLite or an in-memory store instead of MariaDB.
Bookmark this cheat sheet. Every one of these symptoms is something you will see again on a real production system — not because the systems are identical, but because the patterns are. "502 means the layer immediately above me could not reach me" is a truth that generalizes to every reverse proxy on the planet.

14.9 · Deep Lab — Building the Integrated Stack

Time to build. Everything below assumes you have completed Weeks 10–13. If any layer is not already working in isolation, fix it first. Integration of broken pieces only multiplies confusion.

Step 1 — Confirm the prerequisites

On your server VM, verify that all four services are installed and functional in isolation: 

systemctl status mariadb
systemctl status named
systemctl status nginx

# And confirm the backend is running:
curl http://127.0.0.1:5000/health

If any service is not running, or does not respond to its isolation test, fix that before proceeding. Integration of broken layers just produces broken integration.

Step 2 — Configure the DNS zone

Edit the forward zone on your BIND9 server and make sure you have records for our application: 

sudo nano /etc/bind/db.lab.local

Ensure these records are present:

ns1     IN  A   192.168.56.1
app     IN  A   192.168.56.1
db      IN  A   192.168.56.1

Increment the serial. Validate and reload: 

sudo named-checkzone lab.local /etc/bind/db.lab.local
sudo systemctl reload named
sudo journalctl -u named -n 10   # confirm the new serial is loaded

Step 3 — Configure the Nginx virtual host

sudo nano /etc/nginx/sites-available/app.lab.local

Use this configuration, adjusting the backend port if yours differs:

server {
    listen 80;
    server_name app.lab.local;

    location /static/ {
        root /var/www/app.lab.local;
        expires 7d;
        access_log off;
    }

    location / {
        proxy_pass http://127.0.0.1:5000;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 5s;
        proxy_read_timeout    30s;
    }
}

Enable the site and reload:

sudo ln -s /etc/nginx/sites-available/app.lab.local \
           /etc/nginx/sites-enabled/

# Remove the default site if it is still enabled, to remove ambiguity
sudo rm -f /etc/nginx/sites-enabled/default

sudo nginx -t
sudo systemctl reload nginx

Step 4 — Verify the backend and its DB connection

Make sure the Flask application exists and is running. From Week 13, you should have /opt/myapp/app.py. Start it if it is not running: 

python3 /opt/myapp/app.py &

# And verify:
curl http://127.0.0.1:5000/health
curl http://127.0.0.1:5000/api/customers

Step 5 — Local integration check

Before involving the client VM, verify the stack works locally: 

# Direct to Nginx with the Host header:
curl -H "Host: app.lab.local" http://localhost/api/customers

# Expected: the JSON array from the database, proxied through Nginx.

If this works, the DNS/Nginx/Flask/MariaDB chain is correct on the server side. If it does not, debug each layer with the isolation commands from section 14.8.

Step 6 — Point the client at the server for DNS

On the client VM, verify that it is using our server as its DNS resolver: 

cat /etc/resolv.conf

# Expected: first "nameserver" line is 192.168.56.1

If it is not, edit /etc/netplan/*.yaml or /etc/resolv.conf on the client to use our server first. Apply and re-check.

Step 7 — Full test from the client

# From the client VM:
dig app.lab.local A
# Should return 192.168.56.1 and the "aa" flag.

curl http://app.lab.local/api/customers
# Should return the JSON array.

curl -X POST http://app.lab.local/api/customers \
    -H "Content-Type: application/json" \
    -d '{"name":"Integration Test","email":"itest@lab.local"}'
# Should return 201 Created.

curl http://app.lab.local/api/customers
# The new customer should be in the response.
When this works, you have built a three-tier web application. Take a moment to recognize what happened: a client that knows nothing about your internal architecture resolved a name, made an HTTP request, had that request routed by a reverse proxy to a backend application, which queried a database, and the result came back to the client. Every layer was a service you configured. That is not a lab exercise — that is the pattern of production software.

The build is not the deliverable. The proof is. Every serious infrastructure change ends with documentation: what was done, whether it works, and how you know. This section walks you through producing that evidence.

Every real deployment is described by a service inventory. Write one for your stack. It is short — one row per service — and it is the single most useful document when someone else has to operate the system.

This inventory is not a formality. It is the difference between a system that two engineers can jointly own and a system that only one person can touch.

Real-world habit: commit the service inventory to version control alongside the configuration files. When you change a port, a path, or a policy, update the inventory at the same time. Documentation that lives separately from the code it describes drifts; documentation that is versioned alongside the code stays accurate because it has to.

Writing a short technical report

Your final report should answer four questions, in order:

  1. What was built? The architecture, the components, the network layout. A short paragraph and the stack diagram.
  2. How does it work? The flow of a request through the stack, from client to DNS to Nginx to backend to database and back. Include one concrete example — "a POST to /api/customers goes..." — with the actual commands.
  3. How do you prove it works? The evidence — the command outputs from the verification section. Each one captioned with what it demonstrates.
  4. How would you debug it if it broke? The diagnostic methodology — the bottom-up walk, the logs at each layer, the symptom-to-layer cheat sheet. This shows that you not only built the system but understand how to operate it.

The report should be short. Two to four pages is plenty. The point is not to impress with length — it is to prove that you understand what you built.

What you have at the end of this week: not just a working stack, but the evidence that it works and a documented methodology for keeping it that way. That combination — working system, evidence, and methodology — is the exact package that a professional engineer delivers when asked to "build a service."

Week 14 Summary

  • Integration is a discipline. DNS, HTTP, and MariaDB in isolation are three services. Wired together, they are a three-tier application — and that is what production software looks like.
  • Every layer has a clear role. DNS resolves names to addresses. HTTP transports requests and dispatches to the backend. MariaDB stores the data durably. Each layer can be tested in isolation, and each layer answers a specific question.
  • Plan before you build. Five questions — domain, addresses, hostnames, ports, log locations — and a written layout. This is what makes the lab tractable and what makes the system maintainable afterward.
  • Wiring is small and specific. Five connections between layers, each one editable in a single line of a single config file. When something breaks, the file that owns the broken connection is almost always obvious.
  • Test layer by layer, then end to end. Isolate each layer with one command. Then run the full round-trip test. If layer isolation fails, integration is hopeless — fix the layer first.
  • Diagnose from the bottom up. Running? Reachable? Configured for this specific request? Three questions, at each layer, in order. Stop at the first failure, fix it, re-test.
  • Know the symptom-to-layer map. "Could not resolve host" is DNS. 502 is the backend being unreachable. 500 is the backend itself. Wrong page is a virtual host mismatch.
  • Documentation is a deliverable. A service inventory, a technical report, and evidence. Together, they turn a working system into an owned system.
  • This is the pattern. Every serious web service in the world has the shape you just built. The tool names differ — HAProxy instead of Nginx, PostgreSQL instead of MariaDB, Kubernetes instead of systemd — but the layers, the connections, and the diagnostic methodology are the same.
